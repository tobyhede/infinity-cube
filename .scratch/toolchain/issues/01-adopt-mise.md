# 01 — Adopt mise for toolchains and tasks

**Status:** ready-for-agent

**Category:** enhancement

**Blocked by:** rust-host 16, which removes the `db:migrate*` scripts and adds the `migrate` verb this ticket makes a task.

**What to build:** Bring in [mise](https://mise.jdx.dev/) repo-wide: one `mise.toml` pinning Node and pnpm and defining the repository's tasks that have no pnpm script, used both locally, by agents, and in CI. The acceptance criteria are the Agent Brief's, below.

**Why:** Toolchains are pinned in three places today: `package.json` (`engines.node`, `packageManager` for pnpm), `rust-toolchain.toml` (Rust) and each CI job's `pnpm/action-setup` and `actions/setup-node` steps. Tasks are split between `package.json` scripts and cargo commands spelled out in `AGENTS.md`. When the grilling of rust-host 16 asked whether `pnpm db:migrate*` should survive as wrappers over the Rust verb, the maintainer asked whether mise should replace them, and chose to take that up here rather than in 16 (2026-11-23). mise was chosen over `just` (tasks only) and Nix or devbox (heavier) because one tool both pins toolchains and runs tasks (2026-11-24).

### Agent Brief (confirmed with the maintainer, 2026-11-24)

**Category:** enhancement
**Summary:** A `mise.toml` that is the truth for the Node and pnpm versions and holds the tasks without a pnpm script; CI, agents and contributors get their tools through it.

**Current behavior:** Node is pinned by `engines.node` and pnpm by `packageManager` in the root `package.json`; Rust by `rust-toolchain.toml`, which rustup reads. Every CI job that needs Node installs it with `pnpm/action-setup` then `actions/setup-node` with `cache: pnpm`. Commands with no pnpm script (`cargo run -p infinity-cube --locked -q -- migrate --store …` after rust-host 16, the `rust` job's `cargo fmt`, `clippy`, doctest and `nextest` invocations, the HTTP conformance run against the Rust CLI) are written out in `AGENTS.md` and the workflow files. Agents run in non-interactive shells, so nothing activates a version manager for them.

**Desired behavior:**

- **Pins.** `mise.toml` at the repository root pins Node and pnpm, and is the one place a version is changed. `packageManager` and `engines.node` stay, because pnpm and npm read them, and a unit test fails when either disagrees with `mise.toml`. `.node-version`, which CI's `setup-node` steps read, is deleted once no job reads it, and anything else that names it (the release-build instructions among them) is pointed at `mise.toml`. Rust stays pinned by `rust-toolchain.toml`, which rustup and cargo read wherever they run (under mise too); `mise.toml` does not pin a second Rust version.
- **Tasks.** `mise.toml` defines a task for each command that has no pnpm script: at least `migrate` (taking the store), the four Rust checks the `rust` job runs, and the HTTP conformance run against the Rust CLI. The `package.json` scripts stay where they are; `verify` stays defined only there, and no mise task duplicates a pnpm script. CI and `AGENTS.md` call the mise tasks instead of spelling the commands out.
- **CI.** `jdx/mise-action`, pinned by commit as every other action is, replaces each job's `pnpm/action-setup` and `actions/setup-node` steps. The pnpm store stays cached, keyed on the lockfile, and no job's setup gets slower than on `main`: compare the setup step times of the PR's CI run with a recent `main` run and report them.
- **Release.** `release/build.sh` and the install script do not require mise: a person who runs the build needs only the pinned tools, however installed, and a tester who downloads a preview build needs nothing. The release workflow's jobs get their tools through mise as CI's do.
- **People.** `AGENTS.md` and the getting-started skill tell a contributor to activate mise in their interactive shell by adding `eval "$(mise activate bash)"` (or their shell's equivalent) to its rc file, mise's own recommendation for an interactive shell; `mise activate` alone only prints that script, before `mise install`, so bare `pnpm` and `node` resolve; the documented commands stay bare `pnpm …`.
- **Agents (Claude Code).** A SessionStart hook in the tracked `.claude/settings.json` appends `eval "$(mise hook-env -s bash)"` to `$CLAUDE_ENV_FILE`, as mise's [Coding agents](https://mise.jdx.dev/agents.html) page sets out, so every Bash command an agent runs has mise's tools and follows `cd`; it does nothing, and fails nothing, where mise is not installed. The cloud environment's setup script (a Claude Code environment) installs mise and runs `mise install`, which needs network access to wherever mise downloads Node and pnpm from; if the environment's network policy refuses that, say so in the PR rather than working around it.
- **Docs.** `AGENTS.md` Commands names `mise install` as the install step before `pnpm install` and names the tasks; `docs/agents/build-tooling.md` records where each version is pinned and which file wins; the `infinity-cube-getting-started` skill makes mise the one tool to install, with the version bump in all three plugin manifests that a change to it needs.

**Acceptance criteria:**

- [ ] In a fresh clone and a shell that has evaluated `mise activate`'s output (`eval "$(mise activate bash)"`), `mise install` installs the pinned Node and pnpm, after which bare `pnpm install` and `pnpm verify:local` succeed.
- [ ] A unit test fails when `packageManager` or `engines.node` disagrees with `mise.toml`, and passes on the PR.
- [ ] `mise run migrate` (or the task's chosen name) migrates each store as `infinity-cube migrate --store <store>` does, and the Rust check and conformance tasks run what the `rust` job runs.
- [ ] No CI job or release job uses `pnpm/action-setup` or `actions/setup-node`; `CI passed` is green, and the PR reports setup step times against `main`.
- [ ] `sh release/build.sh` succeeds on a machine with the pinned tools and no mise.
- [ ] A Claude Code session in the repository finds `node`, `pnpm` and the mise tasks in a plain Bash command without `mise x`, and a session without mise installed starts without error.
- [ ] `AGENTS.md`, `docs/agents/build-tooling.md` and the getting-started skill (with the manifest bumps) say what is above.

**Out of scope:**

- Moving the `package.json` scripts, `verify` among them, into mise tasks.
- Pinning Rust in `mise.toml` or removing `rust-toolchain.toml`.
- Codex and other agents: mise's Coding agents page offers Codex only a weaker, untested shim setup, so `AGENTS.md` notes that a non-Claude agent needs mise's shims on its PATH and nothing more is built for one here.
- mise's MCP server (`mise mcp`): the repository's tasks already run through Bash.
- Adopting a community mise skill.
- Managing secrets or environment variables (`.env`) through mise.
- System libraries (WebKitGTK, PostgreSQL), which stay with the operating system and Compose.
