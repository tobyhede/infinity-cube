# 04 — The SQL repository's concurrency seam, and its test instrumentation

**Status:** ready-for-agent

**Blocked by:** 02 (so SQLite's table cases guard the refactor).

**What to build:** The one Rust SQL repository (`crates/host/src/sql.rs`) made able to run the TypeScript PostgreSQL protocol (`spec.md`, Where things stand) while SQLite keeps its answers; the two shared gaps the audit found, fixed failing test first; and the instrumentation 06, 07 and 12 pause and observe operations through.

- [ ] Process serialisation becomes the store's choice: SQLite keeps the mutex now at `sql.rs:183`/`:227`; a store may run operations concurrently. `close()` waits for operations under way on either store.
- [ ] `SqlStore` gains the aggregate lock in two modes, taken as the first statement after the transaction's own `BEGIN`: exclusive for aggregate commits, `load_aggregate` and both lifecycle doors (`src/persistence/sql-space-repository.ts:763-772` and its callers); shared for the single-Space fast path (`:623`); none for `list_spaces`, `load_space`, `load_meta_space_id`, `mark_exported`, `store_asset` and `load_asset` (`:304-326`, `:937-941`, `:491-499`, `:412-444`). The store chooses how a transaction begins (Q3: SQLite's `BEGIN IMMEDIATE` for writes; PostgreSQL's `READ COMMITTED` for locking transactions and `REPEATABLE READ READ ONLY` for multi-statement unlocked reads).
- [ ] The fast path and the aggregate decision run in separate transactions, the first ended before the second begins (`:555-596`), nothing written before the hand-off.
- [ ] An update writes as `#writeUpdate` does (`:673-701`): take the row lock while reading the revision the row carried when the lock was granted; if it differs from the expected revision, roll back and answer a conflict carrying the Space read afresh outside the transaction (`:537-550`); else write the next revision, re-read the Space's Resource rows under the lock, and write only those that changed.
- [ ] **Shared gap, fixed failing test first:** a Resource upsert reads back the row's owner, and an update meeting a Resource another Space owns is refused as `invalid-commit` (`:709-726`), on SQLite and memory too. Today `upsert_resource` (`sql/sqlite.rs:373-386`) reads nothing back.
- [ ] **Shared gap, fixed failing test first:** `install` and a created Space insert rather than upsert their Space rows (`write_space`, `sql/sqlite.rs:301-312`), and a deleted Space's delete checks a row was removed (`:578-592`), so a row written by anything outside the lock surfaces as TypeScript surfaces it.
- [ ] The Meta identity is read and its row locked, re-read once if a replacement moved it, and answered Unreachable after a second move (`:763-772`). Replacement relocks every stored row in id order and conflicts if a revision moved since its baseline (`:1001-1017`), answering the Meta identity read afresh (`:1020-1026`), without decoding any document (ADR 0094). Initialization that loses a primary-key race on `spaces` or `repository_state`, or an ownership race on `resources`, re-reads and classifies (`:964-979`).
- [ ] **Each operation runs to completion (Q16):** the repository runs each operation in a `tokio::spawn`ed task that owns its connection and transaction, and the caller awaits its answer; dropping the caller drops only the wait. Both stores, so SQLite's process mutex is released by the task, not the caller. A test drops the caller at each pause point below and holds that the store reaches the state the operation would have reached and that the next operation is not blocked by a lock left behind.
- [ ] **Instrumentation** behind the `test-support` feature (02): pause an operation at a named step (the Meta read, the complete read, a Space's row lock, the Resource re-read, the replacement's truncation) until the test releases it; record each lock taken with its mode; and the recreation hook 02 left unprovided, now placed at the row-lock step. SQLite's harness provides the hook, so 02's pending `:2444` exemptions are deleted here.
- [ ] A Rust unit test of the seam over a scripted store (no database) holds each operation's statement order (which lock, which mode, before which read; the fast path's transaction ended before the aggregate one begins), and drives the branches a real database reaches only under a race: a prior revision under the row lock that differs from the decision read (conflict, nothing written), a relock that finds the Meta row gone once (retried, the second identity answered) and twice (Unreachable).

**Named mutants (each killed by this ticket's tests):** fast path takes the exclusive lock; fast path takes no lock; aggregate path takes the shared lock; fast path and aggregate decision in one transaction; revision compared from the decision read instead of the row lock's answer; Resource rows judged against the decision read (killed by the table case `:2444` once the hook exists); Meta relock retry removed; Meta relock answers the identity read before the move; replacement skips the per-row relock; conflict answered with the Space read inside the aborted transaction; upsert ownership read-back dropped; `install` upserting again; an operation run on the caller's future instead of a spawned task (killed by the dropped-caller test at the fast path's hand-off).
