# 13 — Swap the sidecar for the Rust host

**Status:** ready-for-human

**Blocked by:** 04, 07, 08, 12.

**What to build:** The shell from 04 composes the Rust `host` in its own process instead of starting the Node sidecar: one run per window, served through a custom URI scheme (no port, so no Host check or launch secret), the same Content Security Policy, and Export awaited before a window or the application closes. Only once the intake corpus (07) is green through the Rust `check` and the HTTP conformance suite (08) is green against the Rust binary (12), both in CI. Test on a temp copy of `packages/app/fixture`.

**One origin per talk.** Each talk is served from its own origin under the scheme, with the talk in the host part (spec, decision 4), so two talks presenting at once do not share a `BroadcastChannel` or Web Locks; and the host part is the same on every launch of that talk, so what the page keeps in `localStorage` (the colour scheme) survives a restart, which the sidecar's random port did not give. Opening a Resource independently and the Notes window open under the same origin as their talk.

**Windows.** Tauri serves a custom scheme on Windows from `http://<scheme>.localhost`, so the scheme, not the host part, sets the origin there, and talks under one scheme would share an origin. Decide before the swap, and record here: either register one scheme per talk on Windows, named stably from the talk so the origin survives a restart, or key the presentation channel and lock names by talk and accept a shared `localStorage` on Windows. 22 ships Windows; this ticket does not, but its seam must not rule either out.

**What goes and what stays.** The shell's sidecar wiring (`src-tauri/src/sidecar.rs`), `packages/desktop/scripts/build-sidecar.ts`, the `externalBin` entry, the Node single-executable build and the sidecar step in 06's release pipeline go. The production Node host itself (03, `src/desktop/`) stays: it is the host 08 holds every other one to in CI, and the host the standalone-http-host tickets adopt, until 20 retires it.

**A seam first.** (Done, then removed: once the swap left one server behind the seam, the trait was a single-adapter port, which `AGENTS.md` rules out; `main.rs` calls `server::TalkServer` directly, and `Registry<S>` stays generic so its transitions are tested without a run.) Before the swap `main.rs` called the sidecar directly (`sidecar::start` and the `Sidecar` type). Put the talk server behind a small seam in the shell (a trait, or an enum of the two servers) before the swap, so that swapping is one module and the window code does not change.

- [x] A 10 MiB asset upload works through the custom scheme.

## Decisions and evidence (recorded by the implementation)

**The per-talk origin (the spec's open question).** A talk's key is the first 128 bits of the SHA-256 of its canonical folder path, as 32 lower-case hex digits (`packages/desktop/src-tauri/src/address.rs`); on macOS and Linux the talk is served at `infinitycube://<key>/`. It is the simpler of the two answers: it needs no state, since the shell already canonicalizes a folder (two spellings are one talk), so the same folder has the same key on every launch; and it is safe in a URL host and in a scheme name, and names nothing of the path. An id the shell kept would need a store mapping folders to ids beside the application, and could not live in the folder itself, which only Export writes (ST-65). The cost: a folder moved or renamed gets a new origin, and what its page kept in `localStorage` (the colour scheme) is not carried over.

**Windows.** Decided: one scheme per talk, `infinitycube-<key>`, served by Tauri from `http://infinitycube-<key>.localhost/`, named stably from the talk as above, so each talk keeps its own origin and its `localStorage` across restarts, and the browser application does not change (the spec rules out changing it, which keying channel and lock names by talk would). Tauri can register a scheme after the Builder: `AppHandle::plugin` initializes a plugin at runtime (`tauri` 2.12.5 `src/app.rs:528`), a plugin's `initialize` registers its schemes into the webview manager (`src/plugin.rs:811-816`), and each webview is handed the schemes registered when it is created (`src/manager/webview.rs:232-243`); wry rewrites `infinitycube-<key>://localhost/…` to `http://infinitycube-<key>.localhost/…` for WebView2 and back for the handler (`wry` 0.57.2 `src/custom_protocol_workaround.rs`), matching a request to a scheme by the `<scheme>.` prefix, so `infinitycube.` and `infinitycube-<key>.` do not collide. The shell does this when a talk's window opens (`register_talk_scheme` in `src/server.rs`, once per scheme, as a plugin named for the scheme), and the address, key parsing and navigation rule have both styles (`SchemeStyle`), unit-tested on every platform. Windows is not built or tested here (22 ships it); the code path compiles on Linux but has never run.

**The `Origin` rule, as WebKitGTK sends requests.** Under Xvfb with WebKitGTK 2.52.6, a page's `fetch` POST to its own origin under the custom scheme carries no `Origin` header at all, only `Referer` (the page), `Content-Type`, `Accept` and `User-Agent`. A rule requiring the talk's `Origin` would refuse every Edit. The handler therefore admits a change whose one `Origin` is the talk's, or which names no `Origin` and whose one `Referer` is a page of the talk; any other `Origin`, more than one, or neither header is refused 403. Behind it stands a stricter check the label gives: the handler answers only the windows that belong to that talk (Tauri passes the requesting webview's label), so neither the home window nor another talk's window reaches it. What WKWebView on macOS sends was not observed.

**Redirects.** WebKitGTK does not follow a 302 a custom scheme answers a navigation with: the window stayed on the empty body of `/`. The shell asks the run for `/` itself and opens the window at the address it redirects to (the Meta Space's product address); a window of the talk later asked for `/` (a link, a reload, a page opening it) is sent there by the navigation handler (`TalkWindows::navigation`), and a page opening `/` opens a window there. Serving the redirect's target at `/` instead would not do: the browser application reads its Space from the location, and `/` is outside product addressing. The handler still answers `/` with 302 on the wire, as 08 requires.

**Windows the page opens.** Opening a Resource independently and the Notes window call `window.open(…, 'noopener')`; with no handler WebKitGTK opens nothing. The shell's `on_new_window` opens a URL of the talk's own origin as a new window of the talk (label `view-<key>-<n>`, `<n>` counted across every talk for the life of the process so no label is reused, admitted by the scheme handler as one of the talk's windows, held to the same navigation rule) and denies every other. The window is built on another thread; one built after its talk began closing is destroyed.

**Stopping.** No kill: closing a talk stops serving it, waits for every change (a request other than `GET` or `HEAD`) still being answered, with no limit, so an Edit the page was answered 200 for is in the last write (a change waits on nothing outside the process: the webview hands over its whole body and the store is in memory; a read commits no Edit, so it is not waited for), then waits for the run's last write with no limit, the window staying open until it lands. A failed write is reported on standard error and in a dialog, and the window closes once the dialog is dismissed, so closing the last window cannot take the dialog with it; on quit, on standard error only. A write still running ten seconds after a close or a quit asks whether to keep waiting or close without saving (Storage ST-122, `src/waiting.rs`, the question window `ui/closing.html`). ST-63's "stopping never loses an edit" holds again for the desktop; ADR 0155's five-second kill belonged to the sidecar.

**Paths.** The webview normalises dot segments before the handler sees a request: `/a/./b/../c%2e%2e/%2E%2E/d` arrived as `/a/d`. The handler passes the target on as received. wry builds the request's headers with `insert`, so a header the page repeats reaches the handler once, with its last value.

**Evidence.** Unit: `src/scheme/tests.rs` (the trust boundary; the body-limit, header, redirect and fallback cases of `conformance/http/wire-cases.ts` ported through the handler, a 10 MiB asset stored and served back), `src/server.rs` `closing_a_talk` (an edit written on close; an edit still being answered when the close begins written however long it takes; open and close with no edit byte for byte unchanged; a request refused once closing), `src/server.rs` `a_talk_window` (the root sent to its redirect's address) and the refusal messages (each refusal's kind and location, `intake`'s `Refusal::located`, which the CLI shares), `src/scheme/tests.rs` `names_no_window_twice_when_a_talk_is_opened_again` and `a_close_waits_for_a_change_being_answered_and_not_for_a_read`, `src/address.rs`. The blocking dialog, the root redirect in a live window and a window built while its talk closes need a window and were not run. By hand under Xvfb, with a diagnostic build (an initialization script and request log, not committed): two talks at two origins; an Edit (200) and a 10 MiB asset (201) committed from each page; a Notes window opened by a click under its talk's origin, its `BroadcastChannel` message reaching its own talk's window and not the other talk's; `localStorage` set in one launch read back in the next; a remote navigation, a remote popup and a remote `fetch` refused; closing an edited talk's window left the edit on disk, and closing an unedited one left the directory identical to the fixture; closing the home window then ended the process.

**Not met here.** Two talks not crossing and the colour scheme surviving were observed on Linux only, by hand; macOS was not available. The release pipeline (06) does not exist in this repository (no workflow under `.github/workflows/` builds a bundle), so it has no Node single executable step to remove; 06's own text now names no sidecar build.

## macOS check by hand

The maintainer runs this on a Mac before the pull request merges; nothing here has been run on macOS. Windows is not built (22), and a macOS CI job is a later change (05).

**Prerequisites:** Xcode Command Line Tools (`xcode-select --install`); rustup, which installs the toolchain `rust-toolchain.toml` pins on first use; Node 26.8.1 or later and pnpm 9; `pnpm install` at the repository root.

**Build**, from the repository root:

1. `pnpm --filter @project/app exec vite build` (the browser application in `packages/app/dist`, which the bundle carries and the shell's build script reads).
2. `pnpm --filter @project/desktop tauri build` (the bundle: `target/release/bundle/macos/InfinityCube.app`, and a `.dmg` beside it under `bundle/dmg/`).

Work on a copy of the fixture in a git repository of its own, so `git diff` shows what was written: `cp -R packages/app/fixture /tmp/talk-a && git -C /tmp/talk-a init -q && git -C /tmp/talk-a add -A && git -C /tmp/talk-a commit -qm fixture`, and the same for `/tmp/talk-b`. To see the shell's standard error, start it from Terminal: `ls target/release/bundle/macos/InfinityCube.app/Contents/MacOS/` names the executable; run it with the folder as its argument.

1. Open the application and choose Open… with `/tmp/talk-a`; expect the talk in a window of its own, titled `talk-a`, at the Meta Space.
2. Close that window without editing; expect `git -C /tmp/talk-a status --short` to print nothing (ST-65).
3. Open it again, rename a Resource, wait two seconds; expect `git -C /tmp/talk-a diff` to show the new Title in a Resource file.
4. Rename another Resource and close the window at once (within a second); expect the window to stay until the write lands and then close, and `git diff` to show the second Title. Then quit with Command-Q with a talk open and edited; expect the process to exit only after `git diff` shows that edit.
5. Open `/tmp/talk-a` and `/tmp/talk-b` together; expect two windows. Edit each; expect each folder's `git diff` to show only its own edit. Start presenting in one and open its Notes window; expect the Notes window to follow only its own talk. Choose a colour scheme in one, quit, reopen it; expect the colour scheme kept (the per-talk origin), and the other talk unaffected.
6. With `/tmp/talk-a` open, choose Open… with `/tmp/talk-a` again; expect its window focused and no second window. A second launch of the application with the same folder (running the executable again from Terminal with `/tmp/talk-a`) is not guarded: this branch keeps no lock across processes (ST-120 and ST-121 name none), so expect a second process serving the same folder in its own window, and record whether that is what happens; both would write the folder.
7. The close question (ST-122). A write that hangs cannot be made reliably by hand: a read-only folder makes the write fail at once rather than hang. To see the failure case, `chmod -R a-w /tmp/talk-a` after opening it, edit, close the window; expect a dialog "The last edit to /tmp/talk-a may not be on disk: the last write failed: …", the window closing once it is dismissed, and no close question (the write ended in under ten seconds); `chmod -R u+w /tmp/talk-a` afterwards. To see the question, put a fixture copy on an SMB share served by another machine, open it, edit, disconnect that machine from the network, and close the window; expect, if the write blocks for more than ten seconds, a small window naming the folder with "Keep waiting" (the caret on it) and "Close without saving". Keep waiting: expect it gone and back ten seconds later. Reconnect: expect it gone by itself and the talk's window closed. Repeat with Close without saving: expect the window closed at once, and opening the folder again to say it is still being written until the write ends. With two such talks writing, Command-Q: expect one question naming both folders.
8. Which header WKWebView sends on an Edit: start the executable from Terminal with `INFINITY_CUBE_LOG_ADMISSIONS=1` set and a folder as its argument, and edit; expect a line `Admitted POST /api/spaces by its Origin header.` or `… by its Referer header.` on standard error for each change. Record which here; WebKitGTK 2.52 sends only `Referer`.
