# 03 — A production Node host, with no Vite

**Status:** ready-for-agent

**Blocked by:** 02. Not blocked by 01: this ticket implements ADR 0155's first stage while the ADR is proposed, and its code landed ahead of acceptance by the maintainer's choice (17 November 2026).

**What to build:** A Node entry that composes a run (`startRun`, `src/run/run.ts`) and serves it with `@hono/node-server`: the Fetch application, product addresses through `resolveProductRequest` before the shell (routing as `packages/app/vite-space-http-plugin.ts` does today), the built `vite build` output, and `index.html` as the single-page fallback, with a Content Security Policy adapted from `packages/app/mount-headers.ts`. Locked down for a desktop sidecar (ADR 0155): binds `127.0.0.1` on a port the OS picks; refuses a request whose `Host` is not `127.0.0.1:<port>`; requires a secret minted at launch, presented once as `/?launch=<secret>` and traded for an `HttpOnly`, `SameSite=Strict` cookie by a redirect, after which every request needs the cookie (decided 17 November 2026); prints one JSON line on standard output (`src/desktop/announcement.ts`): `{ "kind": "listening", "port", "secret" }` once listening, or `{ "kind": "refused", "message" }` when it cannot run the folder; on standard input closing, stops the run (Export) and exits zero. Built into a single Node 26 binary per platform; if a single executable cannot hold the bundle, ship the Node binary and the bundled JavaScript as resources instead. The standalone-http-host tickets (`.scratch/standalone-http-host/issues/`) adopt this host rather than build another TypeScript host (spec, decision 12); 19 moves what they serve to Rust.

- [x] A Vitest suite for the Request-to-Response routing (API, product address, static file, fallback, Host refusal, missing or wrong secret). `test/unit/desktop-handler.test.ts`.

## Comments

**2026-11-17 (progress).** Built in `src/desktop/`: `desktop-handler.ts` (the Fetch function: Host check, launch secret traded for the cookie, API, product addresses, built files, page fallback with its CSP), `static-files.ts` (built files under a root, never outside it; the desktop CSP), `desktop-process.ts` (the sidecar) and `announcement.ts` (its one stdout line). `pnpm desktop-sidecar:build` bundles it to one 377 kB ES module. Checked: `test/unit/desktop-handler.test.ts` (10 cases) and `test/integration/desktop-sidecar.test.ts` (an edit written on stdin close, exit 0; a refusal announced, exit 1). By hand: the bundle served `packages/app/dist` and the fixture to headless Chromium with no console errors or CSP violations.

**Single-file form:** a Node 26.8.1 single executable application holds the bundle as an ES module (`node --build-sea` with `"mainFormat": "module"`), 151 MB on Linux x64, and ran the same edit-and-stop check. Shipping that, built per platform, rather than the Node binary beside the JavaScript. The built application directory still ships beside it as a resource.

**2026-11-17 (review).** Ticked the routing suite and the single-file record; the integration box stays open until a test starts the built executable rather than `src/desktop/desktop-process.ts` through `tsx`. Since the first comment: the session cookie's name carries the sidecar's port (`sessionCookieName`, `src/desktop/desktop-handler.ts`), because a webview keeps one cookie store for every talk window and scopes a cookie by host, not port, so two talks open at once no longer overwrite each other's cookie (`test/unit/desktop-handler.test.ts` › "keeps each window’s session when two talks share one cookie store"); and SIGHUP stops the sidecar as SIGINT and SIGTERM do, writing the last edit and exiting zero (`test/integration/desktop-sidecar.test.ts` › "writes an edit to the directory and exits zero on SIGHUP, as a run does").
