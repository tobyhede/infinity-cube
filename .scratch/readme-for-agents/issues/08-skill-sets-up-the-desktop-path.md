# 08: Teach the getting-started skill the desktop application path

**What to build:** An agent following `infinity-cube-getting-started` can set a person up to open their Space in the desktop application, which the README's Getting started now leads with, as well as with `pnpm cube run`. When the person passes on the README's "Running a Space" points, the agent tells them only what applies to the host they are using.

**Blocked by:** none. The README side landed in PR #514.

**Status:** ready-for-agent

**Why:** PR #514 rewrote the README's Getting started around the desktop application, built from source, with `pnpm cube run` as the alternative. The skill (`plugins/infinity-cube/skills/infinity-cube-getting-started/SKILL.md`) still starts only `pnpm cube run`. Its step 6 tells the agent to read the README's "Running a Space" and "Stopping and lost edits" and pass on each point. That section now also covers the desktop application, with each desktop-only clause marked inside its bullet. So a `cube run` user can be told desktop details, and a desktop user gets no build or open steps from the skill. This was raised in review on PR #514 and left out of it, because a skill change needs a plugin version bump.

- [ ] The skill offers the desktop application as a path: the tools (Rust through rustup, Tauri's system prerequisites), the browser build before `cargo build -p infinity-cube-desktop`, and opening `target/debug/infinity-cube-desktop <dir>`, each with a checkable done-signal. It takes these from the README's Getting started rather than restating them, as ticket 07 did for Running.
- [ ] The skill says which path to choose, taking the platforms from the README's Getting started rather than restating them: desktop only where the README says it runs (Linux today; on macOS only with a warning that it has not been tried; never on Windows), and only when the person wants a window and can build Rust. Otherwise, or when the agent will start the run itself (`--no-open`), `pnpm cube run`.
- [ ] For the desktop path, the skill passes on all of README Getting started step 8 and ends on its done-signal: close the Space window, then the home window (Quit on macOS); Keep waiting is always safe and Close without saving loses unwritten edits; a failed-write dialog means those edits are not on disk; and never Ctrl-C, close the terminal or send a signal, because the shell writes pending edits only on close.
- [ ] Step 6 passes on only the "Running a Space" and "Stopping and lost edits" points that apply to the chosen host. Some "Stopping and lost edits" points hold for both hosts (a kill or power cut loses the last second; a crash mid-write can leave files mixed, and git restores them), so the README marks that section's `cube run`-only clauses as "Running a Space" does, and the skill passes on the rest for the desktop path too.
- [ ] Steps 5 and 6 get desktop done-signals in place of the address, which a desktop run never prints. Signals only the person can see (the Space window showing the Map with `Resource 1`, both windows closed with no dialog) are the person's to confirm, and the agent asks them. Where the agent starts the application itself, it can also check that the process is running and `.infinity-cube.lock` exists in the directory.
- [ ] The skill's `description` frontmatter names the desktop application, so a request to set it up routes to this skill.
- [ ] The plugin version is bumped in all three manifests (`plugins/infinity-cube/plugin.json`, `plugins/infinity-cube/.claude-plugin/plugin.json` and `plugins/infinity-cube/.codex-plugin/plugin.json`; not the root `.claude-plugin/marketplace.json`), per the Workflow doc's skills section. Links stay absolute, since the skill is installed outside this repository (`test/unit/agent-skill-commands.test.ts`).
