# One Closing module between the shell's events and the close-wait decision

Candidate 3 of the desktop shell's architecture review (26 November 2026). The design was settled in the project thread on 28 November 2026.

## A term

This spec says **unasked exit** for the process ending without the application being asked first: on macOS, Quit from the Dock, or logging out (Storage ST-122). Tauri reports it only as `RunEvent::Exit`. The term is this spec's alone, and it does not go into a requirements doc or CONTEXT.md; the code names the method for it `exiting`.

## The problem

What a close, a quit and an unasked exit do is spread across `main.rs`, where no test reaches it: `on_window_event` begins a window's close, `RunEvent::ExitRequested` begins a quit and decides whether the application may end, `RunEvent::Exit` stops servers on threads of its own for an unasked exit, `spawn_stop` reports a failed write and frees the folder, `apply` carries out the close-wait decision's effects, and `waiting::drive` runs that decision on a channel. `waiting.rs` and `aggregates.rs` are tested; the wiring between them, and between them and Tauri, is not. ST-122 says so.

## What was settled

- **A `closing` module owns the handling.** `closing.rs` handles a window's close request, a quit request (including a second one while a quit is under way), an unasked exit, the question's answer, the question's own window being closed (which is Keep waiting, ST-122), a timer that elapsed, and a stop that ended. It reaches the `Registry` and `Waiting` directly. The decision's interface (`Waiting::on`, `Event`, `Effect`) is unchanged; the `waiting` module loses `drive` and gains `ask_after` (below). `main.rs` forwards Tauri's events to it and does what it answers.
- **What the shell does crosses a `ClosingPort`.** Stopping a server, saying a failed write on standard error, showing it in a dialog, starting a timer, asking or dismissing the question, closing a window, closing an Aggregate's window with the windows its page opened, and ending the application. Its Tauri adapter is `closing/tauri_shell.rs`; its tests drive a recording fake. A stop begun through the port ends when the adapter calls back, so the fake holds stops and the tests end them in the order they choose.
- **The decision runs where the event arrives.** `Waiting` sits behind a lock, and its effects go to the port while that lock is held, so they reach the shell in the order they were decided. Every port method called under the lock returns at once and never calls back into the module: the Tauri adapter hands window work to one task that does it in order, off the event loop's thread, as `drive`'s task did. Showing a failed write in a dialog waits for the presenter, so it is never called under the lock. The lock order is `Waiting`, then the `Registry`; nothing takes `Waiting` while holding the `Registry`. `waiting::drive` goes. A new function, `waiting::ask_after(wait)`, waits `ASK_AFTER` and answers `wait`; the Tauri adapter's timer awaits it and then tells the module the timer elapsed.
- **One stop path.** A window's close, a quit and an unasked exit begin each stop the same way: the write signal is stored in the Registry, then the port stops the server. When the stop ends, in this order: a failure is said on standard error; the write signal is sent; the Registry decides (`stopped`) whether a dialog also shows, and if it does, it shows; the folder is freed; `Waiting` is told. Saying every failure on standard error before the signal means an unasked exit, which ends the process once every signal has come, never ends it before the failure has been said, whenever it begins. A dialog shows after the signal, since it needs the event loop an exit holds, and an unasked exit that begins while it shows may end the process with it; the failure is already on standard error. The Registry decides the dialog after the signal, so an unasked exit begun before then turns it to standard error alone, as a quit does. Today `spawn_stop` signals before the Registry decides and says the failure only after, so an unasked exit can end the process before a failure is said anywhere; this closes that gap.
- **An unasked exit stops through the one path and then waits.** It takes every open Aggregate (`take_all`), as a quit does, and begins each one's stop, which stores its write signal. Only then does it take the write signal of every close not abandoned (`take_writing`, in place of `take_for_exit`), so it waits for the stops it has just begun as well as those already under way. It returns once each has been sent. The threads `RunEvent::Exit` started of its own go.
- **An unasked exit tells `Waiting` nothing.** Once an unasked exit begins, the module marks itself ended: a stop that ends still says a failure, sends its signal and frees its folder, but `Waiting` is told nothing more and the port is given no window work, no timer and no exit, since the process is ending and `RunEvent::Exit` holds the event loop. An unasked exit begun after `Waiting` ended the application does nothing.
- **The module decides whether the application may end.** `exit_requested(code, last_window) -> Exit::{Allow, Prevent}`. `code` is Tauri's: none means the last window closed. `last_window` is what `launch::last_window_closed(Platform::CURRENT)` answers today, the typed `LastWindow::{RunOn, Quit}`, passed in so tests choose the platform. It is allowed once `Waiting` has ended the application. It is prevented, beginning nothing, for the last window closing (the Start window counts, ST-131) where the application runs on with no window (macOS; ST-122, ST-131). A second request while a quit is under way is prevented and begins nothing new: `take_all` finds nothing open, and the quit's wait goes on. Otherwise it is prevented while a quit begins. `main.rs` obeys.
- **Names.** `aggregates::Exit<S>` goes with `take_for_exit`, so `closing::Exit` takes no name already in use. `aggregates::Closing` and `State::Closing` are private to `aggregates.rs`; the `closing` module's public names are `Closings`, `ClosingPort`, `Stop` and `Exit`.
- **Tests drive the module, not the adapter.** `closing/tests.rs` drives the module with the real `Registry` and `Waiting` and the fake, end to end. The fake's timer runs `ask_after` on tokio's paused clock and then calls the module, so the timing ST-122 cites moves here from `waiting/tests.rs`'s `given_the_paused_clock`, which drives `drive`:
  - a window holding no open Aggregate closing at once, and a second close of one closing beginning nothing;
  - a close asking at ten seconds and not before;
  - a close ending in time closing its window and freeing its folder, and never asking, its timer firing after the write ended asking nothing;
  - Keep waiting asking again ten seconds after the answer, and closing the question's own window doing the same;
  - the write ending while asking taking the question away and closing the window;
  - Close without saving closing the window and its views, its failure said on standard error alone;
  - a failure after a window close said on standard error and then in a dialog, before the folder is freed;
  - a quit with nothing open ending at once; a quit asking once, ten seconds after it was asked for, naming every folder; a quit ending once every write has ended; a window close it overtook reporting on standard error alone; a second quit request while one is under way beginning nothing;
  - a close, then a quit, then Close without saving ending the application;
  - the last window closing on macOS beginning nothing, and elsewhere being a quit;
  - an unasked exit waiting for every write, including those of stops it began, but not an abandoned one, saying each failure on standard error before it returns, and giving the port no window work.

  The Tauri adapter (`closing/tauri_shell.rs`) is reached by no test: destroying windows, finding an Aggregate's views (`scheme::is_view_of`, itself tested), building the question (`question::ask`), the stop thread and the timer task. It stays thin, each method one call or a hand-off to its task, and ST-122 keeps saying the adapter is driven by no test.

## Out of scope

The question window's page (`ui/closing.html`), `Waiting`'s internals, `question.rs` beyond the Tauri adapter calling it, and opening a folder.
