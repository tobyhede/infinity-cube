# The Rust PostgreSQL store mirrors the TypeScript lock protocol, and records where its answers differ

Status: accepted
Date: 2026-11-26
Refines: 0174
Related: 0095, 0155, 0162

Rust-host 16 puts PostgreSQL beneath the one Rust SQL repository (Storage ST-3, ST-119) and serves it with `infinity-cube serve --store postgres`. The TypeScript PostgreSQL store (`src/prisma/sql-store.ts`, `src/persistence/sql-space-repository.ts`) is the frozen reference: the Rust store is at least as good as it wherever it is right. The Rust SQL repository serialises every operation behind a process mutex, which is right for SQLite's single writer and is not enough for two hosts on one database. The maintainer settled seventeen questions on 25 November 2026, after a cold audit of the plan and probes against PostgreSQL 16; `.scratch/rust-postgresql-store/spec.md` (Decisions for PostgreSQL) carries each with its evidence. This ADR records them.

## The decision

- **One Rust repository contract for every store.** The Rust ports of `spaceRepositoryContract` are written once, as a table each store runs (`crates/host/tests/repository_contract/`, generated per store by `repository_cases!(harness)` as `http_conformance::cases!` generates the HTTP cases), asserting the contract's absolute answers, never agreement with another Rust store. A store adds only its own cases.
- **The TypeScript PostgreSQL protocol, exactly.** No process serialisation on PostgreSQL. A transaction-scoped advisory lock on the key `(1213812818, 1)`, the TypeScript key, so a TypeScript and a Rust host on one database exclude each other: exclusive for an aggregate commit, `load_aggregate` and both lifecycle doors; shared for the single-Space fast path; none for `list_spaces`, `load_space`, `load_meta_space_id`, `mark_exported` or the asset operations. The fast path and the aggregate decision run in separate transactions, so a holder of the shared lock never asks for the exclusive one. A Space's revision is re-read under its row lock, and a stale one answers a conflict carrying the Space read afresh after the rollback. The Meta row is relocked once more if a replacement moved it, and a second move answers Unreachable. Every row is relocked on replacement. Rows are created by plain `INSERT`, a delete must remove its row, and an update whose upsert finds the Resource owned by another Space is refused as `invalid-commit`. Rust may lock the Meta row with `SELECT … FOR UPDATE` where TypeScript writes it; rollback makes the two indistinguishable. The fast path locks its Space's row with `SELECT … FOR UPDATE` before it reads the Space and its Resources, so a conflict it answers carries one stored state (ST-17), where TypeScript reads the two in separate statements with no row lock. `close()` waits for operations under way through the pool's own close; `serve` waits for it at most five seconds after its first stop signal, then exits zero (ST-120).
- **Isolation levels are set, not inherited.** Every locking transaction begins `BEGIN ISOLATION LEVEL READ COMMITTED`; an unlocked read of more than one statement (`load_space`'s Space and Resources) runs as one `REPEATABLE READ READ ONLY` transaction, so a commit between its statements cannot tear it into a Space that fails intake. TypeScript inherits the server's default and reads `loadSpace` in separate statements.
- **Lock waits stay unbounded**, as in TypeScript: no `lock_timeout` or `statement_timeout`. This is a recorded risk: a stuck holder hangs every writer, and neither driver enables TCP keepalive, so a half-open connection can hang either runtime. Bounding waits is a separate decision for both runtimes.
- **Failure classification.** Unreachable (503): the TypeScript SQLSTATE allowlist exactly (`08000 08001 08003 08004 08006 40001 40P01 53300 55P03 57P01 57P02 57P03`), read wherever the error arises, `COMMIT` included; a socket failure by `io::ErrorKind` (`ConnectionRefused`, `ConnectionReset`, `ConnectionAborted`, `NotConnected`, `BrokenPipe`, `UnexpectedEof`, `TimedOut`, `HostUnreachable`, `NetworkUnreachable`); the pool timing out or closed. Unclassified failure (500): `28P01`, `28000`, `3D000`, every other SQLSTATE but `42P01`, and every other driver error. A lost primary-key race (`23505`) is answered per operation, as TypeScript answers it: initialization re-reads and classifies, replacement propagates.
- **A missing table (`42P01`) is an Invariant failure**, one rule for both Rust stores. TypeScript answers it unclassified; both answer 500 and stop start-up after the confirming retry, and only the name, the log and the problem detail differ.
- **`DATABASE_URL`, read once by `main`.** The process environment wins; when it is unset, the nearest `.env` fills it, read without writing the process environment and taking `DATABASE_URL` alone. The search starts at the current directory, as `sqlx-cli`'s does; TypeScript's starts at its module's directory, which a binary has not. The value is trimmed, an unset or blank one is refused naming `DATABASE_URL` before anything is served. Where the URL is silent, the store takes the other connection settings as `pg` does: `sqlx` fills them from the `PG*` variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` and the rest) and a password from the password file, and `PGSSLMODE`, read once when the store is opened, decides TLS for a URL that names no TLS setting (below).
- **The pool** holds 10 connections with a 2 second acquire timeout, opened lazily and reopened after an outage. The driver retries a refused connection, `53300` and `57P03` itself and surfaces them only when acquisition times out, so an outage answers 503 after up to 2 seconds where TypeScript answers at once. An operation holds one connection at a time.
- **TLS** trusts the operating system's roots (`sqlx`'s `tls-rustls-ring-native-roots`), so an operator trusts a private CA by installing it; Node checks against its own bundled roots, so the trusted sets differ. **`sslmode` means what it means to `pg`**, TypeScript's driver: a URL naming no `sslmode`, `sslrootcert`, `sslcert`, `sslkey` or `ssl` takes `PGSSLMODE` as `pg` 8.22 reads it, connecting without TLS when it is unset, `disable` or a value `pg` does not know, encrypting without checking for `no-verify`, and verifying as `verify-full` does for `prefer`, `require`, `verify-ca` and `verify-full`; `disable` and `verify-full` mean themselves; outside `uselibpqcompat=true`, `no-verify` encrypts without checking the certificate; `prefer`, `require`, `verify-ca` and any other value verify as `verify-full` does; and `sslrootcert`, `sslcert`, `sslkey`, `ssl=true` or `ssl=1` with no `sslmode` asks for TLS, verified as `verify-full`. Under `uselibpqcompat=true` the values take libpq's meanings, except that `prefer` never falls back to plaintext, as `pg` never does: `prefer` and `require` encrypt without checking, `require` with `sslrootcert` checks the CA, `verify-ca` checks the CA and is refused without `sslrootcert`, `verify-full` also checks the host, and `no-verify`, which libpq does not have, is checked as `verify-full` is. The URL is translated before connecting, never passed unchanged, which would weaken TLS.
- **Two values `jsonb` changes are recorded defects, not accepted variations.** Each gives an answer on PostgreSQL that the other stores do not give for the same commit, which ADR 0078 calls defective; the Rust store gives TypeScript's answer, and the fix belongs to intake in both runtimes. A string holding the escape `\u0000`, which intake accepts and `jsonb` refuses with `22P05`, answers its commit as an Unclassified failure, 500, in both runtimes ([`.scratch/postgresql-store-followups/issues/01-a-nul-escape-intake-accepts-and-jsonb-refuses.md`](../../.scratch/postgresql-store-followups/issues/01-a-nul-escape-intake-accepts-and-jsonb-refuses.md)). A committed `-0` loads as `0` on PostgreSQL in both runtimes, where SQLite and memory keep `-0` ([`.scratch/postgresql-store-followups/issues/04-intake-rewrites-negative-zero.md`](../../.scratch/postgresql-store-followups/issues/04-intake-rewrites-negative-zero.md)). `1e400` is not a PostgreSQL difference: intake reads it as infinity in both runtimes before a store sees it, and what a store then does with an infinite number does not depend on PostgreSQL (TypeScript's SQL stores refuse to write it in `toJsonValue`, and the Rust stores write it as `null`, as `JSON.stringify` does).
- **An operation runs to completion when its request is dropped.** Each repository operation runs in a task that owns its connection, so a client that disconnects drops only the wait for the answer, never an operation part-way between its two transactions.
- **The term is Unreachable** (`CONTEXT.md`) for a Repository that cannot answer now, and so 503. TypeScript's sources say "unavailable", which the glossary keeps for a command.

## Accepted differences from TypeScript

Each is an answer the Rust store gives on purpose where the TypeScript one differs, and the ports test names the decision beside the case it exempts: the isolation levels above; a temporary resolver failure (`EAI_AGAIN`), which reaches Rust indistinguishable from a name that does not resolve and so answers unclassified where TypeScript answers 503; a missing table as an Invariant failure; where the `.env` search starts; 503 after the acquire timeout rather than at once during an outage; the operating system's TLS roots; the fast path's row lock before it reads; and, shared with the Rust SQLite store, a commit's answer that does not depend on the order of its changes. The two `jsonb` defects above are not among them.

## Why

Mirroring the protocol is the only choice under which the TypeScript PostgreSQL race cases port as written and a TypeScript and a Rust host can share a database during the move to Rust. The differences are the places where the Rust driver or a binary cannot give TypeScript's answer, or where TypeScript's answer depends on a server setting it never makes.

## Rejected

- **A process mutex**, as SQLite has. It excludes within one process, so two hosts on one database commit over each other.
- **SERIALIZABLE with a retry on `40001`.** A different protocol, under which no TypeScript race case ports as written, and a retry bound is a new decision.
- **Row locks alone.** Nothing orders an aggregate commit, which touches several Spaces and Meta, against the fast path.
- **One exclusive lock around every write.** Map-internal Edits to different Spaces could no longer commit side by side (ST-5).
- **A different advisory key.** Each runtime is safe alone and not together.
- **Passing `sslmode` through unchanged, or refusing all but `verify-full`.** The first weakens TLS against TypeScript's meaning; the second breaks local development, which has no TLS.

## Consequences

`.scratch/rust-postgresql-store/` builds the store and `serve --store postgres`; rust-host 16 keeps `migrate`, the Prisma Next retirement and the CI `db verify` step. The PostgreSQL tests run in CI against a server, in the `rust` and `crap-rust` jobs, and fail rather than skip when the server variable is unset. Four issues out of the store's scope are filed beside the plan: `\u0000`, TypeScript's tearable `loadSpace`, bounding lock waits, and intake rewriting `-0`. The next requirements refresh folds this into Storage.
