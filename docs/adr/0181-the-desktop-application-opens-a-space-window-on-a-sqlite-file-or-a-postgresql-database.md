# The desktop application opens a Space window on a SQLite file or a PostgreSQL database, as well as a folder

Status: accepted
Date: 2026-11-28
Related: 0155, 0162, 0163, 0171, 0174, 0177

The desktop application opens a Space window on an Aggregate directory and nothing else (ADR 0155, ADR 0171, Storage ST-121 and ST-131). The Rust host it embeds (`crates/host`) already holds every Repository InfinityCube has: memory, the SQLite repository and the PostgreSQL repository, all compiled into the shell, and `infinity-cube serve --store sqlite` and `--store postgres` already serve a window's worth of HTTP over each (ST-120). What is missing is a way for a person to choose a Repository in the desktop application, and the rules for a window served from one. A window on a folder Imports it into memory, Exports Edits back once they are quiet, holds the folder's lock (ADR 0162) and waits for its last write on close (ADR 0163, ST-122). Several of those rules mean nothing for a database, and two of them, the origin and the recent history, are keyed by a folder path. This ADR says what each becomes. The maintainer accepted it on 28 November 2026, settling four points in particular: a hosted InfinityCube is out of scope, the shell stores no password, the shell neither creates a SQLite file nor migrates a database, and one database reached by two host names gets two origins.

## The decision

- **A Space window opens on one of three things**: an Aggregate directory (a folder), a SQLite file, or a PostgreSQL database named by a URL. A person is shown "folder", "SQLite file" and "PostgreSQL database", never "Repository", "store" or "backend". Memory is not offered: a memory Repository with no folder behind it loses every Edit when its window closes. **A hosted InfinityCube reached over HTTP is out of scope.** The shell serves only a host it runs itself, through the `infinitycube` scheme; a window on another machine's host would need that host's authentication, a trust boundary other than the scheme handler's, and a different answer for every rule below.
- **Each is offered where a folder is.** The Start window and the File menu offer opening a SQLite file (the platform's file chooser) and connecting to a PostgreSQL database (a form taking a URL, with a separate password field) beside Open Folder…. Where each control sits is UI's to decide, not this ADR's. File › Open… stays the folder chooser. Opening a SQLite file or a database that is already open in a window focuses that window, as a folder does.
- **A database window has no Import, no Export and no directory lock**, as `serve` has none. Every Edit is committed to the Repository before it is answered, so nothing waits to be written. The host serves the Repository as `serve` does: the HTTP application over the SQL repository, establishing the Meta Space from Default Content in the background when the Repository holds no Aggregate (ST-10), and opening the window once it is established, or reporting why not. Two windows, or a window and a `serve` or `pnpm dev`, may share a PostgreSQL database: ADR 0177's lock protocol already makes two hosts on one database safe. A SQLite file is the same, within SQLite's single writer and the repository's busy timeout.
- **The shell migrates nothing.** It opens a SQLite file only when it exists and has been migrated, and a PostgreSQL database only when it has been migrated, as `serve` does (ST-120, ST-126); an unmigrated one is refused in a dialog naming what to run, as a refused folder is reported (ST-117). The shell never creates a SQLite file. A new Space is still written to a folder (ADR 0171); a person who wants one in a database migrates it first.
- **A Space window's origin is keyed by what it opens, and names nothing of it.** A folder keeps its key: the first 128 bits of the SHA-256 of its canonical path (`src/address.rs`), so no folder's `localStorage` moves. A SQLite file's key is the same hash of `sqlite:` followed by the file's canonical path, so a file and a folder at one path get two origins. A PostgreSQL database's key is the same hash of `postgres:` followed by its identity: the user, the host in lower case, the port (5432 when none is named) and the database name, each as the connection resolves it, and nothing else. The password, TLS settings and every other parameter are left out, so changing a password or a TLS setting keeps the origin, and the key, being a hash, carries no part of the identity. One database reached by two host names gets two origins; that is accepted.
- **No secret is stored by the shell.** A recent entry, and the set to reopen at launch (ADR 0171), names a folder or a SQLite file by its canonical path and a PostgreSQL database by its URL with the password removed: the URL's user-info password and any `password` parameter are dropped before it is kept or shown. When a database is opened from a recent entry, or reopened at launch, the password comes from where `pg` finds one without being told (`PGPASSWORD` and the password file, which `sqlx` reads, ADR 0177); with none found, the shell asks for it and keeps it only for that window's life. Reopening at launch never waits on a question: a database that needs a password is skipped there and marked in Recent, as a Space that did not open is. Neither the password nor the URL holding one is written to standard error, a dialog or a page; a refusal names the database by its kept, password-free URL. The URL reaches the shell only from the Start window's form, through a command only that window holds, never from a Space window's page.
- **The shell reads no `DATABASE_URL`.** The person names the database. The CLI reads `DATABASE_URL` because a developer's shell sets it; an application started from the Dock or a launcher has no such environment, and opening a database the person did not name would be a surprise.
- **Closing a database window waits for the changes being answered, and for nothing else.** ST-122's wait for the last write is a wait for Export, which a database window does not have. But a change to a PostgreSQL database waits on a server, and ADR 0177 leaves its lock waits unbounded, so a change can still be under way when its window closes. A close stops serving the window, so no change arrives after it, then waits for every change already being answered; ADR 0163's rule applies to that wait unchanged: after ten seconds the presenter is asked, Keep waiting or Close without saving, and the shell never decides. Close without saving leaves those changes to finish or fail on their own, and says that each may or may not have been committed, since a commit can land after its answer is abandoned. Once no change is under way, the Repository is closed (its connections released) and the window closes. A quit asks one question for every window still waiting, as ST-122 says.

## Why

- **The host already does this.** `serve --store sqlite` and `--store postgres` serve a window's worth of the application over each Repository today, held to the HTTP conformance table. A desktop window over the same Repository is the scheme handler in front of the same application, so the new surface is choosing a Repository and the few rules above, not a new host.
- **Credentials are the one new risk.** A folder path is not a secret; a database URL may hold one. Keeping only a password-free URL, and taking the password from where PostgreSQL's own clients take it, means a recent-history file, the reopen set or a crash report never holds a password, and the origin key leaks nothing even before it is hashed.
- **Origins keep `localStorage` apart without moving anyone's.** Prefixing only the new kinds leaves every folder's origin as it is, so a person's colour scheme and other page settings stay where they were.
- **Migrating is a deliberate act.** ADR 0174 makes `sqlx` the only migrator and `serve` never migrates, because a migration run by whichever program opens a database first is a migration nobody chose. The desktop application holds to the same rule.

## Rejected

- **A hosted InfinityCube over HTTP as a fourth kind.** It would put a remote origin behind the `infinitycube` scheme, or a remote page in a window with no scheme handler in front of it, and needs authentication the hosts do not have. It can be decided later, on its own.
- **Storing the password in the operating system's keychain.** It would let a database reopen at launch without asking, at the cost of a platform keychain dependency on three platforms and a secret the shell then owns. Password files and `PGPASSWORD` already give a person that without the shell holding anything; a keychain can be added later without changing anything here.
- **Keying a database's origin by its whole URL.** It would change the origin, and lose `localStorage`, whenever a password or TLS setting changes, and hashing a URL holding a password is still hashing a secret.
- **Re-keying folders with a `folder:` prefix**, for symmetry. It would move every folder's origin and lose every page's `localStorage` once, for no gain: no canonical path begins `sqlite:` or `postgres:`.
- **Migrating a database, or creating and migrating a SQLite file, from the shell.** Convenient for a person with no command line, but it is a schema change made by whichever program opened the database first, against ADR 0174's single migrator and `serve`'s rule. A New Space form for a SQLite file can be decided later, once `infinity-cube migrate` exists (rust-host 16).
- **Treating a database window's close as instant**, since every commit is durable. A commit waiting on a PostgreSQL lock is not answered yet, and closing under it would leave the presenter not knowing whether their last Edit landed.

## Consequences

- If accepted, the next requirements refresh restates ST-121, ST-122 and ST-131 and Storage's desktop row for a Space window on a SQLite file or a PostgreSQL database, and `CONTEXT.md`'s **Space window** ("a window the desktop application opens on an Aggregate directory") and **Start window** gain the two new kinds.
- The scheme handler serves an application over any of the host's repositories, not only a run's (`src/scheme.rs`'s `AggregateApplication`), and its tests run the HTTP conformance table over the SQLite and the PostgreSQL repositories as they run it over a folder, the PostgreSQL ones ignored by default and run in the `rust` job with the other `postgres*` binaries.
- `InFlight::settled`'s premise that a change waits on nothing outside the process no longer holds for PostgreSQL, so the close's wait for changes being answered gains ADR 0163's ten-second question.
- The recent history and the reopen set, not yet built (ST-131), record which of the three kinds each entry is.
