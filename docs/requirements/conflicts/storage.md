## Closed

### S3. Closed by ruling S3

Ruled 20 November 2026 by the maintainer: option (a), recorded as ADR 0165, which refines 0155. Prisma Next applies its own packages, `sqlx` applies the plain-SQL files, and tests hold them to the same statements and the same schema. ST-125 states it.

For the record, the conflict as it stood:

- **Rules affected.** ST-125.
- **Disagreement.** ADR 0155 says "the migrations are plain SQL files that Prisma (PostgreSQL), the SQLite migrator and `sqlx` all apply". Prisma Next applies a migration package's `ops.json`, and the packages already in `migrations/app/` and `migrations-sqlite/app/` are history that is never rewritten (ADR 0085; `test/unit/current-domain-vocabulary.test.ts`). So the plain-SQL files under `migrations-sql/` are applied by `sqlx` alone, and Prisma Next applies the same statements from its packages.
- **Options.**
  - (a) Keep both: each package and its file are held to the same statements by `test/unit/shared-migrations.test.ts`, and to the same schema by `crates/host/tests/shared_migrations.rs`. Read the ADR as one schema history in two encodings until Rust owns it.
  - (b) Rewrite the existing packages so each executes its `.sql` file through `rawSql`, against the rule that history is not rewritten; a database Prisma Next migrated before would no longer match the packages' hashes.
  - (c) From now on, write each new package's operations as one `rawSql` reading its `.sql` file, leaving the history as in (a).
- **Recommendation.** (a). Either host can serve a database the other migrated, which is what the ADR wants the shared files for, and nothing already migrated breaks.
- **Evidence.** `migrations-sql/README.md`; `test/unit/shared-migrations.test.ts`; `crates/host/tests/shared_migrations.rs`; `.scratch/rust-host/issues/14-shared-plain-sql-migrations.md`.

### S2. Closed by ruling S2

Ruling Storage S2 in `../DECISIONS.md` ("Checkpoint 3 rulings", ruled 12 November 2026), recorded as ADR 0152, which refines 0054 and 0056: option (a), extended to browser-stored copies. The format rolls forward because InfinityCube is unreleased and makes no compatibility promise for any copy outside the repository; an Aggregate directory is recovered from git or read with the build that wrote it, and a browser's stored copy of a mounted Aggregate (not built) may be unreadable after a deploy. ST-36's *Why:* states it; the rule is unchanged.

For the record, the conflict as it stood:

- **Rules affected.** ST-36's *Why:*. The rule itself (no versioned reader, no migration, no compatibility path) is accepted and built, and this conflict does not question it.
- **Disagreement.** 0054 and 0056 justify the rule by "the repository is the only source of state": every database and directory is derived and regenerated by a reset. Three later decisions break that premise without revisiting the rule. Under Running (now `cube run`) an Aggregate directory is the durable copy and may be an author's own, outside this repo (0117). Image bytes outside the repo are excepted (0106, 0118). A mounted Aggregate will keep edits in browser storage (0132, not built). So a format change can leave an author's directory, or a browser's stored copy, unreadable by the next build, with only git to recover it.
- **Options.**
  - (a) Restate the reason as "the product is unreleased and makes no compatibility promise: an author recovers an old directory from git, or reads it with the build that wrote it".
  - (b) Leave the reason as 0056 states it.
- **Recommendation.** (a). It matches the code and 0117's accepted cost ("git answers for history"). (b) states a premise that no longer holds. Adding an upgrade path for directories would change the rule, which is a new decision, not this conflict.
- **Evidence.** `docs/adr/0054`, `0056`, `0117`, `0118`, `0132`; AGENTS.md "State" already names the image exception. `test/unit/import-aggregate.test.ts` › "refuses a version 2 space directory rather than migrating it"; `test/unit/run.test.ts` › "serves the directory it was started on".

### S1. Closed by ruling S1

Ruling S1 in `../DECISIONS.md` ("Checkpoint 2 rulings"): every working read goes through the one initializing loader, wherever it runs. Which reads count as working reads is MG-75.

For the record:
- **What the conflict was.** 0080 said one server-side boundary. The old contract R18 said one boundary per context. The code builds the loader in three places.
- **What the ruling settles.** The number of call sites is not a requirement. Each site must use the one loader. The ruling keeps 0080's one server-side boundary: behind HTTP the browser's loaders read through the single-Space route, which has already initialized the Space, and a mounted page hosts that route itself because ADR 0130 puts the HTTP application in the page. "Wherever it runs" means those hosts, not a second boundary.
- **Evidence.** `http/src/index.ts` (the single-Space route); `persistence/src/session-registry.ts` (`workingTargetSelection`); `app/src/open-spaces.ts` (`compose`); `persistence/src/working-space.ts` `createWorkingSpaceLoader`. Behind HTTP, the browser loaders read through the single-Space route, which has already initialized the Space.
