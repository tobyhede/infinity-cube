**Terms** (definitions are in `CONTEXT.md`; MG terms are in maps-and-graphs.md):
- **Ordinary Space**: every Space but the Meta Space.
- **Door**: any place a Resource enters: intake of a file or stored snapshot, an Edit, or Import.
- **Aggregate intake**: the check that a whole set of Spaces is valid together (references between Spaces, rooting).
- **Target**: the Resource a Reference Resource shows. **Target Space**: the Space a Space Resource references.
- **Selection**: the Map and Graph a Space Resource shows. **Framing**: its saved centre and zoom.
- **Content kind**: a kind that adds content (Markdown, Image). Ur, Reference and Space are kinds but not content kinds.
- **Content action**: what a kind's own content lets an author do (Edit, Replace, choosing a selection).
- **Drawn Map**: a Map drawn inside an Open Space Resource. **Occurrence**: one drawing of a Map, named by the path of drawing Resources from the canvas's own Map to it.
- **Resource N**, **Space N**: a neutral title, numbered one past the highest already used.

**Status:** **built** means code and a named test match the rule. **built (untested)** means code matches and no test covers it. **not built** means the rule is decided and no code implements it. **bug: code differs** means the code does what the note says instead. **undecided (Cn)** means the rule waits on conflict Cn; the note says what the code does meanwhile. A test is named as `file` › "test name". Paths that start with `test/` are at the repo root; all others are under `packages/`.

## Operations index

Each completion first runs the guards in editing.md (ED-19 to ED-21). The Checks column then lists its own checks in the order they run; the first failure answers, and "unchanged" marks where an unchanged answer is given. The coordinated Edits (Create, Link and Delete Space Resource) can also refuse `persistence-recovery-required`, `aggregate-refused` and `persistence-read-failed` (editing.md).

| Create Resource (Markdown, Ur) | one empty Resource at the visible centre | `map-not-found` | SR-36, SR-37 |
| Create Image Resources | one Resource per picture, in a row | no pictures: unchanged → `image-url-unsupported` | SR-39 |

## Spaces and ids

- **SR-1** A Space holds its Resources and its Maps (MG-1). A Resource belongs to exactly one Space. *Why:* a Space is the unit that is authored, stored and owned. **built**: `graph/test/space-aggregate.test.ts` › "refuses duplicate Resource ids across Spaces while allowing Map and Graph id reuse".
- **SR-2** Spaces nest only through Space Resources, to any depth. Maps, Graphs and navigation each belong to one Space and never span a global graph. *Why:* one primitive, the Space, nests. **built**: `app/test/space-resource-embedded-map.test.tsx` › "edits the target through the Open Resource without changing the containing Space", "keeps a second-level Map inert while its containing Map is being edited".
- **SR-3** A Space title is one non-empty, trimmed line. Rename Space trims, refuses a blank title (`space-title-required`), answers the same trimmed title unchanged, and writes nothing but the title. *Why:* a Space title is a label in lists. **bug: code differs**: neither Rename Space nor intake refuses a line break, and intake accepts an untrimmed or whitespace-only title (`z.string().min(1)`): `app/test/space-authoring-operations.test.ts` › "refuses a blank Space title and treats the stored title with padding as unchanged"; `core/test/title.test.ts` › "keeps a Space title exactly as written".
- **SR-4** A Space's title and the Title of a Space Resource referencing it are independent. They agree at creation and nothing propagates between them afterwards. *Why:* neither is the authority for the other. **built**: `app/test/space-resource-authoring.test.tsx` › "leaves the target Space’s title alone when the Resource is renamed".
- **SR-5** Every Space and Resource has exactly one id, a UUID. There is no second, authored or derived id. *Why:* two ids per entity means every reader must know which one a position wants. **built**: `graph/test/new-space.test.ts` › "mints fresh UUID identity for each new space and its first resource".
- **SR-6** Space ids and Resource ids are unique across the whole aggregate. Intake refuses a repeat, within one Space or across Spaces (`duplicate-space-id`, `duplicate-resource-id`). *Why:* the aggregate indexes Resources across independently stored Spaces. **built**: `graph/test/space-aggregate.test.ts` › "refuses duplicate Space ids with every snapshot location", "refuses duplicate Resource ids across Spaces while allowing Map and Graph id reuse"; `graph/test/space.test.ts` › "rejects the same resource id in two files, naming both".
- **SR-7** A title is never an identifier: two Resources, or two Spaces, may share one. *Why:* ids do that job (SR-5). **built**: `app/test/resource-rail-actions.test.tsx` › "continues in the new Reference Resource’s own Title editor, seeded from its Target".

## The Resource envelope and Title Lines

- **SR-8** A Resource is `{ id, title, kind, content }` wherever it is held. The Title is the one field every Resource shares beyond its id and kind; everything else is content its kind owns. There is no shared Description, subtitle, summary or second content slot. *Why:* the common contract is identity, not presentation. **built**: `core/test/resource-envelope.test.ts` › "stores a $kind Resource as { title, kind, content }".
- **SR-9** Only the kind's own schema reads `content`, the same way at every door. Content that does not match its kind is refused, and `content` is required even when the kind's is empty. *Why:* the core never parses a kind's content itself. **built**: `core/test/resource-document-equality.test.ts` › "reads a $kind Resource the same way at every door"; `core/test/resource-envelope.test.ts` › "refuses content that does not match its kind", "requires content, even for an Ur Resource whose content is empty".
- **SR-10** A Space's Resources are ordered by Title, whatever order they were read in. *Why:* array order means nothing authored, so it must not depend on how the files were read. **built**: `graph/test/space.test.ts` › "orders resources by title, whatever order the files arrived in".
- **SR-11** A Title is one or more Title Lines in one string, and an authored line break is significant. The first line is the Resource's name. Line 1 has the role `title`, line 2 `subtitle`, and line 3 and every later line `caption`, with no limit. The lines name and qualify the Resource; they are not content. *Why:* structure in the string keeps every consumer of a name unchanged. **built**: `core/test/title.test.ts` › "gives the second line the subtitle role and the third the caption role", "has no fourth role and no cap: every line after the third is a caption too", "answers only the first line of a Title written on several".
- **SR-12** Every door normalizes a Title the same way: CRLF and lone CR become LF, each line loses trailing whitespace, leading and trailing blank lines go, and interior blank lines and leading whitespace stay. *Why:* a stored Title and an imported one get one answer. **built**: `core/test/title.test.ts` › "folds CRLF and a lone CR to LF", "trims the trailing whitespace of every line and keeps the leading whitespace", "drops leading and trailing blank lines, whitespace-only ones included", "keeps an interior blank line verbatim, because an author who left a gap meant it", "normalizes the Title at every door a Resource arrives through".
- **SR-13** A Title that normalizes to nothing is refused with `resource-title-required`, at intake and by every Edit that writes a Title. Renaming to a Title that normalizes to the stored one is unchanged. *Why:* a Resource always has a name. **built**: `core/test/title.test.ts` › "refuses a Title that normalizes to nothing, under one stable code"; `app/test/space-authoring-operations.test.ts` › "refuses a title that is only whitespace, which the schema would accept", "normalizes a Title as the schema does, and reads one that only gained padding as unchanged".
- **SR-14** Only a Resource's Title has Title Lines. A Space title is SR-3; a Map or Graph title is MG-8. *Why:* those are labels with nothing to draw a ladder on. **built**: `core/test/title.test.ts` › "gives the second line the subtitle role and the third the caption role".

## Kinds

- **SR-15** Five kinds are registered: `markdown`, `image`, `ur`, `reference`, `space`. Each is a module registered once. The domain names no kind and branches on none; a kind declares flags (takes a Shape, can Open, may be a Target, owns referenced Spaces) and the core reads them. *Why:* a new kind is one module, not a change at every layer. **built**: `core/test/kind-registry.test.ts` › "registers every kind module"; `test/unit/kind-ids-in-modules.test.ts` › "names %s nowhere outside a kinds/ module".
- **SR-16** Every Resource names a registered kind; there is no default. Intake refuses a missing kind or one no module registers. A Resource's kind is fixed at creation, and an Edit that changes it is refused (`resource-kind-immutable`). *Why:* a kind nothing registers is one nothing can store, resolve or draw. **built**: `core/test/schema.test.ts` › "requires a kind, defaulting none", "refuses a kind no module registers"; `app/test/image-replacement.test.ts` › "refuses a Resource that is not an Image Resource". The Edit Resource path of `resource-kind-immutable` is untested.
- **SR-17** A kind id is bare for a built-in kind and `vnd.<owner>.<name>` otherwise; each part holds ASCII letters, digits and hyphens and starts with a letter or digit. A kind id is never a media type. *Why:* a later kind never collides with a built-in, and a kind is a behaviour, not a format. **built**: `core/test/kind-registry.test.ts` › "accepts %j", "refuses %j".
- **SR-18** Every capability is a Resource's: every Resource is titled, placed, connected, resized, presented and referenced alike. A kind adds only content actions: Edit for Markdown, Replace for Image, and for a Space Resource choosing its selection and authoring its drawn Map. Ur and Reference add none. Which kinds Open and take a Shape is in MG-28 and MG-30. *Why:* a kind takes nothing away. **built**: `core/test/resource-content.property.test.ts` › "answers each kind’s own authoring and content facts".
- **SR-19** A content kind declares the media types it holds and is created from, and creating a Resource from a dropped or pasted file chooses the kind by the file's media type, `type/*` wildcards included. *Why:* one kind holds many formats. **not built**: kind modules declare no media types (`core/src/kinds/kind-module.ts`); every dropped file goes to the Image kind, and a file the browser declares is not an image is refused.
- **SR-20** A kind's domain half (id, content schema, file codec, content resolution, declared references, flags) is registered wherever intake runs; its view half only in the application. *Why:* domain logic stays out of React. **built**: `test/unit/kind-module-imports.test.ts` › "refuses every name a kind module exports, and no name a kind-neutral module does".

## Markdown, Image and Ur

- **SR-21** A Markdown Resource's content is the literal source its author wrote, and no Edit normalizes it. A new one's source is empty. *Why:* Hyper authors Markdown source, not a document model. **built**: `graph/test/resource-file.test.ts` › "keeps the sidecar verbatim: no fence is read, and no newline is added or removed"; `graph/test/new-space.test.ts` › "begins neutral Resource numbering at Resource 1 with an empty body (ADR 0018, ADR 0020)".
- **SR-22** Replace image is one Edit that writes an Image Resource's URL (and its natural size, SR-26) and keeps its id, Title, placement, size, Shape and Edges. The new URL is entered, or is that of a picture just stored, one file at a time. Replacing with the URL the Resource already holds (after trimming) is unchanged and makes no Edit, including when an upload stores a picture already held. *Why:* replacing a picture keeps everything authored around it. **built**: `app/test/image-replacement.test.ts` › "changes the URL and the recorded natural size in one Edit, and nothing else", "answers unchanged for the URL the Resource already holds, trimmed, without loading it", "makes no Edit or commit when an upload stores the picture already held", "refuses multiple files before storing, measuring or editing".
- **SR-23** An Image Resource's content is a URL (and a natural size, SR-26). It owns the URL, not the picture's bytes, and stores nothing about where the URL points. *Why:* a picture already at a URL needs no copy. **built**: `core/test/schema.test.ts` › "gives an Image Resource no body — it owns its URL, not its bytes".
- **SR-24** An image URL is `https:`, `http:`, or `/images/<id>` where `<id>` has the form of a stored-image id (intake checks the form, not that the store holds it). Any other URL, `data:` included, is refused with `image-url-unsupported`, at intake and by creation and Replace. *Why:* `data:` puts the bytes back in the document, and other relative forms resolve against whatever page drew them. **built**: `core/test/schema.test.ts` › "parses an image URL it accepts: %s", "refuses an image URL it does not accept, naming the rule: %j"; `app/test/image-replacement.test.ts` › "refuses a URL an Image Resource may not hold rather than throwing on intake".
- **SR-25** An Image Resource's Title is the picture's text alternative; there is no alt field. *Why:* a kind gets fields only where it needs them. **built**: `ui/test/PresentedResource.test.tsx` › "presents an Image Resource as its name and its image, the name as the text alternative".
- **SR-26** The picture is measured when its URL is set, by creation and by Replace, and its natural size recorded, or none when it did not load. **undecided (C1)**: the code records it (`app/src/image-creation.ts`, `app/src/image-replacement.ts`) and nothing reads it: `app/test/image-replacement.test.ts` › "records no natural size when the new picture does not load".
- **SR-27** A picture that will not load is not a refusal: the Space stays valid, the Resource still Opens, and its image can still be replaced. *Why:* an external URL can change or vanish at any time. **built**: `ui/test/ResourceImage.test.tsx` › "replaces the skeleton with the failed-image state when the picture does not load".
- **SR-28** An Ur Resource's content is empty. It has no content action, so no Edit, and it may be a Target. Its Map-entry rules (never Open, takes a Shape) are MG-28 and MG-30. *Why:* the simplest Resource, for diagramming without documents. **built**: `core/test/schema.test.ts` › "is an id, a Title, its kind and empty content, in a file and as a Resource"; `app/test/canvas-resource-authoring.test.tsx` › "offers an Ur Resource no Open, Close or content edit, and Opens nothing for it".

## Reference Resources

- **SR-29** A Reference Resource's content is a pointer to its Target, another Resource of the same Space. It has no content of its own. Content resolves on read, one hop, and is never copied or flattened at intake. To show content a second time in one Map, an author makes a Reference (MG-5). *Why:* exactly one Resource owns the content, so nothing can drift. **built**: `core/test/kind-registry.test.ts` › "is the Target when its kind names one", "never asks the Reference kind to resolve content, which it has none of"; `graph/test/space-intake.test.ts` › "accepts a single-hop reference to a markdown resource".
- **SR-30** Every kind except Reference may be a Target. A Target that is missing (`reference-target-missing`), is the Reference itself (`reference-targets-self`) or is another Reference (`reference-target-not-targetable`) is refused at intake and at creation. So chains and cycles cannot exist, and there is no cycle check. *Why:* single hop keeps the source unambiguous. **built**: `graph/test/space-intake.test.ts` › "refuses a reference resource whose target resolves to no resource", "refuses a reference resource that points at itself", "refuses a reference resource whose target is itself a reference resource", "accepts a reference resource whose target is an Ur Resource (ADR 0113)", "accepts a reference resource whose target is a Space Resource"; `app/test/space-authoring-operations.test.ts` › "refuses a Target that is itself a Reference Resource, so no chain is ever authored".
- **SR-31** The Target is chosen once, at creation, and never changes. An Edit naming another Target is refused (`reference-target-immutable`); a wrong Target means delete and create. *Why:* retargeting would make an established Resource and its Edges mean different content. **built**: `app/test/space-authoring.property.test.ts` › "keeps an existing Reference Resource Target immutable while accepting Title edits".
- **SR-32** Apart from its Target, a Reference Resource is an ordinary Resource: its own Title, membership, placement, Edges, Open state and size are authored on it. Its Title is never its Target's, and renaming one never renames the other. *Why:* the occurrence and its content are different things. **built**: `app/test/resource-authoring.test.tsx` › "renames a Reference Resource through the shared Title interaction and preserves Target content".
- **SR-33** Open, a Reference Resource shows its Target's content read-only and offers no content action. To author that content the author opens the Target, and every Reference to it then shows the change. *Why:* one source of truth, one authoring subject. **built**: `app/test/resource-authoring.test.tsx` › "opens each Reference Resource on resolved Target content without a source editor", "updates shared content only when its Target is opened explicitly"; `core/test/resource-content.property.test.ts` › "offers authoring only for own content of a kind that authors it".
- **SR-34** What a Reference Resource's content asks of the canvas, whether it embeds a Map and whether it draws a content area, is its Target's. A Reference to a Space Resource draws that Space Resource's selection (SR-46), read-only (SR-51). *Why:* a Reference shows what its Target shows. **built**: `core/test/resource-content.property.test.ts` › "answers Map embedding and content area regardless of via".
- **SR-35** Jump to Target navigates to the Target at its own product address and never authors it through the Reference. *Why:* content is authored on the Target. **not built**: `app/src/entity-actions.tsx` offers Copy link to Target only; tracked in `.scratch/alias-cards/issues/05-jump-to-alias-target.md` (repo root).

## Creating Resources

- **SR-36** Every creation completes its Edit on one activation, with no pane, picker or Cancel. What a kind needs beyond a Title comes from where the gesture was made. Markdown and Ur Resources are created empty from a press, at the visible centre, stepping off an occupied point (MG-18). *Why:* a form collects nothing the gesture does not already know. **built**: `app/test/resource-authoring.test.tsx` › "creates an Ur Resource in one press and continues in its Title"; `app/test/space-authoring-operations.test.ts` › "creates one neutrally titled detached Resource at the anchor it was given", "creates one neutrally titled Ur Resource at the anchor, in one Edit".
- **SR-37** A new Resource is titled `Resource N`, one past the highest `Resource N` among Resource names (first lines), unless SR-38, SR-41 or SR-43 says otherwise. *Why:* a neutral name the author renames in place. **built**: `app/test/titles.test.ts` › "takes one past the highest number already in use", "reads a Resource’s name, so a Title with more lines still occupies its number", "does not let a line below the name claim a number".
- **SR-38** A Reference Resource is created from its Target, by a gesture on the Target. It copies the Target's Title once, and the two are independent afterwards; an empty Title mints `Resource N`. It is aimed at a fixed offset past the Target's bottom-right corner, or at the visible centre when the Map does not place the Target, stepping off an occupied point (MG-18). *Why:* the copied Title is how the author sees what it points at. **built**: `app/test/resource-rail-actions.test.tsx` › "creates a Reference Resource of the Resource whose menu ran the command", "continues in the new Reference Resource’s own Title editor, seeded from its Target", "places the Reference Resource at a fixed offset from the Resource it was made from"; `app/test/space-authoring-operations.test.ts` › "creates and places a Reference Resource on its Target, minting a neutral title when none was typed".
- **SR-39** Image Resources are created from chosen files, dropped files or a pasted URL. Each file is stored first (measuring: SR-26). One Edit then creates one Resource per picture, titled `Resource N` in order, never after the file or URL, in a row from the anchor (exact for a drop or paste; a press steps off). If any file is refused, nothing is created and the notice names each refused file. The Resources land on the Map the gesture was made on, and on nothing if it is gone. *Why:* several pictures are one gesture. **built**: `app/test/image-creation.test.ts` › "stores each file, measures it, and creates one Resource per file in one Edit", "creates nothing when any file is refused, and names the file and the code", "lands on the Map the gesture was made on, and leaves the canvas where the author went", "creates nothing when the Map the gesture was made on is gone"; `app/test/space-authoring-operations.test.ts` › "creates several in one Edit, numbered in order, in a row from the anchor".
- **SR-40** A new Space is created complete, in one Edit: one empty Markdown Resource titled `Resource 1`, Closed at (0, 0), in a Map titled `Map 1` that owns one empty Graph titled `Graph 1`, which is its Active Graph, and that Map is the Space's `defaultMap`. Every path that creates a Space makes this shape. The first Resource is never named after the Space. *Why:* an empty canvas offers no way in and reads as a failure. **built**: `graph/test/new-space.test.ts` › "starts complete with its first Resource at the canonical centred position", "begins neutral Resource numbering at Resource 1 with an empty body (ADR 0018, ADR 0020)", "creates the same complete one-Resource shape as newSpace from one identity source".
- **SR-41** Create Space Resource is one coordinated Edit that creates a new Space (SR-40) and a Space Resource selecting the Map and Graph that Space opens on. Both are titled one `Space N`, numbered over the containing Space's Resource names. *Why:* one title seeds both, so they agree by construction. **built**: `app/test/space-resource-authoring.test.tsx` › "creates a Space Resource and the new Space it names from one Space N", "numbers each new Space from the Space Resources already on the Map"; `persistence/test/space-resource-lifecycle.test.ts` › "atomically creates the first Space Resource and its normal target Space".
- **SR-42** A created Space Resource is drawn when its local Edit installs, without awaiting the durable commit. A refusal comes before anything is placed, so a refused creation leaves nothing, and its notice names the Space that was not created. *Why:* a Resource that appears a round trip late is indistinguishable from a press that did nothing. **built**: `app/test/space-resource-authoring.test.tsx` › "continues in the created Resource’s own Title editor", "creates nothing and names the Space when the lifecycle refuses". That placement does not await the commit is untested.
- **SR-43** Linking references an existing Space; it is a separate gesture from creating one. The Space Resource takes the Space's title and selects what the target opens on: its `defaultMap` and that Map's Active Graph. The containing Space is never offered as a target. *Why:* a Space Resource always selects something real. **built**: `app/test/space-resource-authoring.test.tsx` › "references an existing Space instead of creating a second one", "takes an initialized target’s opening selection and initializes nothing"; `persistence/test/space-resource-lifecycle.test.ts` › "selects the Map's authored Active Graph rather than the head of its list"; `app/test/space-resource-lifecycle.test.ts` › "offers every stored Space but the one the Resource would live in".
- **SR-61** A link first runs the containing Space's own checks; a link they refuse initializes nothing and mints no id. Only then is a mapless target durably initialized (MG-74), in its own commit, and that initialization stands even if the link is later refused. A target that cannot be read, initialized or found refuses the link (`space-resource-target-unavailable`). *Why:* an Edit already refused must leave no trace, and an initialized Space is valid on its own. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "refuses %s when its containing Map is absent", "durably initializes a stored mapless target before the Resource that selects it exists", "keeps a target it initialized when the Edit that asked for it is refused"; `app/test/space-resource-authoring.test.tsx` › "creates nothing and says so when its target could not be prepared".

## Space Resources

- **SR-44** A Space Resource's content names a target Space, a Map of it, a Graph that Map owns, and optionally a framing. Map and Graph are required, and nothing falls back to the target's `defaultMap`. Aggregate intake refuses a missing target (`space-reference-missing`), Map (`space-resource-map-missing`) or Graph (`space-resource-graph-missing`), and a Graph another Map owns (`space-resource-graph-outside-map`); each means a dangling reference. *Why:* one Space Resource's view must not follow another Space's opening choice. **built**: `graph/test/space-aggregate.test.ts` › "accepts a Space Resource naming a Map of its target and a Graph that Map owns", "locates a Space Resource whose target is absent", "locates an explicit Map that the target does not supply", "locates an explicit Graph that the target does not hold", "refuses a Graph outside the explicit Map".
- **SR-45** The target Space is chosen at creation and never changes; an Edit naming another is refused (`space-resource-target-immutable`). Many Space Resources, in many Spaces, may reference one Space. A reference cycle, a Space Resource targeting its own Space included, is refused (`space-reference-cycle`). *Why:* identity stays stable, and Open Space Resources cannot draw one another without end. **built**: `app/test/space-resource-selection.test.tsx` › "offers no way to change the Space it references"; `graph/test/space-aggregate.test.ts` › "lets two Space Resources converge on one target while each selects its own Map", "refuses a multi-Space reference cycle at the closing Resource"; `graph/test/space-intake.test.ts` › "refuses a Space Resource that targets the Space containing it". The `space-resource-target-immutable` refusal is untested.
- **SR-46** The selection is the Space Resource's. Choosing a Map or Graph on it is an Edit of that Space Resource alone: the target's `defaultMap` and every Map's `activeGraph` stay. Every placement of one Space Resource shows its one stored selection; another view needs another Space Resource. *Why:* independently configured views must not change one another. **built**: `app/test/space-resource-selection.test.tsx` › "writes a Graph chosen from the Map already selected"; `app/test/space-resource-authoring.test.tsx` › "keeps a selection per Space Resource, and stores both".
- **SR-47** Choosing a Map selects that Map's Active Graph and drops the framing. Choosing a Graph of the same Map keeps the framing. *Why:* a framing belongs to one Map. **built**: `app/test/space-resource-selection.test.tsx` › "writes the chosen Map and re-seeds the Graph from it", "seeds the Graph from the chosen Map’s Active Graph"; `core/test/space-kind.test.ts` › "drops the framing when the Map changes, since it was the old Map's", "keeps the framing when only the Graph changes, since it frames the same Map".
- **SR-48** Framing, a centre and zoom in Map coordinates, belongs to the Space Resource, never to the Map. Framing is an Edit of the Space Resource and moves no Resource of the target. *Why:* two Space Resources may frame one Map differently. **built**: `app/test/space-resource-embedded-map.test.tsx` › "authors framing on each Space Resource wheeled within the debounce window".
- **SR-49** Open, a Space Resource draws its selected Map and Graph. Editing inside that drawn Map authors the target Space (what it writes to `defaultMap` and `activeGraph`: MG-80); moving, resizing, Opening or Closing the Space Resource authors the Map that contains it. *Why:* each Edit belongs to the Space whose data it changes. **built**: `app/test/space-resource-embedded-map.test.tsx` › "draws the Map the Resource selects, not the target own default", "edits the target through the Open Resource without changing the containing Space".

## Drawn Maps

- **SR-50** A drawn Map is its target Space's Map: it offers every command, gesture, refusal and notice the canvas Map offers, through that Space's own authoring. Any difference not listed here is a defect:
  - only the canvas's own Space presents (navigation.md);
  - one camera (rendering.md);
  - Edit is not offered below the first level (SR-52);
  - an Edge joins Resources of one Space (MG-59);
  - a drop on an inert or read-only drawn Map is refused (SR-53).

  *Why:* a Map behaves the same wherever it is drawn. **built**: `app/test/space-resource-embedded-map.test.tsx` › "offers the full entity menu while editing a drawn Map and creates its Reference in that Space", "chooses a Shape inside a drawn Map, writing that Space’s Map and drawing it there".
- **SR-51** Each drawn Map has one policy, from most to least permissive: authoring, inert, read-only. It is read-only when it is shown through a Reference Resource, when its Space is stale, or when its Space is kept after a failed commit; read-only then passes to every Map inside it. Otherwise the Space Resource drawing it decides: Edit gives authoring, Read gives inert. Below the first level a Map is inert at most. *Why:* permission is decided once, in one place. **built**: `app/test/map-surface-policy.test.ts` › "is $policy from $inherited at depth $depth (reference $throughReference, stale $stale, editing $editing)", "passes read-only to every Map inside, and is inert at most below the first level".
- **SR-52** Edit is offered only on a Space Resource drawn in the canvas's own Map. An authoring drawn Map still moves, Opens and Closes the Space Resources in it, but what they draw is inert. *Why:* Edit must not nest without limit. **built**: `app/test/map-surface-policy.test.ts` › "offers Edit and presenting only on the canvas’s own authoring Map"; `app/test/space-resource-embedded-map.test.tsx` › "moves, closes and reopens a Space Resource inside an authoring drawn Map".
- **SR-53** A drop or paste aimed at a drawn Map that is read-only, inert, or not taking a new Resource now is refused (`drawn-map-read-only`, `drawn-map-not-in-edit`, `drawn-map-nested`, `drawn-map-unavailable`) and never falls through to the Map beneath. *Why:* a gesture lands where it was aimed or nowhere. **built**: `app/test/map-surface-policy.test.ts` › "on a $policy Map at depth $depth is refused as $code".
- **SR-54** One Space or Map may be drawn several times, and each drawing is its own occurrence. A Space Resource whose selected Map is already drawn above it, the canvas's own Map included, draws nothing inside. *Why:* recursion through Space Resources must end. **built**: `app/test/space-resource-embedded-map.test.tsx` › "allows only one content editor across two embeddings of the same target", "stops embedding a Space Resource whose Map is already on the containing path".
- **SR-60** A keyboard command or a Resource's toolbar acts on the Space of the selected occurrence, or on the canvas's own Space when nothing is selected. A pointer gesture (drop, empty modifier drop, paste at the pointer) lands in the Map under the point. The Command Dock always acts on the canvas's own Space. *Why:* a command acts where the author is working. **built**: `app/test/space-resource-embedded-map.test.tsx` › "creates by keyboard in the selected drawing and continues naming there", "begins title editing with F2 in the drawing whose Resource is selected"; `app/test/map-surface.test.ts` › "keeps one selection and continuation across two drawings of the same Map". That the Dock acts on the canvas's own Space is untested.

How long a drawn Space stays composed (its holds) is NV-81.

## Space lifetime, the Meta Space and deletion

- **SR-55** There is one permanent Meta Space. No Space Resource creates it and no deletion reaches it, and it is the only Space that needs no reference. Every ordinary Space is created by creating its first Space Resource. *Why:* every Space operation is then a Resource operation. **built**: `persistence/test/space-resource-planning.test.ts` › "never cascades to the Meta Space"; `test/support/repository-contract.ts` › "`<repository>` refuses an authored commit that deletes the Meta Space"; `persistence/test/space-resource-lifecycle.test.ts` › "atomically creates the first Space Resource and its normal target Space".
- **SR-56** Every ordinary Space must be reached from the Meta Space. Aggregate intake refuses an ordinary Space no Space Resource references (`ordinary-space-unreferenced`) and an aggregate without its Meta Space (`meta-space-missing`). How a commit treats a Space the stored aggregate already left unreferenced, which lets the Edit that initializes it commit, is ST-104. *Why:* an unreferenced Space is an unreachable one. **built**: `graph/test/space-aggregate.test.ts` › "refuses every ordinary Space with no inbound Space Resource", "refuses an aggregate without its configured Meta Space".
- **SR-57** The Space Resources referencing a Space own its lifetime together. It survives while any remains. Deleting the last deletes it in the same Edit, and so on down: every Space left with no Space Resource is deleted in that Edit. The count of references is the whole rule; there is no reachability sweep. There is no Delete Space command. *Why:* one set of operations over Resources, not a second over Spaces. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "links an existing Space and deletes its target only after the last reference is removed"; `persistence/test/space-resource-planning.test.ts` › "cascades to every Space the removal leaves unreferenced and opens the stored ones"; `graph/test/declared-references.property.test.ts` › "releases exactly the Spaces the removed references leave unreachable from the Meta Space". The absence of a Delete Space command is untested.
- **SR-58** Delete from Space removes a Resource from its Space and from every Map (MG-20). It is refused for a Resource the Space lacks (`resource-not-found`) and for one a Reference Resource in the Space still targets (`resource-has-references`, naming each by name). Deleting a Reference leaves its Target untouched. *Why:* a Space must not lose a Target from under its References. **built**: `graph/test/snapshot-edits.property.test.ts` › "always refuses to delete a Resource a Reference Resource in the Space still targets"; `app/test/space-authoring-operations.test.ts` › "refuses a Resource its Reference Resources still point at, naming them", "deletes a Reference Resource and leaves its Target untouched".
- **SR-59** A Space Resource is deleted only through the Space Resource lifecycle, as one coordinated Edit (SR-57); a one-Space Edit refuses it (`space-resource-deletion-unsupported`). The lifecycle refuses a Resource that is not a Space Resource (`space-resource-not-found`), and one a Reference still targets (`resource-has-references`). *Why:* only the lifecycle can count references across Spaces. **built**: `app/test/space-authoring-operations.test.ts` › "refuses deleting a Space Resource rather than orphaning the Space it owns"; `app/test/resource-deletion.test.ts` › "deletes a Space Resource through Space Resource authoring, in the containing Space"; `persistence/test/session-registry.test.ts` › "refuses to delete a Space Resource a Reference Resource targets, and commits nothing"; `persistence/test/space-resource-planning.test.ts` › "refuses a Resource that is not a Space Resource".
