**Terms** (definitions are in `CONTEXT.md`; MG terms are in maps-and-graphs.md):
- **Ordinary Space**: every Space but the Meta Space.
- **Door**: any place a Resource enters: intake of a file or stored snapshot, an Edit, or Import.
- **Aggregate intake**: the check that a whole set of Spaces is valid together (references between Spaces, rooting).
- **Target**: the Resource a Reference Resource shows. **Target Space**: the Space a Space Resource references.
- **Selection**: the Map and Graph a Space Resource shows. **Framing**: its saved centre and zoom.
- **Plugin** (Resource plugin): what draws and authors a kind's Resources inside their rect. A **kind** is the name in a Resource's `kind` that selects its plugin. The build's **plugin list** names every plugin once, and separately the **default plugin**.
- **Missing kind**: a well-formed kind that no plugin in this build's list draws. Its Resources are drawn by the default plugin.
- **Map content**: what a plugin keeps for its Resource on one Map, beside the canvas's position and size (MG-86).
- **Content kind**: a kind whose content names bytes (Markdown, Image). Ur, Reference and Space are kinds but not content kinds.
- **Content action**: what a plugin lets an author do with its content or Map content (Edit, Replace, Open and Close, a Shape, choosing a selection).
- **Drawn Map**: a Map drawn inside an Open Space Resource. **Occurrence**: one drawing of a Map, named by the path of drawing Resources from the canvas's own Map to it.
- **Resource N**, **Space N**: a neutral title, numbered one past the highest already used.

**Status:** **built** means code and a named test match the rule. **built (untested)** means code matches and no test covers it. **not built** means the rule is decided and no code implements it. **bug: code differs** means the code does what the note says instead. **undecided (Cn)** means the rule waits on conflict Cn; the note says what the code does meanwhile. A test is named as `file` › "test name". Paths that start with `test/` are at the repo root; all others are under `packages/`.

## Operations index

Each completion first runs the guards in editing.md (ED-19 to ED-21). The Checks column then lists its own checks in the order they run; the first failure answers, and "unchanged" marks where an unchanged answer is given. The coordinated Edits (Create, Link and Delete Space Resource) can also refuse `persistence-recovery-required`, `aggregate-refused` and `persistence-read-failed` (editing.md).

## Spaces and ids

- **SR-1** A Space holds its Resources and its Maps (MG-1). A Resource belongs to exactly one Space. *Why:* a Space is the unit that is authored, stored and owned. **built**: `graph/test/space-aggregate.test.ts` › "refuses duplicate Resource ids across Spaces while allowing Map and Graph id reuse".
- **SR-2** Spaces nest only through Space Resources, to any depth. Maps, Graphs and navigation each belong to one Space and never span a global graph. *Why:* one primitive, the Space, nests. **built**: `app/test/space-resource-embedded-map.test.tsx` › "edits the target through the Open Resource without changing the containing Space", "keeps a second-level Map inert while its containing Map is being edited".
- **SR-3** A Space title is one non-empty, trimmed line. Rename Space trims, refuses a blank title (`space-title-required`), answers the same trimmed title unchanged, and writes nothing but the title. *Why:* a Space title is a label in lists. **bug: code differs**: neither Rename Space nor intake refuses a line break, and intake accepts an untrimmed or whitespace-only title (`z.string().min(1)`): `app/test/space-authoring-operations.test.ts` › "refuses a blank Space title and treats the stored title with padding as unchanged"; `core/test/title.test.ts` › "keeps a Space title exactly as written".
- **SR-4** A Space's title and the Title of a Space Resource referencing it are independent. They agree at creation and nothing propagates between them afterwards. *Why:* neither is the authority for the other. **built**: `app/test/space-resource-authoring.test.tsx` › "leaves the target Space’s title alone when the Resource is renamed".
- **SR-5** Every Space and Resource has exactly one id, a UUID. There is no second, authored or derived id. *Why:* two ids per entity means every reader must know which one a position wants. **built**: `graph/test/new-space.test.ts` › "mints fresh UUID identity for each new space and its first resource".
- **SR-6** Space ids and Resource ids are unique across the whole aggregate. Intake refuses a repeat, within one Space or across Spaces (`duplicate-space-id`, `duplicate-resource-id`). *Why:* the aggregate indexes Resources across independently stored Spaces. **built**: `graph/test/space-aggregate.test.ts` › "refuses duplicate Space ids with every snapshot location", "refuses duplicate Resource ids across Spaces while allowing Map and Graph id reuse"; `graph/test/space.test.ts` › "rejects the same resource id in two files, naming both".
- **SR-7** A title is never an identifier: two Resources, or two Spaces, may share one. *Why:* ids do that job (SR-5). **built**: `app/test/resource-rail-actions.test.tsx` › "continues in the new Reference Resource’s own Title editor, seeded from its Target".

## The Resource envelope and Title Lines

- **SR-8** A Resource is `{ id, title, kind, content }` wherever it is held: the same value in a Resource file, in a store, on the wire and given to a plugin, so no plugin translates a Resource between forms. The Title is the one field every Resource shares beyond its id and kind; everything else is content its plugin owns. There is no shared Description, subtitle, summary or second content slot. *Why:* the common contract is identity, not presentation. **built**: `core/test/resource-envelope.test.ts` › "stores a $kind Resource as { title, kind, content }"; `test/unit/markdown-resource-value.property.test.ts` › "is the same value in its file, in the store and on the wire, and so is its text".
- **SR-9** Only the listed plugin's own schema reads `content`, the same way at every door. Content that does not match its plugin's schema is refused, and `content` is required even when the plugin's is empty. To the host, `content` is a JSON value it never parses; a missing kind's is any JSON object, carried unread (SR-62). *Why:* the core never parses a kind's content itself. **built**: `core/test/resource-document-equality.test.ts` › "reads a $kind Resource the same way at every door"; `core/test/resource-envelope.test.ts` › "refuses content that does not match its kind", "requires content, even for an Ur Resource whose content is empty"; `core/test/schema.test.ts` › "refuses content a present plugin rejects, though a missing plugin would read it".
- **SR-10** A Space's Resources are ordered by Title, whatever order they were read in. *Why:* array order means nothing authored, so it must not depend on how the files were read. **built**: `graph/test/space.test.ts` › "orders resources by title, whatever order the files arrived in".
- **SR-11** A Title is one or more Title Lines in one string, and an authored line break is significant. The first line is the Resource's name. Line 1 has the role `title`, line 2 `subtitle`, and line 3 and every later line `caption`, with no limit. The lines name and qualify the Resource; they are not content. *Why:* structure in the string keeps every consumer of a name unchanged. **built**: `core/test/title.test.ts` › "gives the second line the subtitle role and the third the caption role", "has no fourth role and no cap: every line after the third is a caption too", "answers only the first line of a Title written on several".
- **SR-12** Every door normalizes a Title the same way: CRLF and lone CR become LF, each line loses trailing whitespace, leading and trailing blank lines go, and interior blank lines and leading whitespace stay. *Why:* a stored Title and an imported one get one answer. **built**: `core/test/title.test.ts` › "folds CRLF and a lone CR to LF", "trims the trailing whitespace of every line and keeps the leading whitespace", "drops leading and trailing blank lines, whitespace-only ones included", "keeps an interior blank line verbatim, because an author who left a gap meant it", "normalizes the Title at every door a Resource arrives through".
- **SR-13** A Title that normalizes to nothing is refused with `resource-title-required`, at intake and by every Edit that writes a Title. Renaming to a Title that normalizes to the stored one is unchanged. *Why:* a Resource always has a name. **built**: `core/test/title.test.ts` › "refuses a Title that normalizes to nothing, under one stable code"; `app/test/space-authoring-operations.test.ts` › "refuses a title that is only whitespace, which the schema would accept", "normalizes a Title as the schema does, and reads one that only gained padding as unchanged".
- **SR-14** Only a Resource's Title has Title Lines. A Space title is SR-3; a Map or Graph title is MG-8. *Why:* those are labels with nothing to draw a ladder on. **built**: `core/test/title.test.ts` › "gives the second line the subtitle role and the third the caption role".

## Kinds

- **SR-15** A kind is its Resource plugin. One build list names five plugins, once each, in the order every choice among kinds is offered in (`markdown`, `space`, `image`, `ur`, `reference`), and separately the default plugin (SR-62). Nothing else imports a plugin, and no other list of kinds exists. The core reads what each listed plugin declares (its content and Map content schemas, whether it may be a Target, the references it holds and whether it owns their Spaces, its outline, how it is created) and names or branches on no kind. *Why:* a new kind is one plugin and one line in the list, not a change at every layer. **built**: `core/test/plugin-kind.test.ts` › "lists every plugin this build draws"; `core/test/plugin-modules.test.ts` › "reads the %s plugin"; `test/unit/plugin-list-imports.test.ts` › "is in no tracked source outside the plugin packages and the list".
- **SR-16** Every Resource names a kind; there is no default. Intake refuses an absent kind or a malformed one. A well-formed kind no listed plugin draws is a missing kind, carried rather than refused (SR-62). A Resource's kind is fixed at creation, and an Edit that changes it is refused (`resource-kind-immutable`). *Why:* a missing `kind` must never quietly mean one. **built**: `core/test/schema.test.ts` › "requires a kind, defaulting none", "refuses a kind that is not a kind id", "reads a kind no plugin draws whole, its content unread (ADR 0142)". The `resource-kind-immutable` refusal is untested.
- **SR-17** A kind id is bare for a built-in kind and `vnd.<owner>.<name>` otherwise; each part holds ASCII letters, digits and hyphens and starts with a letter or digit. A kind id is never a media type. The plugin list refuses a kind listed twice or one that is not a kind id. *Why:* a later kind never collides with a built-in, and a kind is a behaviour, not a format. **built**: `core/test/plugin-modules.test.ts` › "accepts %j", "refuses %j"; `resource-api/test/domain.test.ts` › "refuses a kind listed twice or one that is not a kind id".
- **SR-18** Every Resource is titled, placed, connected, resized, presented, referenced and deleted alike, by the host: the canvas owns the rect, its position and size, which Resource is selected, and the Edges between rects. A plugin owns everything drawn inside its outline and every way its content and Map content are authored: Edit and Open and Close for Markdown, Replace for Image, a Shape for Ur, Open and Close for Reference, and for a Space Resource Open and Close, Edit of its drawn Map and choosing its selection. A plugin never writes a position, a size or an Edge. What each plugin keeps on a Map, and the Edit that writes it, are MG-86–MG-88; what the host draws and what the plugin draws is RD-82. *Why:* a kind takes nothing away, and no kind's differences accumulate in a shared frame. **built**: `core/test/resource-content.property.test.ts` › "answers each kind’s own authoring and content facts"; `plugin-ur/test/ur-plugin.test.tsx` › "offers its Shape on the rail where the Map content commit is present, and commits the choice". That a plugin cannot write a position, size or Edge holds because the Resource API offers no such commit; no test names it.
- **SR-19** A plugin declares where it is created from (the Command Dock, arriving data, another Resource, a Space) and the media types of the data it accepts, `type/*` wildcards included. Creating from a dropped or pasted file or URL chooses among the plugins that accept it: one naming the media type exactly beats one taking it by a wildcard, then list order decides. *Why:* one kind holds many formats, and a second plugin for a format must be able to take it. **built**: `app/test/creation-host.test.ts` › "prefers a plugin naming the media type exactly over one taking it by a wildcard", "takes `type/*` as a wildcard for that type alone", "lets build order decide between two equal matches", "passes over a plugin that does not accept the data", "matches a pasted URL as a URI list".
- **SR-20** A plugin has a domain half (its kind, content and Map content schemas, declared references, Target and creation facts) that names no view and imports no React, loaded wherever intake runs, the server and CLI included, and a view half loaded only in the application. Both reach only the Resource API. *Why:* domain logic stays out of React, and one public door keeps every plugin equal. **built**: `test/unit/resource-plugin-import-restrictions.test.ts` › "keeps %s out of a plugin’s domain half", "permits %s in a plugin’s view half".
- **SR-62** A Resource whose kind no plugin in this build draws (a missing kind) is still a Resource. Intake carries it whole, its `content` any JSON object that nothing reads, and its Map content kept as stored. The default plugin draws it as its Title and a note that its kind is not available (RD-84), and offers no authoring of its content. It is placed, sized, connected, renamed, deleted and presented as any other Resource, and the assets its content names travel with it. It may not become a Target, so creating a Reference to it is refused (`reference-target-not-targetable`); a Reference that already names it is kept. When its plugin returns, the plugin reads the Resource as it stands. A Resource with no `kind`, and content a present plugin's schema refuses, stay refused. *Why:* one Resource whose plugin is absent must not make the whole Aggregate unopenable, and a host that cannot read the content can still carry it. **built**: `core/test/resource-document-equality.test.ts` › "carries a kind no plugin draws whole at every door, its content unread (ADR 0142)"; `core/test/plugin-modules.test.ts` › "lets a Resource whose kind no plugin draws keep whatever Map content is stored"; `test/unit/aggregate-json-schema.test.ts` › "intake and the schema both refuse a kind no plugin draws whose content is not an object"; `plugin-default/test/default-plugin.test.tsx` › "draws the Title and says the kind is not available, offering nothing", "declares no reference, no Create, no outline and no Target"; `graph/test/missing-kind-references.test.ts` › "may not become one: creating a Reference to it is refused", "keeps a Reference that already names it: intake carries it"; `app/test/creation-host.test.ts` › "refuses a Reference to it, saying its kind is not available, and creates nothing"; `test/unit/missing-plugin-round-trip.test.ts` › "imports, and its file, assets and Map content come back as they were written", "renames as an ordinary Edit, its content unchanged and its assets byte-identical", "deletes as an ordinary Edit, leaving no asset only it referenced and keeping a shared one".

## Markdown, Image and Ur

- **SR-21** A Markdown Resource's content is `{ url }` naming its text, an asset (storage.md ST-31). The text is the literal source its author wrote: a Save stores it with `\n` line endings as a new asset and commits its URL, and nothing else normalizes it. A draft unchanged from the stored text saves nothing, even where the stored text has other line endings. A new one names the asset of zero bytes, an empty text. Text that cannot be read is not a refusal: the Resource draws a note in its place and offers no Edit. *Why:* InfinityCube authors Markdown source, not a document model. **built**: `plugin-markdown/test/markdown-plugin.test.tsx` › "stores text with `\n` line endings", "Saves by storing the text with `\n` endings, then committing its URL, and releases its Claim", "Saves nothing for an unchanged draft of a text stored with `\r\n` endings", "is Closed where a Map stores nothing, Open where there is no Map, and starts as the empty asset", "draws a note and offers no Edit when its text cannot be read"; `test/unit/markdown-resource-value.property.test.ts` › "is the same value in its file, in the store and on the wire, and so is its text".
- **SR-22** Replace image is one content commit that writes an Image Resource's content (its URL, SR-26) and keeps its id, Title, placement, size and Edges. The new picture is one file, chosen in a picker opened by the press or dropped on the picture, admitted by the picture rule (SR-63) and stored before the commit; more than one file is refused. It runs as exclusive work under a Claim (ED-80, ED-82). A replacement whose content is the content already held is unchanged. *Why:* replacing a picture keeps everything authored around it. **built**: `plugin-image/test/image-plugin.test.tsx` › "replaces from the rail: picks in the press, then stores and names the picture exclusively", "replaces by a file dropped on the picture, which the canvas never sees", "refuses more than one dropped file", "shows a refused content commit and keeps its picture". The unchanged clause is untested. That it also measures and writes a natural size is SR-26's bug.
- **SR-23** An Image Resource's content is a URL, and optionally a natural size that nothing reads (SR-26). It owns the URL, not the picture's bytes, and stores nothing about where the URL points. *Why:* a picture already at a URL needs no copy. **built**: `core/test/schema.test.ts` › "gives an Image Resource no body — it owns its URL, not its bytes".
- **SR-24** An image URL is `https:`, `http:`, or `/assets/<hash>` where `<hash>` has the form of an asset's hash (intake checks the form, not that the store holds it). Any other URL, `data:` included, is refused: with `image-url-unsupported` at intake, and an Edit or creation naming one is refused `resource-content-invalid`. A pasted URL creates an Image Resource only when it is one of these. *Why:* `data:` puts the bytes back in the document, and other relative forms resolve against whatever page drew them. **built**: `core/test/schema.test.ts` › "parses an image URL it accepts: %s", "refuses an image URL it does not accept, naming the rule: %j"; `plugin-image/test/image-plugin.test.tsx` › "holds a web URL or a stored asset, and refuses any other", "names a URL it refuses by its own refusal code"; `plugin-image/test/creation.test.tsx` › "takes any file, and only an image URL".
- **SR-25** An Image Resource's Title is the picture's text alternative; there is no alt field, and the Image plugin draws no Title. *Why:* a kind gets fields only where it needs them. **built**: `plugin-image/test/image-plugin.test.tsx` › "is its picture, named by its Title, with no drawn Title and nothing offered when every capability is absent".
- **SR-26** Nothing measures a picture's natural size: creation and Replace write the URL alone. The Image content's `naturalSize` stays optional in the file format, and nothing reads it. It is removed at the next deliberate format change, because the plugin's strict schema would otherwise refuse every saved image that carries it (`plugin-image/src/domain.ts`, `imageContentSchema`). *Why:* a field with no reader costs work on every creation and Replace, and holds up a pasted URL's creation until the picture loads. **bug: code differs**: a stored file is sized from its header, and a pasted URL by loading it where the surface draws it (`plugin-image/src/picture.ts`, `plugin-image/src/creation.ts`), and creation and Replace then write `naturalSize`: `plugin-image/test/creation.test.tsx` › "records the size the surface measures where the picture is drawn from"; `plugin-image/test/image-plugin.test.tsx` › "records no size for a picture whose header is silent, and loads none to measure it". The field is published in `docs/aggregate-directory.md` and `docs/schema/resource/kinds/image.schema.json` (repo root).
- **SR-27** A picture that will not load is not a refusal: the Space stays valid, the Resource still draws, saying the picture did not load and naming its URL, and its picture can still be replaced. *Why:* an external URL can change or vanish at any time. **built**: `plugin-image/test/image-plugin.test.tsx` › "draws a skeleton until the picture loads, and names its URL when it does not".
- **SR-28** An Ur Resource's content is empty and it has no content commit, so no Edit, and it may be a Target. Its Map content is its Shape (MG-86), and it has no Open. *Why:* the simplest Resource, for diagramming without documents. **built**: `core/test/schema.test.ts` › "is an id, a Title, its kind and empty content, in a file and as a Resource"; `plugin-ur/test/ur-plugin.test.tsx` › "keeps a Shape per Map, rectangular where a Map stores none and where there is no Map", "refuses Map content that is not a Shape, and content that is not empty".
- **SR-63** A picture an Image Resource stores is admitted by the Image plugin from its bytes before it is stored: PNG, JPEG, WebP or GIF, at most 10 MiB, and never SVG. A file whose declared type is refused is named before any file is stored, and a refused file is named with the formats an Image Resource draws. The picture is stored under the media type its bytes are, whatever the file declared. The asset store itself admits any media type (storage.md ST-75). *Why:* every stored picture must draw, and only these formats are served under their own type. **built**: `plugin-image/test/admission.test.ts` › "refuses %s as an unsupported format", "refuses %s with its own code", "admits an image of exactly the size limit and refuses one byte more", "refuses a declared SVG as SVG, as the host would", "names the file and the formats an Image Resource draws"; `plugin-image/test/creation.test.tsx` › "says a file refused by its declared type before any file is stored"; `app/test/image-picture-rule.test.ts` › "admits only formats the host serves under their own type, so every stored picture draws".

## Reference Resources

- **SR-29** A Reference Resource's content is a pointer to its Target, another Resource of the same Space. It has no content of its own. Content resolves on read, one hop, and is never copied or flattened at intake. To show content a second time in one Map, an author makes a Reference (MG-5). *Why:* exactly one Resource owns the content, so nothing can drift. **built**: `core/test/plugin-modules.test.ts` › "is the Target when its kind names one", "is the Target when the Target cannot be reached, and names no kind"; `graph/test/space-intake.test.ts` › "accepts a single-hop reference to a markdown resource".
- **SR-30** A plugin declares whether its Resources may be a Target: every listed kind except Reference may, and a missing kind may not (SR-62). A Target that is missing (`reference-target-missing`), is the Reference itself (`reference-targets-self`) or may not be a Target (`reference-target-not-targetable`) is refused at intake and at creation. So chains and cycles cannot exist, and there is no cycle check. *Why:* single hop keeps the source unambiguous. **built**: `graph/test/space-intake.test.ts` › "refuses a reference resource whose target resolves to no resource", "refuses a reference resource that points at itself", "refuses a reference resource whose target is itself a reference resource", "accepts a reference resource whose target is an Ur Resource (ADR 0113)", "accepts a reference resource whose target is a Space Resource"; `app/test/space-authoring-operations.test.ts` › "refuses a Target that is itself a Reference Resource, so no chain is ever authored"; `plugin-reference/test/reference-plugin.test.tsx` › "references its Target, shows its content, and may not itself be a Target".
- **SR-31** The Target is chosen once, at creation, and never changes. An Edit naming another Target is refused (`reference-target-immutable`); a wrong Target means delete and create. *Why:* retargeting would make an established Resource and its Edges mean different content. **built**: `app/test/space-authoring.property.test.ts` › "keeps an existing Reference Resource Target immutable while accepting Title edits".
- **SR-32** Apart from its Target, a Reference Resource is an ordinary Resource: its own Title, membership, placement, Edges, Open state and size are authored on it. Its Title is never its Target's, and renaming one never renames the other. *Why:* the occurrence and its content are different things. **built**: `app/test/resource-authoring.test.tsx` › "renames a Reference Resource through the shared Title interaction and preserves Target content".
- **SR-33** Open, a Reference Resource embeds its Target, drawn by the Target's own plugin on a surface that offers no authoring of the Target, and offers no content action of its own. It passes the embedding its own Title and rename, so at most one Title draws and a rename there renames the Reference; a Reference to an Image is a picture. - **SR-34** What a Reference Resource's content asks of the canvas, whether it embeds a Map and whether it draws a content area, is its Target's. A Reference to a Space Resource draws that Space Resource's selection (SR-46), read-only (SR-51). *Why:* a Reference shows what its Target shows. **built**: `core/test/resource-content.property.test.ts` › "answers Map embedding and content area regardless of via".
- **SR-35** Jump to Target navigates to the Target at its own product address and never authors it through the Reference. *Why:* content is authored on the Target. **not built**: `app/src/entity-actions.tsx` offers Copy link to Target only; tracked in `.scratch/alias-cards/issues/05-jump-to-alias-target.md` (repo root).

## Creating Resources

- **SR-36** Every creation completes its Edit on one activation, with no pane or Cancel. A plugin declares how its Resources are created and may gather input in the press (a picker, for one); the host then creates them in one atomic Edit, refused if creation is no longer available or exclusive work is running, places them and continues into the first one's Title. What a kind needs beyond a Title comes from where the gesture was made. Markdown and Ur Resources are created empty from a press, at the visible centre, stepping off an occupied point (MG-18). A Resource created with no kind chosen is of the first listed plugin whose Resources start empty. *Why:* a form collects nothing the gesture does not already know. **built**: `app/test/resource-authoring.test.tsx` › "creates an Ur Resource in one press and continues in its Title"; `app/test/creation-host.test.ts` › "refuses unavailable, then exclusive work", "places every Resource asked for in one Edit at the gesture, and continues into the first one’s Title"; `core/test/plugin-modules.test.ts` › "start a Resource created with no kind chosen as the first of them in list order"; `app/test/space-authoring-operations.test.ts` › "creates one neutrally titled detached Resource at the anchor it was given", "creates one neutrally titled Ur Resource at the anchor, in one Edit".
- **SR-37** A new Resource is titled `Resource N`, one past the highest `Resource N` among Resource names (first lines), unless SR-38, SR-41 or SR-43 says otherwise. *Why:* a neutral name the author renames in place. **built**: `app/test/titles.test.ts` › "takes one past the highest number already in use", "reads a Resource’s name, so a Title with more lines still occupies its number", "does not let a line below the name claim a number".
- **SR-38** A Reference Resource is created from its Target, by a gesture on the Target. It copies the Target's Title once, and the two are independent afterwards; an empty Title mints `Resource N`. It is aimed at a fixed offset past the Target's bottom-right corner, or at the visible centre when the Map does not place the Target, stepping off an occupied point (MG-18). *Why:* the copied Title is how the author sees what it points at. **built**: `app/test/resource-rail-actions.test.tsx` › "creates a Reference Resource of the Resource whose menu ran the command", "continues in the new Reference Resource’s own Title editor, seeded from its Target", "places the Reference Resource at a fixed offset from the Resource it was made from"; `app/test/space-authoring-operations.test.ts` › "creates and places a Reference Resource on its Target, minting a neutral title when none was typed".
- **SR-39** Image Resources are created from chosen files, dropped files or a pasted URL. Each file is admitted by the picture rule (SR-63) and stored first; a pasted URL is not stored. One Edit then creates one Resource per picture, titled `Resource N` in order, never after the file or URL, in a row from the anchor (exact for a drop or paste; a press steps off). If any file is refused, nothing is created and the notice names each refused file. The Resources land on the Map the gesture was made on, and on nothing if it is gone. *Why:* several pictures are one gesture. **built**: `plugin-image/test/creation.test.tsx` › "opens the picker for the formats an Image Resource draws, and creates one Resource for each picture", "says every file its bytes refuse, and creates none of the gesture"; `app/test/creation-host.test.ts` › "places on the Map the gesture was made on, and owes no Title once another is drawn"; `app/test/space-authoring-operations.test.ts` › "creates several in one Edit, numbered in order, in a row from the anchor". That nothing lands when the Map is gone is untested. That a picture is also measured is SR-26's bug.
- **SR-40** A new Space is created complete, in one Edit: one empty Markdown Resource titled `Resource 1`, Closed at (0, 0), in a Map titled `Map 1` that owns one empty Graph titled `Graph 1`, which is its Active Graph, and that Map is the Space's `defaultMap`. Every path that creates a Space makes this shape. The first Resource is never named after the Space. *Why:* an empty canvas offers no way in and reads as a failure. **built**: `graph/test/new-space.test.ts` › "starts complete with its first Resource at the canonical centred position", "begins neutral Resource numbering at Resource 1 naming the empty text (ADR 0018, ADR 0142)", "creates the same complete one-Resource shape as newSpace from one identity source".
- **SR-41** Create Space Resource is one coordinated Edit that creates a new Space (SR-40) and a Space Resource selecting the Map and Graph that Space opens on. Both are titled one `Space N`, numbered over the containing Space's Resource names. *Why:* one title seeds both, so they agree by construction. **built**: `app/test/space-resource-authoring.test.tsx` › "creates a Space Resource and the new Space it names from one Space N", "numbers each new Space from the Space Resources already on the Map"; `persistence/test/space-resource-lifecycle.test.ts` › "atomically creates the first Space Resource and its normal target Space".
- **SR-42** A created Space Resource is drawn when its local Edit installs, without awaiting the durable commit. A refusal comes before anything is placed, so a refused creation leaves nothing, and its notice names the Space that was not created. *Why:* a Resource that appears a round trip late is indistinguishable from a press that did nothing. **built**: `app/test/space-resource-authoring.test.tsx` › "continues in the created Resource’s own Title editor", "creates nothing and names the Space when the lifecycle refuses". That placement does not await the commit is untested.
- **SR-43** Linking references an existing Space; it is a separate gesture from creating one. The Space Resource takes the Space's title and selects what the target opens on: its `defaultMap` and that Map's Active Graph. - **SR-66** Placing a Space row from the Dock's Resources list authors a new Space Resource framing that Space, by the link gesture (SR-43); it never brings back an existing Space Resource. - **SR-61** A link first runs the containing Space's own checks; a link they refuse initializes nothing and mints no id. ## Space Resources

- **SR-44** A Space Resource's content names a target Space, a Map of it, a Graph that Map owns, and optionally a framing. Map and Graph are required, and nothing falls back to the target's `defaultMap`. Aggregate intake refuses a missing target (`space-reference-missing`), Map (`space-resource-map-missing`) or Graph (`space-resource-graph-missing`), and a Graph another Map owns (`space-resource-graph-outside-map`); each means a dangling reference. *Why:* one Space Resource's view must not follow another Space's opening choice. **built**: `graph/test/space-aggregate.test.ts` › "accepts a Space Resource naming a Map of its target and a Graph that Map owns", "locates a Space Resource whose target is absent", "locates an explicit Map that the target does not supply", "locates an explicit Graph that the target does not hold", "refuses a Graph outside the explicit Map".
- **SR-45** The target Space is chosen at creation and never changes; an Edit naming another is refused (`space-resource-target-immutable`). Many Space Resources, in many Spaces, may reference one Space. A reference cycle, a Space Resource targeting its own Space included, is refused (`space-reference-cycle`). *Why:* identity stays stable, and Open Space Resources cannot draw one another without end. **built**: `app/test/space-resource-selection.test.tsx` › "offers no way to change the Space it references"; `graph/test/space-aggregate.test.ts` › "lets two Space Resources converge on one target while each selects its own Map", "refuses a multi-Space reference cycle at the closing Resource"; `graph/test/space-intake.test.ts` › "refuses a Space Resource that targets the Space containing it". The `space-resource-target-immutable` refusal is untested.
- **SR-46** The selection is the Space Resource's. Choosing a Map or Graph on it is an Edit of that Space Resource alone: the target's `defaultMap` and every Map's `activeGraph` stay. Every placement of one Space Resource shows its one stored selection; another view needs another Space Resource. *Why:* independently configured views must not change one another. **built**: `app/test/space-resource-selection.test.tsx` › "writes a Graph chosen from the Map already selected"; `app/test/space-resource-authoring.test.tsx` › "keeps a selection per Space Resource, and stores both".
- **SR-47** Choosing a Map selects that Map's Active Graph and drops the framing. Choosing a Graph of the same Map keeps the framing. *Why:* a framing belongs to one Map. **built**: `app/test/space-resource-selection.test.tsx` › "writes the chosen Map and re-seeds the Graph from it", "seeds the Graph from the chosen Map’s Active Graph"; `core/test/space-selection.test.ts` › "drops the framing when the Map changes, since it was the old Map's", "keeps the framing when only the Graph changes, since it frames the same Map".
- **SR-48** Framing, a centre and zoom in Map coordinates, belongs to the Space Resource, never to the Map. Framing is an Edit of the Space Resource and moves no Resource of the target. *Why:* two Space Resources may frame one Map differently. **built**: `app/test/space-resource-embedded-map.test.tsx` › "authors framing on each Space Resource wheeled within the debounce window".
- **SR-49** Open, a Space Resource draws its selected Map and Graph. Editing inside that drawn Map authors the target Space (what it writes to `defaultMap` and `activeGraph`: MG-80); moving, resizing, Opening or Closing the Space Resource authors the Map that contains it. The host draws the Map through its embedding, and the Space Resource's plugin passes it the selection and the commit that writes it, so a choice made there is that plugin's own content commit (SR-46). An embedding given a Space with no view draws that Space's `defaultMap` and its opening Graph; a Space Resource always gives its view. *Why:* each Edit belongs to the Space whose data it changes. **built**: `plugin-space/test/space-plugin.test.tsx` › "embeds the Map it selects while Open, with no choice and no Claim where nothing is granted", "writes a choice the embedding makes through its own content commit"; `app/test/space-resource-embedded-map.test.tsx` › "draws the Map the Resource selects, not the target own default", "edits the target through the Open Resource without changing the containing Space".

## Drawn Maps

- **SR-50** A drawn Map is its target Space's Map: it offers every command, gesture, refusal and notice the canvas Map offers, through that Space's own authoring. Any difference not listed here is a defect:
  - only the canvas's own Space presents (navigation.md);
  - one camera (rendering.md);
  - Edit is not offered below the first level (SR-52);
  - an Edge joins Resources of one Space (MG-59);
  - a drop on an inert or read-only drawn Map is refused (SR-53).

  *Why:* a Map behaves the same wherever it is drawn. **built**: `app/test/space-resource-embedded-map.test.tsx` › "offers the full entity menu while editing a drawn Map and creates its Reference in that Space", "chooses a Shape inside a drawn Map, writing that Space’s Map and drawing it there".
- **SR-51** Each drawn Map has one policy, from most to least permissive: authoring, inert, read-only. It is read-only when it is shown through a Reference Resource, when its Space is stale, or when its Space is kept after a failed commit; read-only then passes to every Map inside it. Otherwise the Space Resource drawing it decides: Edit gives authoring, Read gives inert. Below the first level a Map is inert at most. *Why:* permission is decided once, in one place. **built**: `app/test/map-surface-policy.test.ts` › "is $policy from $inherited at depth $depth (reference $throughReference, stale $stale, editing $editing)", "passes read-only to every Map inside, and is inert at most below the first level".
- **SR-52** Edit is offered only on a Space Resource drawn in the canvas's own Map. Edit is a Claim (ED-80) the Space plugin takes and passes to the embedding, and Done or Close releases it, so one Claim at a time holds across sibling Spaces. An authoring drawn Map still moves, Opens and Closes the Space Resources in it, but what they draw is inert. *Why:* Edit must not nest without limit. **built**: `plugin-space/test/space-plugin.test.tsx` › "takes a Claim on Edit and passes it to the embedding, releasing it on Done", "releases its Claim when Closed during Edit, so nothing stays held behind a Closed face"; `app/test/map-surface-policy.test.ts` › "offers Edit and presenting only on the canvas’s own authoring Map"; `app/test/space-resource-embedded-map.test.tsx` › "moves, closes and reopens a Space Resource inside an authoring drawn Map".
- **SR-53** A drop or paste aimed at a drawn Map that is read-only, inert, or not taking a new Resource now is refused (`drawn-map-read-only`, `drawn-map-not-in-edit`, `drawn-map-nested`, `drawn-map-unavailable`) and never falls through to the Map beneath. *Why:* a gesture lands where it was aimed or nowhere. **built**: `app/test/map-surface-policy.test.ts` › "on a $policy Map at depth $depth is refused as $code".
- **SR-54** One Space or Map may be drawn several times, and each drawing is its own occurrence. A Space Resource whose selected Map is already drawn above it, the canvas's own Map included, draws nothing inside. *Why:* recursion through Space Resources must end. **built**: `app/test/space-resource-embedded-map.test.tsx` › "allows only one content editor across two embeddings of the same target", "stops embedding a Space Resource whose Map is already on the containing path".
- **SR-60** A keyboard command or a Resource's toolbar acts on the Space of the selected occurrence, or on the canvas's own Space when nothing is selected. How long a drawn Space stays composed (its holds) is NV-81.

## Space lifetime, the Meta Space and deletion

- **SR-55** There is one permanent Meta Space. No Space Resource creates it and no deletion reaches it, and it is the only Space that needs no reference. Every ordinary Space is created by creating its first Space Resource. *Why:* every Space operation is then a Resource operation. **built**: `persistence/test/space-resource-planning.test.ts` › "never cascades to the Meta Space"; `test/support/repository-contract.ts` › "`<repository>` refuses an authored commit that deletes the Meta Space"; `persistence/test/space-resource-lifecycle.test.ts` › "atomically creates the first Space Resource and its normal target Space".
- **SR-56** Every ordinary Space must be reached from the Meta Space. Aggregate intake refuses an ordinary Space no Space Resource references (`ordinary-space-unreferenced`) and an aggregate without its Meta Space (`meta-space-missing`). How a commit treats a Space the stored aggregate already left unreferenced, which lets the Edit that initializes it commit, is ST-104. While a Resource of a missing kind remains, an unreferenced Space is held instead (SR-64). *Why:* an unreferenced Space is an unreachable one. **built**: `graph/test/space-aggregate.test.ts` › "refuses every ordinary Space with no inbound Space Resource", "refuses an aggregate without its configured Meta Space".
- **SR-64** While any Resource of a missing kind remains in the aggregate, an ordinary Space that no Space Resource references is held rather than refused, because that Resource's unread content may be what reaches it. It holds only a Space the stored aggregate already holds: a commit that leaves unreferenced a Space the stored aggregate reached is refused as SR-56 says. Once no Resource of a missing kind remains, a held Space is refused, naming it, so a commit deleting the last such Resource while a Space is held only this way is refused (`aggregate-refused`, `ordinary-space-unreferenced`). Space Authoring refuses that Delete from Space first, naming the missing kind (`missing-plugin-holds-space`), and leaves the working state as it was. *Why:* no store may accept an aggregate that no longer opens, and no Edit may be kept that every later commit of its Space would be refused behind. **built**: `graph/test/space-aggregate.test.ts` › "holds it while any Resource of a missing kind stays, wherever it is", "refuses that Space, naming it, once no Resource of a missing kind is left", "holds a Space already held while a Resource of a missing kind remains", "refuses a Space left unrooted that was not already held"; `persistence/test/commit-decision.test.ts` › "keeps holding a Space the stored aggregate already held"; `test/unit/missing-plugin-round-trip.test.ts` › "refuses deleting the last Resource with no plugin, naming the Space it leaves unrooted", "accepts the deletion while another is missing, and refuses the Space once none is"; `app/test/space-authoring-operations.test.ts` › "refuses deleting the last one, naming its kind, and leaves the working state".
- **SR-57** The Space Resources referencing a Space own its lifetime together. It survives while any remains. Deleting the last deletes it in the same Edit, and so on down: every Space left with no Space Resource is deleted in that Edit. The count of references is the whole rule; there is no reachability sweep. There is no Delete Space command. *Why:* one set of operations over Resources, not a second over Spaces. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "links an existing Space and deletes its target only after the last reference is removed"; `persistence/test/space-resource-planning.test.ts` › "cascades to every Space the removal leaves unreferenced and opens the stored ones"; `graph/test/declared-references.property.test.ts` › "releases exactly the Spaces the removed references leave unreachable from the Meta Space". The absence of a Delete Space command is untested.
- **SR-58** Delete from Space removes a Resource from its Space and from every Map (MG-20). It is refused for a Resource the Space lacks (`resource-not-found`) and for one a Reference Resource in the Space still targets (`resource-has-references`, naming each by name). Deleting a Reference leaves its Target untouched. *Why:* a Space must not lose a Target from under its References. **built**: `graph/test/snapshot-edits.property.test.ts` › "always refuses to delete a Resource a Reference Resource in the Space still targets"; `app/test/space-authoring-operations.test.ts` › "refuses a Resource its Reference Resources still point at, naming them", "deletes a Reference Resource and leaves its Target untouched".
- **SR-59** A Space Resource is deleted only through the Space Resource lifecycle, as one coordinated Edit (SR-57); a one-Space Edit refuses it (`space-resource-deletion-unsupported`). The lifecycle refuses a Resource that is not a Space Resource (`space-resource-not-found`), and one a Reference still targets (`resource-has-references`). *Why:* only the lifecycle can count references across Spaces. **built**: `app/test/space-authoring-operations.test.ts` › "refuses deleting a Space Resource rather than orphaning the Space it owns"; `app/test/resource-deletion.test.ts` › "deletes a Space Resource through Space Resource authoring, in the containing Space"; `persistence/test/session-registry.test.ts` › "refuses to delete a Space Resource a Reference Resource targets, and commits nothing"; `persistence/test/space-resource-planning.test.ts` › "refuses a Resource that is not a Space Resource".
