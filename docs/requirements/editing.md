**Terms** (definitions are in `CONTEXT.md`):
- **Space Authoring**: the one module that derives, validates and installs every single-Space Edit.
- **Completion**: the completed fact a surface reports to Space Authoring, such as "this Resource settled at this point". It carries identities and settled values, never a snapshot or plan.
- **Session**: one Space's working Space, the revision last acknowledged and its persistence status.
- **Interaction draft**: an unfinished value held by the surface conducting it.
- **Replacement epoch**: a counter that tells draft owners the working Space was replaced wholesale.
- **Coordinated Edit**: one atomic Edit over several Spaces' sessions, made by the Space Resource lifecycle. Each Space it changes is a **participant**.
- **Coordination turn**: one coordinated Edit's run from start to the repository's answer. Only one runs at a time, behind the **barrier**, which pauses every session's commits.
- **Recovery replay**: Retry, Keep local or Accept stored on a failed coordinated Edit, which resends it as a new coordination turn.
- **Canvas Edit** and **drawn Edit**: an Edit made through the canvas Map, or through a Map drawn inside an Open Space Resource (see maps-and-graphs.md, Terms).
- **Composed Space**: a Space the browser holds, listed in Open Spaces or only drawn.
- **Plugin commit**: an Edit a Resource's plugin asks for on its own Resource: its Title, its content or its Map content (space-and-resources.md, maps-and-graphs.md MG-87).
- **Claim**: who is interacting with a Resource right now, taken by its plugin (ED-80).
- **Exclusive work**: work a plugin runs under a Claim that withdraws authoring and navigation everywhere until it settles, such as an Image Resource's Replace (ED-68).

**Status:** **built** means code and a named test match the rule. **built (untested)** means code matches and no test covers it. **not built** means the rule is decided and no code implements it. **bug: code differs** means the code does what the note says instead. **undecided (Cn)** means the rule waits on conflict Cn (none is open in this doc). A test is named as `file` › "test name". Paths that start with `test/` are at the repo root; all others are under `packages/`.

## Persistence statuses

A session is always in one of these statuses. Their words and how they show are in ui.md (UI-93); Exit and switching per status are in navigation.md.

| Status | Means | Later Edits | Retry offered | Recovery | Rules |
|---|---|---|---|---|---|
| `settled` | everything acknowledged | commit at once | — | — | ED-42 |
| `pending` | one commit in flight | coalesce behind it | — | — | ED-42 |
| `failed` | retryable failure | install, do not commit | yes | Retry | ED-45 |
| `rejected` | permanent rejection | the next one commits | only for size or when blocked | a later Edit | ED-46, ED-47 |
| `refused` | the backend refused the whole candidate aggregate | the next one commits | only when blocked | a later Edit | ED-48 |
| `conflicted` | the stored revision moved | install, do not commit | — | Keep local, Accept stored | ED-49, ED-27 |

## The Edit lifecycle

- **ED-1** An Edit is a validated transition from one Space to the next. No Space value is ever mutated in place; an Edit derives a new one. Space Authoring makes every single-Space Edit and is the only module that writes a session. The Space Resource lifecycle makes every coordinated Edit (ED-54), and nothing else writes a session. *Why:* one owner per lifecycle, so no caller holds half of it, and a Space stays consistent by construction. **built (untested)**: the only callers of `session.submit`, `acceptRemote` and `resolveConflict` in `app/src` are in `app/src/space-authoring.ts`. The coordinated half is ED-54.
- **ED-2** No React or React Flow type crosses Space Authoring's interface. *Why:* the lifecycle is provable without a mounted application. **built (untested)**: `app/src/space-authoring.ts` imports only `@project/core`, `@project/graph`, `@project/persistence` and app modules.
- **ED-3** A surface installs its own completed state (a drop point, a settled size) before it reports the completion, and the completion carries no snapshot, plan or effect list. *Why:* the surface owns the gesture, and Space Authoring owns the Space. **built**: `app/test/authoring-placement-copy.test.ts` › "keeps a moved Resource drawn at its drop point while its completion waits behind an in-flight one".
- **ED-4** Space Authoring re-reads the current working Space and navigation, derives a complete next Space, mints any new ids and validates the result through intake, all before any effect. A derivation that would produce an invalid Space is a defect (ED-16). *Why:* nothing moves until the whole next state is known to be valid. **built**: `app/test/space-authoring.property.test.ts` › "keeps the working Space loadable through any sequence of semantic operations".
- **ED-5** A completed Edit installs in this order: the session takes the next working Space synchronously, then, for a canvas Edit, navigation moves to the Map and Active Graph the Edit produced. A drawn Edit moves no navigation. *Why:* navigation may name only a Map and Graph that already exist. **built**: `app/test/edit-target.test.ts` › "continues Navigation on the Graph its Edit made active"; `app/test/space-authoring-operations.test.ts` › "creates and connects in the explicitly drawn Map and Graph without changing Navigation".
- **ED-6** Subscribers see one publication per Edit and never an intermediate state, even when installing throws. *Why:* a reader must never see a Map beside a Graph it does not own. **built (untested)**: `app/src/space-authoring.ts` `installTogether` (counts nested windows and publishes in `finally`).
- **ED-7** Every completed Edit persists automatically. There is no Save command, no keyboard Save and no file write-back from the browser. *Why:* durability is not a second act the author can forget. **built**: `app/e2e/editing.spec.ts` › "a completed drag persists automatically".
- **ED-8** An Edit completes without waiting for persistence, and a commit in flight withholds no authoring. *Why:* persistence is asynchronous visible state, never a lock. **built**: `persistence/test/session.test.ts` › "coalesces edits behind one in-flight commit to the latest complete snapshot".
- **ED-9** A completion that arrives while another Edit is installing is queued and is derived later, from the state the earlier Edit installed rather than the state when it arrived. What its caller hears, at every surface, is ED-78. *Why:* reentrant Edits apply in order against real state. **built (untested)**: `app/src/space-authoring.ts` `complete`. The React Flow seam treats a `queued` answer as a broken invariant, reports it and draws nothing, which ED-78 counts as part of its bug: `app/test/render-adapter.test.ts` › "reports and draws nothing when a completion at the React Flow seam is queued".
- **ED-10** A queued completion that throws is reported and is not charged to the Edit that drained the queue. Draining stops there, and every completion still queued is discarded and reported. A caller that asked to be told how its queued Edit settled is told it was refused `edit-abandoned`, the one that threw included. *Why:* the draining Edit already installed, and the rest were written against state that never came about. **built (untested)**: `app/src/space-authoring.ts` `complete`.
- **ED-11** An observer that fails is reported separately. It stops neither persistence nor the observers behind it. *Why:* a broken listener must not lose an Edit. **built**: `persistence/test/session.test.ts` › "persists an optimistic Edit and notifies later observers when one observer fails"; `persistence/test/observable-state.test.ts` › "contains synchronous failures and asynchronous rejections and continues notifying".

## Outcomes

- **ED-12** An authoring attempt that is not queued answers exactly one outcome: completed, unchanged or refused. None of the three is an error. A queued attempt (ED-9) answers `queued`, and ED-78 covers its eventual outcome. *Why:* each surface closes, stays or explains from one answer. **built**: `app/test/command-outcomes.test.ts` › "answers the caller the result its operation produced".
- **ED-13** Completed is an Edit. It is authoritative local work: Escape cannot cancel it, a persistence failure does not roll it back, and its surface closes without waiting for persistence. *Why:* a later failure is the session's to recover, not the Edit's. **built** for the failure: `app/e2e/http-persistence.spec.ts` › "a network failure stays visible until the user retries". Escape and closing without waiting are untested.
- **ED-14** Unchanged means the attempt's own change is nothing (maps-and-graphs.md MG-83): a cancelled gesture, a rename to the stored title, a chosen value the Map already draws. It writes nothing, says nothing, and the surface closes as usual. A Move to the same positions should be unchanged too, and is a bug (MG-83). *Why:* the author already has what they asked for. **built**: `app/test/command-outcomes.test.ts` › "leaves the channel clear on unchanged and queued"; `app/test/space-authoring-operations.test.ts` › "is unchanged when the trimmed draft is the stored Title".
- **ED-15** Refused means the attempt cannot happen now: stale context or a domain rule. It writes nothing and carries a stable code with typed context, never a sentence, a form field or an HTTP status. The application owns the wording, which depends only on the code and its context, and no two codes share a sentence. *Why:* identities survive copy changes and keep tests off prose. **built**: `app/test/authoring-refusal.test.ts` › "writes one distinct sentence for every refusal".
- **ED-16** A broken invariant is never a refusal. It throws, or reaches the non-throwing reporter. When it ends a command from a menu or the Dock, that command's notice says something broke. *Why:* a defect shown as the author's mistake misleads them. **built**: `app/test/command-outcomes.test.ts` › "reaches the reporter and publishes the break sentence, synchronously". A canvas gesture is ED-79.
- **ED-17** A refusal goes back to the surface that made the attempt, which keeps its draft. Focus and where the refusal shows are in ui.md (UI-90). A queued attempt's refusal reaches its surface when the queue drains, and keeps no draft (ED-78). *Why:* the author corrects the draft rather than retyping it. **built**: `app/test/resource-authoring.test.tsx` › "refuses a Title of nothing but line breaks and keeps the draft"; `app/test/edge-authoring.test.ts` › "keeps the draft on a refused Title and retains the refusal for its Edge".
- **ED-18** A creation that continues into a rename completes first, so cancelling the rename keeps what was created. *Why:* the rename is a second interaction over a finished Edit. **built**: `app/e2e/editing.spec.ts` › "Escape discards a Reference Resource rename without undoing the Reference Resource".
- **ED-78** A queued completion (ED-9) that is refused when the queue drains reports its refusal where the author made it: at that surface's refusal place (ui.md UI-90), or as an announcement if that surface has closed. No draft is kept. A drained completion that completes or is unchanged needs no further answer. Every caller treats a `queued` answer the same way: the attempt is waiting, neither completed nor failed, and its outcome arrives when the queue drains. *Why:* every attempt has one outcome, and a refusal goes back to where it was made. **bug: code differs**: the drain now tells a caller that passes a settle callback how its Edit settled (`app/src/space-authoring.ts` `complete`), and the plugin commits and the creation host wait for that answer (ED-81; `app/test/space-authoring-operations.test.ts` › "settles a queued Edit through its settle callback once the drain reaches it", "settles a queued Edit refused when the drain refuses it"; `app/test/plugin-host.test.ts` › "answers a queued Edit when it settles, and any other at once"). Every other caller passes none and hears nothing more: `command-outcomes` clears its notice channel on `queued` (`app/test/command-outcomes.test.ts` › "leaves the channel clear on unchanged and queued"), `completionOutcome` treats it as completed so a rename editor closes (`app/src/authoring-commands.ts:111-124`), `app/src/authoring-contexts.ts:270` throws, and `app/src/connection-completion.ts:115` and `app/src/edge-authoring.ts:484` report it as a broken invariant. So a queued rename, connection or Edge command that is then refused shows nothing.
- **ED-79** A broken invariant reached from any canvas gesture is reported, never thrown, and the gesture does nothing. This covers connecting, Resize, Move and Edge commands. The gesture owes the author no sentence. *Why:* a throw from a gesture handler leaves the gesture half-finished, such as a Resize whose draft stays set. The derivation fails before any change is installed, so reporting it and ending the gesture loses nothing. **bug: code differs**: the canvas reports only a `queued` answer (ED-9). A completion whose derivation fails `assertValidAuthoredSnapshot` (`app/src/space-authoring.ts:89-98`) throws, and no canvas handler catches it: connecting (`app/src/connection-completion.ts:108-123`), Resize (`app/src/render-adapter.ts:487`, which leaves `resizeDraft` set), Move (`app/src/render-adapter.ts:659`) and Edge commands (`app/src/edge-authoring.ts:478`). A plugin commit is the exception: one that throws is reported and answers the plugin refused (`app/test/plugin-host.test.ts` › "answers refused, and reports, when the Edit throws"). A connection drag is probably left stuck too (unverified). The throw does not unmount the canvas: the app has no error boundary or global error handler, and an error boundary does not catch a throw from an event handler. `app/test/render-adapter.test.ts` › "leaves the projected connection uncommitted when the completion fails" expects the throw.
- **ED-81** A plugin commit is an Edit like any other: it goes through Space Authoring, writes only the plugin's own Resource, and answers the plugin once that Edit has been applied, as completed, unchanged or refused, including an Edit that waited behind another (ED-9), which answers when the drain reaches it. A refusal reaches the plugin as the sentence the application words from its code (ED-15), which the plugin shows and never interprets. A commit made from a surface that has gone, or kept past a replacement of its Space, is refused without reaching Space Authoring. *Why:* a plugin never decides for itself whether its Edit happened, and a commit kept past a replacement names a Space that is gone. **built**: `app/test/plugin-host.test.ts` › "answers a settled Edit in the words every refusal is reported in", "answers a queued Edit when it settles, and any other at once", "commits Map content as one Edit, and refuses a commit kept past a replacement"; `ui/test/PluginResource.test.tsx` › "answers a commit the plugin kept refused once the surface has gone".

## Guard order

Every completion asks the exclusive gate (ED-82), then runs the guards below, then its own checks. The first failure is the answer and nothing after it runs. Each action's own checks, their order and their codes are stated with the action: in the "Checks, in order" column of the operations tables in space-and-resources.md and maps-and-graphs.md.

- **ED-82** Before the guards, every completion, in every Space and every action included (Add Map and Rename Space too), asks the exclusive gate: while exclusive work runs (ED-68), an Edit that is not that work's own is refused `exclusive-work-running`. The work's own Edits are admitted, and so is an Edit queued from inside one. A queued Edit that is not the work's own, drained while exclusive work runs, is refused the same way, because the work may have begun after it queued. *Why:* exclusive work is the application's one operation until it settles, wherever the Edit comes from. **built**: `app/test/space-authoring-operations.test.ts` › "refuses every Edit in every composed Space while exclusive work runs, and admits the work’s own", "refuses a queued Edit that is not the work’s own when it drains, and drains the work’s own".
- **ED-19** Guard 1: the Map the Edit writes must exist. For a canvas Edit that is the selected Map; for a drawn Edit, the drawn Map, asked before anything else. Otherwise the attempt is refused `map-not-found`. *Why:* a gesture aimed at a Map that has gone has nowhere to land. **built (untested)**: `app/src/space-authoring.ts` `complete` asks it of a drawn Edit before anything but the exclusive gate (ED-82), and `deriveCompletedEdit` of a canvas Edit. The tests that reach `map-not-found` fake the answer (`app/test/map-authoring-commands.test.ts`, `app/test/graph-authoring-commands.test.ts`).
- **ED-20** Two canvas completions skip guard 1: Add Map, which writes no existing Map, and Rename Space, which checks its title first and asks guard 1 after it. A drawn Edit, Rename Space included, asks guard 1 first. Add Map invoked from an Open Space Resource is a drawn Edit of the target Space followed by a repoint of the Space Resource, and its guard order follows maps-and-graphs.md MG-11. *Why:* on the canvas, a blank Space name is blank whether or not the canvas moved on. **built (untested)** for the order: `app/src/space-authoring.ts` `deriveCompletedEdit` and `complete`. `app/test/space-authoring-operations.test.ts` › "refuses a blank Space title and treats the stored title with padding as unchanged" covers the title check with the Map present. The code runs Add Map from an Open Space Resource as a canvas Edit of the target, which is MG-11's bug.
- **ED-21** Guard 2, drawn Edits only: when the drawing names a Graph its Map no longer owns, the attempt is refused `graph-not-owned`, whatever the action. *Why:* the drawing shows a Graph that is no longer there. **built**: `app/test/space-authoring-operations.test.ts` › "refuses a drawing whose Graph no longer belongs to its Map without changing the Space".
- **ED-22** Every Edge gesture's preview asks the same checks the completion asks, and the completion asks them again at release. *Why:* a preview and its Edit cannot disagree, and the Space may change between them. **built**: `app/test/space-authoring-operations.test.ts` › "offers a connection the completion accepts", "refuses a duplicate with the reason the completion gives".
- **ED-23** Delete Map and Delete Graph are coordinated Edits (ED-54), not completions, so these guards do not apply to them. *Why:* they may repoint Space Resources in other Spaces. **built**: `persistence/test/session-registry.test.ts` › "deletes a Map while moving every Space Resource that selected it", "deletes a Graph while moving every Space Resource that selected it".

## Interaction drafts

- **ED-24** An unfinished interaction keeps its draft in the surface conducting it: changed title text, unsaved Markdown source, a drag or connection attempt, an armed confirmation. A draft is no part of the Space, and cancelling it needs no compensating Edit. *Why:* every incomplete value stays with the one surface that understands it. **built**: `app/test/resource-authoring.test.tsx` › "cancels the edit on Escape without committing the draft".
- **ED-25** A drag has no draft in the session. Intermediate frames never reach persistence, and the drop is one Edit. *Why:* a position is authored when it is released (maps-and-graphs.md MG-21). **built (untested)** for the frames: the render adapter completes `settled-resource-movement` only for position changes no longer dragging (`app/src/render-adapter.ts`). `app/e2e/editing.spec.ts` › "a completed drag persists automatically" covers the drop.
- **ED-26** A draft survives unrelated completed Edits and persistence status changes. *Why:* only a replacement makes a draft stale (ED-30). **built**: `app/test/edge-authoring.test.ts` › "leaves the draft standing through an unrelated completed Edit"; `app/test/delete-confirmation.test.ts` › "keeps the question across a change that replaces nothing".

## Accept stored and the replacement epoch

- **ED-27** Accept stored validates the stored Space before installing it. A refusal (`stored-space-deleted`, `stored-space-invalid` with intake's errors) changes nothing: local work, the conflict and every draft survive. These codes refuse an operation on the session, not an Edit. *Why:* a refused replacement must not cost the author their work. **built**: `app/test/SpaceApp.test.tsx` › "refuses an unloadable remote snapshot instead of accepting it into the session", "keeps the conflicted Space on screen when it refuses the remote snapshot".
- **ED-28** Accepted, it replaces the working Space wholesale and is not an Edit. The session, a fresh navigation (navigation.md NV-4) and one advance of the replacement epoch install as one publication. The Space's composition and session are kept, not rebuilt; only surfaces keyed by the epoch remount. *Why:* one transition, so no reader sees the new Space with the old epoch. **built**: `app/test/SpaceApp.test.tsx` › "replaces the visible runtime and editor placement when remote state is accepted"; `app/test/render-adapter.test.ts` › "drops the published projection when a replacement Space is opened".
- **ED-29** Only Accept stored advances the epoch. Retry, Keep local, a status change, choosing a Map and completing an Edit leave it alone. *Why:* only a wholesale replacement makes local work stale. **built** for Keep local and Retry: `app/test/replacement-invalidation.test.tsx` › "keeps an unsaved Markdown draft when Keep local and retry is chosen". The other cases are untested (`app/src/space-authoring.ts`: only `acceptStoredSpace` increments the epoch).
- **ED-30** When the epoch changes, every draft owner discards its draft and every surface bound to an old target closes. Nothing keeps a list of open drafts: each owner compares the epoch, or is keyed by it. What a replacement clears in navigation is in navigation.md, and focus in ui.md. *Why:* a draft names identities from a Space that is gone. **built**: `app/test/replacement-invalidation.test.tsx` › "discards a Resource title editor holding an uncompleted draft", "drops an in-flight drag and redraws the Resource where the accepted Space places it"; `app/test/edge-authoring.test.ts` › "cancels the draft when a replacement Space is opened over it"; `app/test/continuation.test.ts` › "discards a pending continuation when a replacement takes the local work".
- **ED-31** A queued completion records the epoch it was queued under. When the queue drains, one whose epoch has changed is discarded: no Edit and one diagnostic report, and a caller that asked to be told how it settled is told it was refused `space-replaced`. Later entries still drain. *Why:* applying it would write an abandoned gesture over the Space the author just accepted. **built (untested)**: `app/src/space-authoring.ts` `complete`.
- **ED-32** Accept stored after a failed coordinated save replaces every Space the save covered. Each of those Spaces advances its own replacement epoch in the same publication, the Space where Accept stored was pressed and every other alike, so each discards its drafts and pending work as on any replacement (ED-30, ED-31, ED-73): queued completions, running exclusive work such as an image replacement (dropped, not written into the restored copy), command notices, a delete confirmation and a pending continuation. *Why:* "replaced" has one meaning, and work begun against a Space the rollback removed must not land on the restored copy. **bug: code differs**: Accept stored is offered only in the canvas Space's Dock (`app/src/dock-chrome.ts:487`), and `acceptStoredSpace` advances only that Space's epoch (`app/src/space-authoring.ts:1728`). `restoreCoordinatedCommit` restores the other Spaces without advancing theirs (`persistence/src/session.ts:621`). A Space drawn inside the canvas Space renders inside the canvas Space's `SpaceCanvas`, which is keyed on the canvas Space's epoch (`app/src/App.tsx:381, :404`), so its on-screen drafts close and its plugins remount, which ends their exclusive work's commits (ED-73). Its work keyed to its own epoch survives: queued completions (`app/src/space-authoring.ts` `complete`), plugin commits kept by a surface that did not remount, which compare that Space's own epoch (`app/src/plugin-host/plugin-commits.ts`), command notices (`app/src/command-outcomes.ts:532-563`), the delete confirmation (`app/src/delete-confirmation.ts:104`) and the continuation (`app/src/continuation.ts:165`). `app/test/active-graph-after-coordinated-recovery.test.ts` › "leaves the Dock and the canvas naming one Graph" pins the current behaviour (its header says "no replacement epoch advances").

## Availability

- **ED-33** Availability answers which operations may start now, from what is in progress alone: a plugin's exclusive work running; the canvas not having finished laying out the selected Map; presenting; a plugin holding a Claim on the canvas, as a Markdown text edit does; renaming a Resource on the canvas; renaming the Space, a Map or a Graph in the Dock; editing inside an Open Space Resource; and whether this Space is the one on screen. It never reads the Space and never depends on a Resource's kind, except that a creation in flight that asked to run alone withholds a second press of the same Create (a Space Resource's) while every other kind's stays offered. *Why:* whether the Space allows an operation is checked when it is attempted; availability only stops two interactions from overlapping. **built**: `app/test/authoring-availability.test.ts` › "offers every operation when nothing is in progress"; `app/test/space-resource-authoring.test.tsx` › "withdraws Create Space Resource while its coordinated Edit is in flight"; `app/test/creation-host.test.ts` › "ignores a second one while the first is in flight, and still creates another kind".
- **ED-34** An unavailable operation is not a refusal. Nothing was attempted, so there is no code and no reason. *Why:* outcomes describe attempts. **built (untested)**: `app/src/authoring-availability.ts` (bare booleans, no reason field).
- **ED-35** Each operation has one answer, read by every surface that offers it, the Dock and the canvas alike. Which control draws which answer is in ui.md. *Why:* two surfaces must not disagree about one operation. **built (untested)** for the sharing: `app/src/authoring-availability.ts` is computed once per render and read by both. `app/test/SpaceApp.test.tsx` › "withholds a menu’s Edits until the canvas has a placement to edit" covers the Dock.
- **ED-36** There is no edit mode. An available operation is offered without the author first entering a mode. *Why:* a mode flag would duplicate what availability already says. **built (untested)**: `app/src/authoring-availability.ts` (no mode fact).
- **ED-37** One authoring surface runs at a time. A live Dock rename, a plugin's Claim on the canvas (a Markdown text edit), a Resource rename or an edit inside an Open Space Resource withdraws starting another, and the precise table is `authoringAvailability`. An edit inside an Open Space Resource withdraws the canvas around it but not its own embedding. *Why:* a second surface would interrupt the first. **built**: `app/test/authoring-availability.test.ts` › "keeps a chrome title edit going once it has begun, and offers no second start", "leaves an embedded Map authorable while withdrawing the canvas around it".
- **ED-38** Presenting withdraws all canvas authoring, Edge connection included. *Why:* the Stage covers the canvas. **built**: `app/test/authoring-availability.test.ts` › "withdraws canvas connection while presenting, with every other canvas authoring capability".
- **ED-39** A canvas that is not the one on screen, or that has not finished laying out its Map, authors nothing, and neither do the Maps drawn inside it. *Why:* a hidden Space must not answer keys meant for the visible one. **built**: `app/test/authoring-availability.test.ts` › "withdraws an embedded Map for every reason that is not its own edit".
- **ED-40** Persistence status withdraws nothing, and a mounted session has the same availability as any other. *Why:* ED-8; and a mounted session authors as any session does. **built** for the mounted half: `app/test/mounted-session.test.tsx` › "mounted %s: offers Open, rename, drag and connect". The persistence half holds by construction: `AuthoringInProgress` (`app/src/authoring-availability.ts`) has no persistence fact.

## Sessions, statuses and recovery

- **ED-41** Each Space is its own unit of optimistic concurrency, with one live session per Space. A drawn Edit is the target Space's Edit, with that Space's outcome, session and status (space-and-resources.md SR-50). *Why:* unrelated Spaces never conflict, and a failure belongs to the Space it concerns. **built**: `persistence/test/session-registry.test.ts` › "owns one live session for each Space id"; `app/test/space-resource-embedded-map.test.tsx` › "names a drawn Space in its notice and leaves the canvas’s own Space’s unprefixed".
- **ED-42** A session sends the complete working Space after each Edit. It has at most one commit in flight; Edits made meanwhile coalesce into the newest Space, which commits next against the revision just acknowledged. *Why:* the store always gets a whole valid Space, and the newest one. **built**: `persistence/test/session.test.ts` › "coalesces edits behind one in-flight commit to the latest complete snapshot", "carries the acknowledged revision into the coalesced commit it starts".
- **ED-43** A session decides what to commit from its current working Space, not from the Space it was handed, so an Edit submitted from inside an observer commits once, as the newest. *Why:* deciding from the argument stores an older Space last and undoes a completed Edit. **built**: `persistence/test/session.test.ts` › "coalesces a submit made from an observer into one commit of the newest snapshot".
- **ED-44** A persistence failure reaches the surface as a code, and the application words each code. What a failure arm carries is storage.md ST-102, and how the transport classifies failures is ST-101. *Why:* ED-15, applied to persistence. **built**: `app/test/authoring-refusal.test.ts` › "gives every code a sentence of its own".
- **ED-45** `failed`: later Edits install locally and do not commit, and Retry commits the newest working Space. A commit that throws instead of answering counts as a retryable failure. *Why:* the author chooses when to try again, and Retry sends their latest work. **built**: `persistence/test/session.test.ts` › "stops on retryable failure and retries the latest working snapshot explicitly", "reports a throwing commit as a failure and returns to idle".
- **ED-46** `rejected`: Retry is not offered, except for size (ED-47) or after a blocked recovery replay (ED-66), and the next Edit commits the newest working Space. *Why:* resending a rejected Space unchanged would be rejected again. **built**: `persistence/test/session.test.ts` › "disables retry after permanent failure but allows a later valid submit".
- **ED-47** A rejection for size keeps the Edits and offers Retry. The size counts every Space in the request together, so a coordinated save counts every participant; the limit itself is storage.md ST-77. *Why:* the author answers it by reducing content anywhere, and Retry sends what the Spaces then hold. **built**: `persistence/test/session.test.ts` › "keeps the Edits, offers Retry, and saves once a reduction fits"; `app/test/oversized-save-retry.test.tsx` › "counts every Space a coordinated save carries, and saves once Meta is reduced".
- **ED-48** `refused` (the backend refused the whole candidate aggregate) is a status of its own and recovers as `rejected` does. *Why:* "the aggregate is invalid" and "the server declined" are different facts with one recovery. **built**: `persistence/test/session.test.ts` › "preserves coordinated aggregate refusal identities in a distinct refused session state", "does not recover a refused aggregate through retry()".
- **ED-49** `conflicted`: local work and drafts stay, and later Edits install locally without committing. Keep local commits the newest working Space against the current stored revision, recreating the Space if the store reports it deleted. Accept stored is ED-27–ED-28. *Why:* the author decides which side wins. **built**: `persistence/test/session.test.ts` › "retains local work on conflict until accepting the returned remote snapshot", "recreates a remotely deleted Space when explicitly keeping local work"; `app/test/space-authoring-operations.test.ts` › "commits the newest working Space, including Edits made during the conflict".
- **ED-50** Removed: whether a persistence report takes focus is ui.md UI-93.
- **ED-51** While any status other than `settled` stands, or exclusive work such as an image replacement runs, leaving the page asks first. Otherwise no leave handler is registered. *Why:* unsaved work is not lost by accident, and a settled page keeps the browser's back/forward cache. **built**: `app/test/app-hooks.test.tsx` › "asks before leaving only while persistence is unsettled", "asks before leaving while an image replacement runs, even with persistence settled".
- **ED-52** A mounted session reports persistence as any session does. Where its edits live, and the Dock mark that says so, are in storage.md and ui.md. *Why:* one persistence model everywhere. **built**: `app/test/mounted-session.test.tsx` › "commits an Edit, which the persistence status reports as any session’s".
- **ED-53** The persistence status is the persistence indicator. *Why:* there is no Save to show state through. **built (untested)**: definitional; the report that draws it is ui.md UI-93.

## Coordinated Edits

- **ED-54** Five operations are coordinated Edits: create a Space Resource with its new Space, link a Space Resource to an existing Space, delete a Space Resource with its cascade, Delete Map and Delete Graph. Their effects are in space-and-resources.md and maps-and-graphs.md. Callers name the operation, never snapshots, participants, revisions or order, and there is no generic multi-Space submit. *Why:* coordination stays inside the one lifecycle that needs it. **built**: `persistence/test/session-registry.test.ts` › "offers Space Resource coordination only through its lifecycle operations".
- **ED-55** A coordinated Edit installs every participant and publishes once, then commits them in one atomic commit. The answer must acknowledge every changed or created participant and every deletion exactly once, or it is a protocol rejection. A created participant's session is acknowledged, and a deleted participant's session is removed, only once that complete answer arrives. *Why:* no stored revision ever holds half of it. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "atomically creates the first Space Resource and its normal target Space", "names the participant a malformed coordinated result omitted", "accepts a remote deletion by evicting the absent participant session".
- **ED-56** One coordination turn runs at a time behind the barrier. It pauses every session, then waits only for commits already in flight. Work still queued stays queued for a later turn. The barrier stays up until the repository answers. *Why:* pausing first is what makes the wait end, and no ordinary commit may overtake the coordinated one. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "serializes lifecycle installation behind the preceding atomic repository answer", "pauses a session opened while a coordinated repository request is in flight".
- **ED-57** A link made while the target Space has a new Graph not yet committed selects the target's stored Graph, not the new one. *Why:* the barrier waits only for commits in flight (ED-56), and a bounded wait is worth this stale read. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "links against a target Space's stored selection, not a Graph still queued behind an in-flight commit".
- **ED-58** Each turn reads the stored aggregate once. Participants are read as their working Spaces, which is what the commit sends; every other Space, including a link's target and the Spaces a cascade counts, is read as stored. *Why:* the browser judges the aggregate the repository will judge. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "reads the aggregate once per coordination turn for a cascading delete", "does not cascade a deletion through a target another Space still references in storage after a transient failure elsewhere".
- **ED-59** Before installing anything, the browser judges the candidate with the repository's own commit decision (see storage.md), so a refusal answered then is the repository's. *Why:* the browser's verdict and the store's differ only when stored state moves during the turn. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "forgives a Space already unreferenced in storage when the pre-check judges an unrelated Edit", "does not judge a link that changes only Meta against a non-participant's refused local work".
- **ED-60** A create or link whose containing Space, or a link whose target, is `failed` or `conflicted` is refused `persistence-recovery-required`, naming that Space and its recovery. When a link initializes its target is space-and-resources.md SR-61. *Why:* the Edit would build on a Space whose stored state is unknown. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "refuses an affected $persistence Space without changing local or backend state", "refuses a link whose target is $persistence, naming the target, and installs nothing".
- **ED-61** A deletion (Space Resource, Map or Graph) is refused `persistence-recovery-required`, naming the Space, when a `failed` or `conflicted` Space refers, in its stored or its working copy, to a Space the deletion removes, or selects the Map or Graph it deletes. *Why:* the broken Space's eventual retry would otherwise dangle forever. **built**: `persistence/test/session-registry.test.ts` › "refuses to delete a Graph a failed sibling selects only in its working Space", "refuses to delete a Graph a failed sibling still selects in storage"; `persistence/test/space-resource-lifecycle.test.ts` › "refuses a deletion cascade when its target Space needs recovery", "update: deleting a Map of a Space that needs recovery is refused by name".
- **ED-77** A `rejected` Space, or a Space needing recovery that refers to nothing the deletion removes, does not block a deletion. *Why:* a rejected Space's work is already refused, and one broken Space must not block every deletion. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "does not refuse an ordinary deletion because an unrelated Space needs recovery". The `rejected` case is untested (`persistence/src/session-registry.ts` `recoveryNeeded` counts only `failed` and `conflicted`).
- **ED-62** A coordinated Edit answers completed once every participant is installed, before the repository answers. The repository's answer then becomes every participant's persistence status together. *Why:* ED-8, and the Edit is one. **built** for the shared status: `persistence/test/space-resource-lifecycle.test.ts` › "refuses every participant together when the backend refuses the coordinated aggregate". Answering before the repository is untested (`persistence/src/session-registry.ts`).
- **ED-63** Retry, Keep local and Accept stored, pressed in any participant, resolve every participant together, and Retry carries later local work with it. *Why:* one Edit, one recovery. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "retries every participant together with later local work", "keeps local state across every conflicted participant with one action", "resolves CHILD and TARGET together through CHILD's Accept stored".
- **ED-64** A `rejected` Space may be a participant, and reattempting a rejected coordinated Edit carries every original participant. *Why:* a later valid Edit may already resend its newest work. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "reattempts a permanently rejected coordinated edit with every original participant".
- **ED-65** Authoring stays available during a coordination. An ordinary Edit made after installation queues behind it and commits on a later turn, and is never overwritten by the coordinated snapshot. *Why:* local work is authoritative. **built**: `persistence/test/session.test.ts` › "still commits a plain Edit submitted while a coordinated commit is in flight", "does not let a plain Edit queued before a coordinated commit overwrite it at resume".
- **ED-66** When a recovery replay cannot resend, because another coordinated Edit's recovery still covers one of its Spaces or because reading the stored Spaces failed, every participant records the save as blocked and names the blocking Space. The Edits are kept, and each participant's recovery is offered again: Retry, or Keep local and Accept stored when it is conflicted. Resolving the blocker resends nothing until the author asks. *Why:* the reason shown is the latest attempt's, and nothing saves behind the author's back. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "names the Space whose recovery refused the replay, keeping the Edit it did not save", "does not replay when the blocking recovery resolves, and saves the latest Edits on Retry", "says a Retry whose replay read failed did not save, and keeps Retry available".
- **ED-76** Acknowledging a coordinated commit ends the session's recovery, so a recovery overtaken by a later commit never settles or rolls back a session that has moved on, and a commit in flight always means `pending`. *Why:* a stale recovery must not undo acknowledged work. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "does not let a superseded recovery roll a participant back from a revision a later commit acknowledged", "does not let a superseded recovery settle a session over its in-flight commit".
- **ED-67** A throw anywhere in a coordination leaves every participant in an explicit recoverable status and lowers the barrier. *Why:* a stuck barrier would block every later coordinated Edit. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "releases the barrier and rejects every participant when the backend throws", "unwind: a thrown commit leaves every participant recoverable by one later Edit".

## Claims and exclusive work

What Replace image writes is in space-and-resources.md.

- **ED-80** A Claim is who is interacting with a Resource, and a plugin takes one for an interaction that must run alone: a Markdown text edit, a Space Resource's Edit, an Image Resource's Replace. Claims nest through what a plugin embeds. The first Claim may be taken by any drawing, and a later one only inside the deepest Claim held, so a sibling is refused. Releasing the deepest returns to the Claim outside it; an outer Claim asked to release while an inner one runs is released once the inner one is. Two drawings of one Resource share one Claim, and while one holds it the other is offered no commit. A drawing that unmounts releases every Claim taken through it. Where a Claim's commands show is ui.md. *Why:* one interaction at a time, wherever a Resource is drawn, without a list of every interaction kept anywhere. **built**: `app/test/plugin-host.test.ts` › "grants a first Claim to any drawing, and a later one only inside the deepest", "releases the deepest Claim at once, returning to the one outside it", "keeps an outer Claim released while an inner one runs, and completes it when that one is released", "keeps two drawings of one Resource apart: one Claim, and unmounting the other keeps it", "releases a drawing and every Claim inside it when it unmounts, ending their work"; `ui/test/PluginResource.test.tsx` › "offers no commit to a drawing while another drawing of its Resource holds a Claim".
- **ED-68** A Claim may run work exclusively, as an Image Resource's Replace does. While any composed Space, listed or only drawn, runs exclusive work, every Space withdraws its authoring (its navigation is held too: navigation.md NV-50), and only that work can still commit, to its plugin's own Resource, and store an asset (ED-82). Both return once the work settles, which is once its Edit is applied, without waiting for it to persist. *Why:* several Edits also move the address, and one rule for every Space is simpler than classifying each command. **built**: `app/test/dock-navigation-hold.test.tsx` › "withdraws the canvas Space’s navigation and authoring while an only-drawn Space replaces an image"; `app/test/plugin-host.test.ts` › "withdraws every plain commit while exclusive work runs, and keeps that work’s own live", "withdraws storing and picking while exclusive work runs, and keeps that work’s own store live". Settling without waiting to persist is untested (`app/src/plugin-host/plugin-gate.ts`).
- **ED-69** The work's own surface, and the Claims it nests in, stay held and mounted to show its answer, and every commit they kept from before the work is refused until it settles. *Why:* the author sees the result, and nothing but the work lands while it runs. **built**: `app/test/authoring-availability.test.ts` › "withdraws other operations while replacing an image but keeps its editor mounted"; `app/test/plugin-host.test.ts` › "nests an Image’s Replace inside a Space Resource’s Claim, withdrawing the Space’s kept commits until it ends", "keeps a Claim released during its exclusive work until that work ends".
- **ED-70** During exclusive work, Accept stored is withheld until it answers, while Retry and Keep local stay available. *Why:* the work stands on the session it began in, and a recovery that re-commits replaces nothing. **built**: `app/test/persistence-control.test.tsx` › "keeps Keep local and retry during a replacement and withholds Reload until it answers".
- **ED-71** One exclusive work runs at a time. A second attempt is answered busy and starts nothing. *Why:* ED-68. **built**: `app/test/plugin-host.test.ts` › "runs exclusive work one at a time, for a holder, and grants nothing while it runs", "answers busy to exclusive work while other work runs, and withdraws the gate after".
- **ED-72** The wait is bounded: an asset upload ends after two minutes, whether the host never answers or its answer never finishes arriving. No measurement holds the wait: a Replace reads what size a picture's bytes declare and loads nothing to measure it. Whether a size is recorded at all is SR-26. *Why:* exclusivity must not hold the application indefinitely. **built**: `http/test/asset-upload-timeout.test.ts` › "still ends an upload the host never answers", "still ends an upload whose answer never finishes arriving"; `plugin-image/test/image-plugin.test.tsx` › "records no size for a picture whose header is silent, and loads none to measure it". The two-minute default (`http/src/backend.ts` `uploadTimeoutMs`) is untested.
- **ED-73** Exclusive work whose Space is replaced while it runs is discarded: a replaced Space remounts every plugin, and a surface that unmounts ends its work's commits, so nothing lands on the accepted Space. *Why:* ED-30. **built**: `ui/test/PluginResource.test.tsx` › "draws the plugin again once the Space is replaced or its Map content changes"; `app/test/plugin-host.test.ts` › "ends exclusive work’s commits when its surface unmounts, so only one run is ever live".

## Undo and Redo

- **ED-74** Undo reverses one whole Edit, coordinated Edits included, so an Edit that moved many Resources is undone in full, and Undo of a coordinated Edit reverses it in every participant, not only the selected Space. It acts on the Space of the selected occurrence, or on the canvas's own Space when nothing is selected. Until it is built, an Edit is reversed only by another Edit. *Why:* an Edit is the unit the author made, and a selection names the Space it belongs to. **not built**: no code.
- **ED-75** Redo reapplies the Edit the last Undo reversed, in the same Space. *Why:* the inverse of ED-74. **not built**: no code.

## Effects across operations

- **Every completed Edit is submitted to the session of the Space it changes** (ED-7). Exceptions: a coordinated Edit installs in every participant and commits once for all (ED-55); a queued completion discarded by a replacement submits nothing (ED-31).
- **Every Edit publishes once** (ED-6). Exception: a coordinated Edit publishes once after installing every participant (ED-55).
- **Pending persistence withdraws nothing** (ED-8, ED-40). Exception: running exclusive work withdraws authoring everywhere (ED-68), and every Edit not its own is refused (ED-82).
- **Only Accept stored advances the epoch** (ED-29). After a failed coordinated save it advances the epoch of every Space the save covered (ED-32).
- **A refusal changes nothing**: an Edit refusal (ED-15), an Accept stored refusal (ED-27), a coordinated refusal (ED-59–ED-61) and an unavailable operation (ED-34, not a refusal at all) all leave the Space and every draft as they were.
