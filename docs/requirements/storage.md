**Terms** (definitions are in `CONTEXT.md`):
- **Aggregate**: every Space at once, with the Meta Space named as its root (`{ metaSpaceId, spaces }`). One Space with its Resources is a **Space snapshot**.
- **Aggregate directory**: an Aggregate on disk: `aggregate.json`, one directory per Space, and `assets/`.
- **Asset**: bytes with a media type, named by the SHA-256 of those bytes, which a Resource reaches by the URL `/assets/<hash>`. Every file a Resource uses is an asset: a Markdown Resource's text and an Image Resource's stored picture are the ones written today. The **asset store** holds them; on disk each is `assets/<hash>.<ext>`.
- **Repository** (or **store**): where the live Aggregate is kept: PostgreSQL, SQLite or memory. A **lifecycle door** is one of its two whole-Aggregate operations, `initializeAggregate` and `replaceAggregate`.
- **Intake**: the validation every stored or imported Space and Aggregate passes before it loads.
- **Default Content**: the generated Aggregate a new repository, or `cube init`, starts from.
- **Source**: what the directory reader reads files from: the filesystem, files held in memory, or GitHub. A source names itself, lists one directory and reads one file.
- **Working read**: a read of one Space for authoring. The **working-space loader** answers it and runs the first working read (MG-74) when the Space needs one.
- **Import**, **Export**, **Running**, **Mounting**: reading an Aggregate directory into a repository; writing a repository's Aggregate to a directory; serving a directory through a memory store and Exporting back to it; reading an Aggregate from GitHub into a page.

**Status:** **built** means code and a named test match the rule. **built (untested)** means code matches and no test covers it. **not built** means the rule is decided and no code implements it. **bug: code differs** means the code does what the note says instead. **undecided (Sn)** means the rule waits on conflict Sn; the note says what the code does meanwhile. A test is named as `file` › "test name". Paths that start with `test/` are at the repo root; all others are under `packages/`. Tests in `test/support/repository-contract.ts` run once per repository, and their names begin with the repository's name, which is left out here.

## Data model: the Aggregate directory

| Path or key | Optional | Written by | Refused at intake when |
|---|---|---|---|
| `aggregate.json` `version` | no (`1`) | Export | any other version |
| `aggregate.json` `metaSpaceId` | no | Export | absent, or not a UUID |
| `<space-id>/` | — | Export | it holds `space.json` and its name is not a lower-case UUID |
| `space.json` `version` | no (`1`) | Export | any other version, as one refusal |
| `space.json` `id` | yes, in a hand-written file | Export | it contradicts the directory name |
| `space.json` `title`, `maps`, `defaultMap` | `maps`, `defaultMap`: yes | Export | see maps-and-graphs.md |
| Map `kind` | yes (`positioned`) | Export | any other kind |
| Map `id`, Graph `id` | yes, in a hand-written file | Export | not a UUID |
| `resources/<id>.json` `id` | no | Export | absent, or not a UUID |
| `resources/<id>.json` `title`, `kind`, `content` | no | Export | ST-29–ST-31 |
| `assets/<hash>.<ext>` | yes | Export | not named for its bytes, over 10 MiB, or a second file of one hash |

Every object in `aggregate.json`, `space.json` and a Resource file's envelope rejects a key it does not declare (ST-24). Nothing else in a Space directory is read: a `*.md` file beside `space.json` or in `resources/` is the author's (ST-31).

## Repository

- **ST-1** The browser reaches stored Spaces only through `SpaceBackend` over HTTP. It names no file, path, database or storage, and no request can carry one. Mounting is the one exception (ST-86). *Why:* the browser must not depend on where Spaces are kept. **built (untested)**: `app/src/space.ts` (an `HttpSpaceBackend` is the default backend), lint zone on `@project/aggregate` in `eslint.config.js`.
- **ST-2** The stored seam offers a lazy single-Space read, a complete Aggregate read, a Space listing and one commit. The server's repository is a strict superset that adds the two lifecycle doors, `loadMetaSpaceId` and `markExported`; the browser-facing seam declares neither door. *Why:* establishment and replacement are administrative and must be unreachable from a page. **built**: `test/unit/space-resource-repository.test.ts` › "declares the server repository as a strict superset of the HTTP seam".
- **ST-3** PostgreSQL and SQLite share one Space repository implementation; each database supplies only its own small store of statements. *Why:* two repositories would drift in what they answer. **built**: `test/unit/space-resource-repository.test.ts` › "accepts the one SQL repository and the E2E repository without adapters".
- **ST-4** Every repository (SQL and memory) passes one shared behavioural contract, the whole lifecycle included, and decides every commit with the one commit decision. A repository that answers differently is defective. *Why:* a Space must behave the same whichever store holds it. **built**: `test/unit/sql-fast-path-decision.test.ts` › "decides exactly what decideCommit decides, and hands every structural Edit to it"; `test/support/repository-contract.ts` (composed for each repository).
- **ST-5** In the SQL repository, a commit that is a single update keeping `defaultMap`, every Map and Graph id and which Map owns each Graph, the set of Resources and their kinds, and every Space Resource selection commits without waiting on other such commits (positions, Open, size, Shape, Edges, titles, content and Graph order all qualify). A commit that adds or removes a Space, Resource, Map or Graph, or changes `defaultMap` or a selection, waits until no other such commit or whole-Aggregate operation is running, and so do complete reads and the lifecycle doors. *Why:* ordinary editing must not queue behind the whole Aggregate. **built**: `test/unit/sql-fast-path-decision.test.ts` › "writes a Map-internal Edit to the Space other Spaces select into", "hands deleting a Graph another Space selects to decideCommit, which refuses it".
- **ST-6** A revision is a non-negative integer stored as canonical decimal text, at most 2^63−1, on every database and on the wire. A created Space lands at revision 0 and each update adds one. *Why:* a revision must never lose precision on its way through. **built**: `test/support/repository-contract.ts` › "stores and commits a revision above Number.MAX_SAFE_INTEGER as canonical decimal text", "refuses to store a revision above the 2^63-1 ceiling"; `persistence/test/commit-decision.test.ts` › "lands a created Space at revision 0 with a null exportedRevision".
- **ST-7** A read that meets contradictory stored state (Spaces with no Meta identity, an Aggregate failing intake, a document that does not parse, a non-canonical revision) fails as an invariant failure, which HTTP answers as 500 `internal-error` (ST-80). It is never repaired on read. *Why:* broken stored state is a defect, and guessing would hide it. **built**: `test/support/repository-contract.ts` › "raises an identifiable invariant failure for a stored Space whose revision is not canonical"; `test/unit/database-startup.test.ts` › "fails explicitly on stored Spaces that no Meta identity names".
- **ST-100**: removed, see editing.md ED-1 (an Edit is a validated transition from one Space to the next; Editing owns that no Space value is edited in place).

## Meta lifecycle

- **ST-8** A repository is uninitialized when it holds no Spaces and no Meta identity. Nothing is inferred about Meta from order, count or topology: every complete Aggregate names its Meta Space. *Why:* the root is a stated fact, never a guess. **built**: `test/support/repository-contract.ts` › "initializes and replaces only through explicit Meta-rooted aggregates".
- **ST-9** `initializeAggregate` takes a complete Aggregate. It answers `initialized`, `existing` when the same Aggregate is already stored, or `already-initialized` when a different one is. Sameness compares authored meaning, not serialization or object-key order. Only one of two different concurrent initializations succeeds. *Why:* re-running an initialization must be harmless and never merge. **built**: `test/support/repository-contract.ts` › "classifies canonical and different initialization proposals", "ignores object-key insertion order when classifying initialization", "lets only one different concurrent initialization establish state".
- **ST-10** A database host initializes an uninitialized repository at start-up, from Default Content, and never reseeds an initialized one. While the database is unreachable it keeps retrying with a bounded back-off; it stops on a failure that a second attempt confirms no wait cures. *Why:* a fresh database opens on a Space, and an author's deletions are never undone. **built**: `test/unit/database-startup.test.ts` › "initializes an uninitialized repository from Default Content", "answers the stored Meta identity without reseeding an initialized repository", "backs off, up to a bound it then holds", "stops at contradictory stored state that a second read confirms".
- **ST-11** Default Content is one deterministic generator, used by database start-up and `cube init`. What it generates is ordinary authored state: nothing protects, repairs or re-adds it, and deleting all of it never triggers a reseed. Which Aggregates are valid is in space-and-resources.md. Today it generates the ordinary new Space (see space-and-resources.md), titled `New space`. *Why:* initialization and reset must not drift. **built**: `test/unit/database-startup.test.ts` › "mints one complete Meta Space through the injected identity source", "answers the stored Meta identity without reseeding an initialized repository"; `test/unit/run.test.ts` › "writes a new aggregate to a %s directory, which a run then serves".
- **ST-99** Default Content will generate the release's starting talk (its content is tracked in `.scratch/v1-release/issues/16`, repo root), and a CLI hard reset rebuilds the repository from the same generator. The hard reset also clears the asset store; nothing else does. There is no merge-style seed command and no reset control in the browser. *Why:* a fresh install and a reset show the same thing. **not built**: as above; today `cube import <dir> --dangerous-replace` stands in for the reset, and it keeps the asset store.
- **ST-12** `replaceAggregate` deletes everything stored and writes the new Aggregate, in one step, whether or not the stored state is valid or even parses. *Why:* replacement is the way out of broken stored state. **built**: `test/support/repository-contract.ts` › "replaces everything stored, freeing the Resource ids it clears"; `test/unit/import-aggregate.test.ts` › "truncates a stored aggregate that fails intake and imports in its place".
- **ST-13** Replacement is never unconditional. It must name the Meta Space id the operator saw, read without validating the rest (`loadMetaSpaceId`). If a different Meta id is stored when it writes, it conflicts and writes nothing. If none was stored when read, replacement may clear Spaces that have no Meta. *Why:* an operator must not replace an Aggregate they did not look at. **built**: `test/support/repository-contract.ts` › "refuses a replacement authorized against a superseded Meta identity", "truncates stored Spaces without a Meta identity only when none was expected".
- **ST-14** Replacement answers `uninitialized` on an empty repository and never establishes first state; the caller then takes the initializing door. *Why:* each door does one thing. **built**: `test/support/repository-contract.ts` › "refuses replacement before initialization"; `test/unit/import-aggregate.test.ts` › "initializes rather than replaces an empty repository under replace".
- **ST-15** Both lifecycle doors refuse an Aggregate that fails intake with structured refusals, before anything is deleted or stored. *Why:* a bad proposal must cost nothing. **built**: `test/support/repository-contract.ts` › "refuses an initialization that fails domain intake, storing none of it", "rolls back a refused replacement".

## Commits

- **ST-16** A commit is one non-empty change set. Each change creates a Space snapshot, updates one at its expected revision, or deletes one at its expected revision, and names a Space at most once. *Why:* a single Edit and a topology Edit use the same operation. **built**: `persistence/test/commit-decision.test.ts` › "refuses an empty change set", "refuses one Space named twice".
- **ST-17** A commit has one outcome, named once for both sides of the seam: `committed` (every assigned revision and deleted id), `conflict` (every mismatched current value), or `aggregate-refused` (stable intake identities and locations). A malformed request is `rejected`. *Why:* both sides decode the same three answers. **built**: `test/support/repository-contract.ts` › "reports every conflict and rolls back every refused aggregate", "answers a stale expected revision with the current aggregate".
- **ST-18** A candidate is accepted only if the whole resulting Aggregate passes intake; a refused commit stores nothing. Which Aggregates are valid is in space-and-resources.md. *Why:* no commit may leave the store inconsistent. **built**: `test/support/repository-contract.ts` › "refuses a commit that fails domain intake and stores nothing".
- **ST-19** Deleting a Space that a Space outside the commit still references is a conflict, not an aggregate refusal. A reference the commit itself submits is judged by intake and refused. *Why:* the caller's view of the other Space is stale, so it reloads rather than invents a revision. **built**: `test/support/repository-contract.ts` › "atomically creates, links, reads, converges on, and deletes a Space".
- **ST-20** A commit may not claim a Resource another Space owns. The store adds no check of Map or Graph ids across Spaces. Uniqueness itself is SR-6 (Spaces and Resources) and MG-2, MG-35 (Maps and Graphs). *Why:* only Spaces and Resources are looked up store-wide. **built**: `test/support/repository-contract.ts` › "refuses a commit claiming a Resource another Space owns", "scopes Graph identities to their containing Space".
- **ST-21** A repository answers a Space's Resources in ascending id order, whatever the order they arrive in. The domain's own order is SR-10. *Why:* reads are deterministic. **built**: `test/support/repository-contract.ts` › "returns a Space's Resources in ascending id order however they were supplied".
- **ST-104** The commit decision forgives `ordinary-space-unreferenced` for a Space the stored Aggregate already left unreferenced, so the Edit that initializes a stored mapless target can commit on every repository. *Why:* an unrelated Edit must not be refused for a state it did not cause. **built**: `persistence/test/space-resource-lifecycle.test.ts` › "forgives a Space already unreferenced in storage when the pre-check judges an unrelated Edit".

## Intake and strictness

- **ST-22** Every Space value is built by one intake that parses the space document and every Resource, validates references and indexes the result, whether it comes from files or from a stored snapshot. Nothing downstream takes a value that has only passed the schema. *Why:* a Space is consistent and indexed by construction. **built**: `graph/test/space.test.ts` › "reports a bad shape as errors rather than throwing"; `graph/test/space-snapshot.test.ts` › "builds the validated indexed Space consumed by graph logic", "reports an invalid persistence shape without constructing a Space".
- **ST-23** Intake does no I/O and is synchronous: Resource files are handed to it as an argument. *Why:* reading bytes is the shell's business, so intake runs anywhere. **built (untested)**: `graph/src/space.ts` `loadSpace`.
- **ST-24** `aggregate.json`, the space document, a Map, a Map entry, a size, a Graph and an Edge each reject a key they do not declare, at every door: file, stored document, HTTP and intake. A Map entry declares `x`, `y`, `size` and `content`, so a retired `open`, `shape` or `openSize` key is refused like a misspelt one. *Why:* a stripped key is a question answered silently. **built**: `core/test/schema.test.ts` › "rejects an undeclared key rather than opening on a Map its author did not name", "rejects a key the map does not declare, rather than stripping it", "refuses a value JSON cannot carry, and the retired shape and open keys", "refuses the retired openSize", "refuses a Graph carrying a key the format does not declare, rather than stripping it", "refuses a key the Edge does not declare, rather than stripping it".
- **ST-25** A Resource file's envelope rejects an undeclared key. A stored Resource document, which is also what HTTP carries, strips one. Each listed plugin's `content` is strict at every door, parsed by that plugin's schema and nothing else; a kind no plugin in the build draws has its `content` carried unread (SR-62). *Why:* a file is hand-written and must say what it got wrong; the plugin's schema is the one parser of its content. **built**: `core/test/schema.test.ts` › "strips a key beside the stored envelope, and refuses one its kind's content does not declare"; `core/test/resource-document-equality.test.ts` › "refuses an unknown $kind content key at every door", "carries a kind no plugin draws whole at every door, its content unread (ADR 0142)".
- **ST-26**: removed, see space-and-resources.md SR-10.

## File format

- **ST-27** An Aggregate directory holds `aggregate.json` (`version` 1 and `metaSpaceId`, and no Space inventory), one directory per Space named by its lower-case UUID, and `assets/`. A Space is in the Aggregate because its directory is there. *Why:* one fact, one place. **built**: `test/unit/aggregate-round-trip.test.ts` › "writes a versioned aggregate file naming the Meta Space, and one directory per Space"; `test/unit/read-aggregate.test.ts` › "refuses a Space directory whose name is its UUID in upper case".
- **ST-109** The root file is `aggregate.json` and nothing else: Import, Running, `check`, Export's read-back and a mount read no other name, so a directory holding only the earlier root file, `hyper.json`, is refused as one with no `aggregate.json`. Export into such a directory writes `aggregate.json` and leaves `hyper.json` alone, as it leaves every file it does not own (ST-56); the author renames or removes it with git. *Why:* the file is named for what it roots, so a later rename of the product does not touch the format, and reading two names would put a rule for one rename in every source. **built**: `test/unit/read-aggregate.test.ts` › "refuses a directory with no aggregate file, naming it"; `test/unit/export-aggregate-in-place.test.ts` › "never touches what Import does not read". No test uses the earlier file's name.
- **ST-28** A Space directory holds `space.json` (`version`, `id`, `title`, `maps`, `defaultMap`) and `resources/`. The space file lists no Resources and has no Space-level `graphs`: a Map holds its Graphs, and a Graph's `edges` is required and may be empty. *Why:* the directory is the inventory. **built**: `core/test/schema.test.ts` › "holds no resources — a resource exists because its file does (ADR 0020)", "nests a Graph under the Map that owns it, with no Space-level collection", "accepts a graph with no edges — a Map mints its initial Graph empty".
- **ST-29** Each Resource is `resources/<id>.json` holding the envelope `{ id, title, kind, content }`, specified as JSON Schema in `docs/schema/resource/`. Its identity is the `id` inside, never the file name, and a duplicate id across files is refused naming both. *Why:* renaming a file is not an identity change. **built**: `test/unit/aggregate-json-schema.test.ts` › "admits a valid Resource file through the whole of intake"; `graph/test/space.test.ts` › "rejects the same resource id in two files, naming both".
- **ST-30** `kind` is required, with no default: a file with no kind, or a malformed kind id, is refused. A well-formed kind that no plugin in this build draws is not refused: its Resource is read with its `content` whole (SR-62). The kind-id grammar is SR-17. *Why:* a missing kind must never quietly mean one, and one Resource whose plugin is absent must not make the whole Aggregate unreadable. **built**: `graph/test/resource-file.test.ts` › "refuses a file that declares no kind, with no Ur default (ADR 0128)", "refuses a malformed kind id, saying what a kind id is", "reads a well-formed kind id no plugin in this build draws, its content whole (ADR 0142)".
- **ST-31** A Resource keeps no file beside its Resource file: every file a Resource uses is an asset (ST-34), which its content names by URL. A Markdown Resource's content is `{ url }`, and its URL is `/assets/<hash>`; its text is a plain Markdown file with no frontmatter, held at `assets/<hash>.md` in an Aggregate directory, where `<hash>` is the last segment of the URL. A path locator, a media type, inline source and any other URL are refused. A new Markdown Resource names the asset of zero bytes, which needs no file. A Markdown asset the directory does not hold is not refused. A `*.md` file in a Space directory or its `resources/` is not read, and Export leaves it alone. *Why:* a Markdown file and a picture are the same thing to the host, and one way of holding bytes is enough. **built**: `core/test/schema.test.ts` › "reads a Markdown Resource file as the URL of the asset holding its text (ADR 0142)", "refuses a Markdown Resource file that carries its source, a sidecar or an outside URL"; `graph/test/resource-file.test.ts` › "refuses a sidecar locator, an inline source, or a URL outside the asset store"; `test/unit/run.test.ts` › "writes a Markdown Resource as its Resource file and its text as an asset, and removes both on delete"; `test/unit/export-aggregate-in-place.test.ts` › "never touches what Import does not read".
- **ST-32** Resources are found only directly in `resources/`, and Space directories only directly in the Aggregate directory. *Why:* nested Spaces may later want subdirectories, which a recursive scan would make ambiguous. **built**: `test/unit/read-single-space.test.ts` › "reads a space-file or directory input with globally sorted, non-recursive resources"; `test/unit/read-aggregate.test.ts` › "does not descend past the immediate children".
- **ST-33** A Map stores `kind: 'positioned'`, the only kind. A hand-written Map may leave it out; any other kind is refused. *Why:* a second kind can be added without a migration, and a hand-written Map stays short. **built**: `core/test/schema.test.ts` › "defaults a map with no kind to positioned, so one can be hand-written", "rejects a map kind it does not know".
- **ST-34** A stored asset is `assets/<hash>.<ext>`, where `<hash>` is the SHA-256 of its bytes as 43 characters of unpadded base64url, also the last segment of its URL. The extension gives its media type through one table, and any other extension, or none, is `application/octet-stream`. Export keeps the name of a file already there, and names a new one by the table, `.bin` for a type the table does not list. One asset is written once however many Resources reference it. *Why:* the name proves the bytes. **built**: `test/unit/aggregate-round-trip.test.ts` › "stores one file for two Resources showing the same picture", "keeps each asset file name and media type through Import then Export", "carries a listed media type through Export then Import, and an unlisted one as octet-stream"; `test/unit/export-aggregate.test.ts` › "keeps the name an asset has in the directory, so its extension survives".
- **ST-35** One directory format serves every store: the same Aggregate Exports to the same bytes whichever store held it and however its objects were ordered. Sizes are written width before height and Resource file keys in envelope order. Every Map content, and the `content` of a Resource whose kind no plugin draws, is written with its keys sorted at every depth. An asset is written as the bytes the store holds. *Why:* a directory is reviewed in git. **built**: `test/unit/export-aggregate.test.ts` › "exports one Space identically however its stored objects were ordered", "writes every size width before height, however it was stored"; `test/unit/infinity-cube-cli.test.ts` › "canonicalizes a Resource file independently of document key insertion order"; `test/unit/missing-plugin-round-trip.test.ts` › "writes its content and Map content in one key order, whatever order the store answers".

## Rolling forward

- **ST-36** A format change rolls schema, fixtures, examples and tests forward in one change. There is no versioned reader, transitional key, alias, document migration or compatibility parser. *Why:* InfinityCube is unreleased and makes no compatibility promise for any copy outside the repository. An Aggregate directory is recovered from git or read with the build that wrote it, and a browser's stored copy of a mounted talk (ST-95, not built) may be unreadable after a deploy. **built**: `test/unit/import-aggregate.test.ts` › "refuses a version 2 space directory rather than migrating it".
- **ST-37** A file whose `version` this build does not read gets one refusal naming the version, not one per key. A Space-level `graphs` key gets its own refusal, because authors still write it by mistake. No other refusal names a key this build does not declare. *Why:* one clear sentence beats a refusal per key, and a refusal is for something someone can write now. **built**: `test/unit/read-single-space.test.ts` › "answers a version it cannot read once, ahead of every key that moved", "refuses a retired space-level graphs key rather than stripping it".
- **ST-38**: removed, see ST-24 (view or canvas keys and ids are undeclared keys).

## Reading a directory

- **ST-39** One reader reads a complete Aggregate, assets included, from a source that names itself, lists one directory (a missing one lists empty), reads one file (answering its bytes or why not) and states how many reads it allows at once. Neither source operation throws. The reader imports nothing from Node. *Why:* the CLI, Running, Export's read-back and Mounting read through one reader and refuse in the same words. **built**: `test/unit/read-aggregate.test.ts` › "reads aggregate.json first, then what the scan finds, in its order"; `test/unit/aggregate-package-browser-safe.test.ts` › "imports no Node builtin from any source module".
- **ST-40** The reader refuses a root with no `aggregate.json`, reads and parses `aggregate.json` before anything else and stops on a malformed one, and never has more reads in flight than its source allows. *Why:* a directory that is not an Aggregate fails fast. **built**: `test/unit/read-aggregate.test.ts` › "refuses a directory with no aggregate file, naming it", "reads nothing past a malformed aggregate.json", "never has more reads in flight than the source allows".
- **ST-41** The reader reports every directory it could not list, every file it could not read and every Space's diagnostics together, each under its path. *Why:* an author fixes everything in one pass. **built**: `test/unit/read-aggregate.test.ts` › "reports every unreadable Space together rather than stopping at the first", "reports every directory that could not be listed together, in ordinal order".

## HTTP

- **ST-73** The HTTP application is a Hono app on the Web Fetch model. It exports its route type for a typed client, validates every value crossing the network at runtime, and imports no Node builtin or Vite module. Hosts, asset serving and process lifecycle live in adapters. *Why:* one application runs in every host, a page included. **built**: `test/unit/http-node-builtin-restrictions.test.ts` › "restricts the node: prefix for every builtin, including the prefix-only ones"; `test/unit/vite-hono-host.test.ts` › "loads one Fetch application and serves its API through a real Node socket".
- **ST-74** The API is `GET /api/spaces` (listing), `GET /api/spaces/:id` (a working read), `GET /api/aggregate` (a complete read, which never initializes), `POST /api/spaces` (one commit), `POST /assets` and `GET /assets/:hash`. Nothing else is served: a method the contract does not serve is 405, and an undeclared path 404. A working read of a Space that does not exist is 404 `not-found`. Every answer but a stored asset carries `Cache-Control: no-store`. *Why:* one write door and lazy reads. **built**: `http/test/space-http-app.test.ts` › "retains collection listing and lazy resource loading", "loads the complete aggregate from its own resource", "refuses the retired PUT resource commit", "keeps invalid ids distinct from undeclared paths", "returns not found for an absent lazy resource"; `http/test/asset-http-app.test.ts` › "answers 405 for %s under %s, naming what is allowed".
- **ST-75** `POST /assets` takes the raw bytes as its body and admits any media type up to 10 MiB, counted as it arrives. The declared `Content-Type` is the media type, stored as its lower-case essence, and `application/octet-stream` when it is missing or invalid; bytes already stored keep the type they were first stored under. An encoded body is refused. It answers `{ url }` and `Location`, 201 when stored and 200 when the store already holds those bytes. Refusals: `unsupported-media-type` (415, for a content-encoded body) and `asset-too-large` (413). Which pictures an Image Resource stores is the Image plugin's rule, applied before storing (SR-63). *Why:* every plugin saves bytes the same way, and the store draws no line between text and binary. **built**: `http/test/asset-http-app.test.ts` › "admits %s under the declared media type, whatever it is", "answers the same URL for the same bytes, stores them once, and keeps the first type", "refuses a body over 10 MiB by counting what arrives, storing nothing", "stores an asset of exactly 10 MiB", "refuses an encoded body rather than storing the encoding"; `persistence/test/assets.test.ts` › "reads %j as %s".
- **ST-76** A stored asset's hash is the SHA-256 of its bytes as unpadded base64url, and its URL is `/assets/<hash>`. It is served there immutably cached, with `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`. Only PNG, JPEG, WebP and GIF are served under their own type; every other asset is served as `application/octet-stream`, so stored HTML or SVG never runs as a page of this origin. The stored type travels beside the served one, and the browser's asset client reads the bytes typed as they were stored. A malformed hash is 400 `invalid-asset-hash` and an absent asset 404; HEAD is served. The asset of zero bytes is always held, as `application/octet-stream`, and storing it writes nothing. Every repository is also the asset store, nothing deletes an asset from it, and neither lifecycle door touches it. *Why:* content addressing makes a URL permanent, and a store that admits anything must never serve active content. **built**: `persistence/test/assets.test.ts` › "is named by the SHA-256 of nothing", "serves %s as %s"; `http/test/asset-http-app.test.ts` › "serves %s as application/octet-stream, never as active content", "answers HEAD with the headers GET would carry", "answers 400 for a malformed hash whatever the method", "answers 404 for a well-formed hash nothing is stored at", "serves the asset of zero bytes though nothing stored it"; `http/test/asset-http-client.test.ts` › "reads an asset back under the media type it was stored as, whatever it is served as"; `test/support/repository-contract.ts` › "keeps stored assets outside the aggregate its lifecycle doors replace", "holds the asset of zero bytes already, under the type it always has".
- **ST-77** A commit request must be `application/json` in UTF-8 with no content encoding (else 415 `unsupported-media-type`) and at most 1 MiB, counted as it arrives; `Content-Length` is never trusted. An oversized body is 413 `payload-too-large`, read and discarded up to an allowance so the connection survives, and the connection is dropped past it. *Why:* a lying header must not smuggle a body, and an honest client keeps its connection. **built**: `http/test/space-http-app.test.ts` › "rejects a %s-encoded request body", "measures the body rather than trusting an over-declared length", "drains an oversized body that ends within the drain allowance", "stops draining a body that keeps arriving past the drain allowance".
- **ST-78** A commit outcome maps to one status, from one table both the application and the browser transport read: `committed` 200, `conflict` 409 (carrying the current values), `aggregate-refused` 422. A rejected commit is 400 `invalid-request`. *Why:* the two sides cannot disagree. **built**: `persistence/test/http-protocol.test.ts` › "gives every commit outcome a status of its own, and decodes each by it"; `http/test/space-http-app.test.ts` › "maps a rejected commit to request correction".
- **ST-79** Every HTTP error is RFC 9457 Problem Details (`application/problem+json`). Its `type` is a closed, stable identity; `title` and `detail` are prose no consumer branches on; optional `errors` carry codes and RFC 6901 pointers. The codec is strict and decoded once into the commit result; there is no other error shape. *Why:* errors cross seams as identities, never sentences. **built**: `persistence/test/http-protocol.test.ts` › "round trips every problem identity and an RFC 6901 whole-document pointer", "strictly rejects unknown problem types, fields, and malformed pointers", "rejects a Problem Details title or status that disagrees with its type".
- **ST-80** A stored-seam failure answers by what it is: an unreachable database 503 `persistence-unavailable`; broken stored state, or a failure nothing classifies, 500 `internal-error`. The reason goes to the log, never the response. *Why:* 503 promises the wait will help, which only an outage justifies. **built**: `http/test/space-http-app.test.ts` › "answers a commit failure that is neither named arm as 500 internal-error", "hides and logs aggregate repository failures"; `test/unit/vite-hono-host.test.ts` › "answers one invariant failure on the root with a 500 after one read".
- **ST-101** The browser's commit result is the repository's outcome plus the transport's own failures, retryable or permanent, and the transport classifies those failures itself. A Fetch rejection is a retryable `network` failure and a timeout a retryable `timeout`. `request-timeout` is `timeout`; `rate-limited` is retryable `rate-limited`; `persistence-unavailable` and `internal-error` are retryable `unavailable`, each carrying the delay when the response sends a valid `Retry-After`. `unauthorized` and `forbidden` are permanent `forbidden`, `invalid-request` permanent `invalid-commit`, `payload-too-large` permanent `payload-too-large`. Any other problem, a malformed body, a status that disagrees with its Problem Details, or an unexpected client error is a permanent `protocol` failure. *Why:* the repository and HTTP never decide what the session retries. **built**: `http/test/http-backend.test.ts` › "maps %s to retryable %s"; `test/unit/http-space-backend-failures.test.ts` › "maps Fetch rejection to a retryable network failure", "honours Retry-After on an unavailable response", "rejects malformed success and conflict bodies as permanent protocol failures", "maps unexpected client errors to permanent protocol failures".
- **ST-102** A commit result's failure arms carry a code (and a `Retry-After` where one applies) and no message. A `protocol` failure carries only a typed `ProtocolFault` naming the broken expectation, for diagnostics. A Problem Details `detail` is never passed on. How the application words each code is in editing.md. *Why:* errors cross the seam as identities, never sentences. **built**: `test/unit/http-space-backend-failures.test.ts` › "rejects malformed success and conflict bodies as permanent protocol failures"; `http/test/http-backend.test.ts` › "mints a distinct failure for each rejected commit".
- **ST-81** A server host answers a product URL with these statuses: a malformed URL is 400; a well-formed one that resolves to nothing (a canvas id, which product URLs do not carry, included) is 404, with Problem Details or the application's error surface; an existing one reaches the application. HEAD answers as GET does, with no body; any other method is 405. The destination table it resolves by is NV-80. *Why:* a web address has real HTTP semantics. **built**: `test/unit/vite-hono-host.test.ts` › "answers malformed and unresolved Space URLs before Vite fallback", "answers a removed canvas identity as not found", "resolves HEAD like GET while sending no product response body", "refuses a method the product contract does not serve".
- **ST-82** `/` redirects (302) to the Meta Space's canonical URL. With no Meta Space it answers 503 `persistence-unavailable`, saying none has been established, and creates nothing. The page side is NV-25. *Why:* 503 is the only status true of a healthy host with nothing to open yet. **built**: `test/unit/vite-hono-host.test.ts` › "redirects root to the compact Meta Space URL without a second read of it", "says why the root has nothing to redirect to yet".

## The working-space loader

- **ST-83** Every working read goes through the one initializing loader, wherever it runs: the HTTP application's single-Space route (on a server or in a mounted page), the Open Spaces composition, and the session registry's target reads. Which reads are working reads, and what initialization writes, are in maps-and-graphs.md (MG-74–MG-77). *Why:* one loader means one first working read, whichever path reaches a Space. **built**: `test/unit/app-http-startup.test.ts` › "initializes a mapless Space through an injected memory backend before opening it"; `test/unit/vite-hono-host.test.ts` › "mints working-load initialization from the identity source it was composed with"; `persistence/test/space-resource-lifecycle.test.ts` › "durably initializes a stored mapless target before the Resource that selects it exists".
- **ST-84** A first working read's initialization is an ordinary commit to the store the loader reads, so it persists across a fresh host. *Why:* initialization is durable like any Edit. **built**: `test/support/repository-contract.ts` › "persists first-working-load initialization for a fresh repository host".

## Mounting

- **ST-85** Mounting reads a complete Aggregate from a public GitHub location, `github:owner/repo@ref/path`, into a memory repository inside a static page, established through `initializeAggregate`. The page answers its own HTTP API through the same Space host, intake, commit decision and working-space loader as a server. *Why:* a talk can be shown with no server or database, and behaves as a Running one. **built**: `app/test/mount.test.tsx` › "opens the Meta Space with its Resources at the root, and moves the address to it".
- **ST-86** Only a mount composition reads an Aggregate or uses a lifecycle door in the browser; no other app module imports the reader. *Why:* ST-1 holds everywhere else. **built (untested)**: lint zone on `@project/aggregate` in `eslint.config.js`; `app/src/mount/`.
- **ST-87** GitHub is the only source, public repositories only, and no token is ever used. `ref` defaults to the default branch and `path` to the root; a ref runs to the next `/`. The location resolves to a commit once, in at most one call, and only the selected directory's tree is listed, in one call. A truncated tree is refused before anything is fetched. *Why:* the unauthenticated API allows few calls. **built**: `app/test/github-location.test.ts` › "ends a ref at the next slash, so a slashed branch is addressed by SHA or tag"; `app/test/github-source.test.ts` › "spends no call resolving a ref that is already a commit SHA", "lists only the selected directory's tree, by its path at the commit, in one call", "refuses a directory whose own tree is truncated".
- **ST-88** The selected directory must directly hold `aggregate.json` and bounds the Aggregate; nothing outside it is read. *Why:* a repository may hold several talks and other material. **built**: `app/test/github-source.test.ts` › "fetches only the selected aggregate's scanned files, relative to it"; `app/test/mount.test.tsx` › "shows a location whose directory holds no aggregate.json in the reader’s words".
- **ST-106** One static build serves every talk: a build-time setting may name a default GitHub location, the `source` query parameter overrides it, and with neither, or with one that is not a GitHub location, the page asks for a location. How `source` rides product URLs is in navigation.md. *Why:* one deployment per talk is a pinned default, not a separate build. **built**: `app/test/mount-source.test.ts` › "mounts the source parameter over the build-time default", "mounts the build-time default when the address has no source", "asks for a location when there is neither", "asks again, saying why, when the source parameter is not a GitHub location".
- **ST-89** The GitHub source fetches at most eight blobs at once. It retries a blob once when it answers 429 or 5xx or its fetch throws (honouring `Retry-After`), does not fetch a file listed over 25 MiB, and stops fetching once GitHub keeps throttling; each such file is reported as unreadable. Any 429, and a 403 with no requests remaining, a `Retry-After` or a secondary-rate-limit message, is a rate limit. *Why:* a talk must fail with a reason, not hang. **built**: `app/test/github-source.test.ts` › "fetches at most eight blobs at once", "waits the Retry-After seconds a throttled blob names before retrying it", "does not retry a blob that is not there", "does not fetch a file listed over 25 MiB, reporting its size, and fetches the rest", "reports every file read after GitHub went on throttling as not fetched", "answers a %d with no requests remaining as a rate limit".
- **ST-90** A mount refuses what the CLI refuses, in the same words: the reader's diagnostics and intake's. *Why:* one reader (ST-39). **built**: `app/test/mount.test.tsx` › "refuses a directory whose space.json is a symbolic link, as the CLI does", "shows Import’s diagnostics for an aggregate that is refused".
- **ST-91** The in-page application accepts writes as a server does: a mounted session's commits and stored assets go to the page's store. A plugin reads a mounted asset's bytes from that store, and every stored picture, the directory's and an uploaded one, is drawn from an object URL over its bytes, typed by the served-type rule (ST-76). *Why:* one behaviour wherever a talk is open. **built**: `app/test/mount.test.tsx` › "stores an uploaded asset in the page and draws it from an object URL over its bytes", "draws a stored image from an object URL over the mounted bytes", "reads a mounted asset from the in-page store, never through an object URL".
- **ST-92** Nothing a mounted page does writes to GitHub. *Why:* a page holds no token, and a page that could write would change the talk for everyone. **built (untested)**: `app/src/mount/github-source.ts` (reads only).
- **ST-93**: removed, see navigation.md NV-39 (a mounted page answers every address itself).
- **ST-94** The static build's Content Security Policy lets the page connect to GitHub (`api.github.com`, `raw.githubusercontent.com`) and nothing else beyond its own origin. It draws stored pictures from object URLs and an external Image URL from any https origin, and sends `nosniff` everywhere. *Why:* a page that mounts any public repository must fetch data from nowhere else. **built**: `app/test/mount-headers.test.ts` › "reaches GitHub, and only GitHub, beyond its own origin", "draws a mounted picture from an object URL, and an authored one from anywhere", "sends nosniff everywhere".
- **ST-95** A mounted talk keeps its Edits across reload in that browser: the page's store is an IndexedDB repository held to the shared contract (ST-4), deciding each commit in one transaction with the shared commit decision, one database per resolved repository, directory and commit, so a new commit starts clean. A mount opens an existing copy on `existing` or `already-initialized`. *Why:* a reader's changes survive a reload in their own browser. **not built**: `.scratch/mounting/issues/11-keep-mounted-edits-in-the-browser.md` (repo root). Today the page's store is memory and a reload loses its Edits: `app/test/mount.test.tsx` › "commits a write in the page, which a fresh mount of the same files does not hold".
- **ST-96** Discard local edits deletes the stored copy and mounts again from GitHub; other tabs of the scope reconnect to the new copy, and the revision floor never goes backwards. *Why:* the committed talk is always one step away. **not built**: as ST-95.
- **ST-97** Persistent browser storage is requested on the first Edit only, best effort, and never decides whether an Edit commits. *Why:* no prompt for a reader who only watches. **not built**: as ST-95.
- **ST-98** Two tabs of one scope are two sessions: a stale one meets an ordinary conflict, and nothing broadcasts between them. *Why:* the existing conflict handling covers it. **not built**: as ST-95.
- **ST-107** Nothing Exports an edited mounted talk out of the page. *Why:* saving somewhere durable is the author's `cube run` over their checkout. **built (untested)**: no export path in `app/src/mount/`.

## Effects across operations

- **Nothing writes an Aggregate directory except Export.** `init` and Running both write through Export, and Import, Mounting and opening a Space write nothing (ST-48, ST-51, ST-65). Exception: under Running, today's code Exports a first working read's initialization (ST-65, bug).
- **Every door applies the same intake.** File, stored document, HTTP, Import, Export's read-back, the lifecycle doors and Mounting all refuse the same shapes with the same identities. Exception: a stored Resource document strips an undeclared envelope key that a file refuses (ST-25).
- **Nothing initializes a Space but a working read.** Listing, the complete Aggregate read, Import, Export and the mount reader never do (MG-75). No exceptions.
