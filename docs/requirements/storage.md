**Terms** defined in [`CONTEXT.md`](../../CONTEXT.md) and used here: Aggregate, Space snapshot, Aggregate directory.

**Terms not yet in `CONTEXT.md`** (working definitions until the glossary carries them):
- **Asset**: bytes with a media type, named by the SHA-256 of those bytes, which a Resource reaches by the URL `/assets/<hash>`. Every file a Resource uses is an asset: a Markdown Resource's text, a Mermaid Resource's source and an Image Resource's stored picture are the ones written today. The **asset store** holds them; on disk each is `assets/<hash>.<ext>`.
- **Repository** (or **store**): where the live Aggregate is kept: PostgreSQL, SQLite or memory. A **lifecycle door** is one of its two whole-Aggregate operations, `initializeAggregate` and `replaceAggregate`.
- **Intake**: the validation every stored or imported Space and Aggregate passes before it loads.
- **Default Content**: the generated Aggregate a new repository, or `cube init`, starts from.
- **Source**: what the directory reader reads files from: the filesystem, files held in memory, or GitHub. A source names itself, lists one directory and reads one file.
- **Working read**: a read of one Space for authoring. The **working-space loader** answers it and runs the first working read (MG-74) when the Space needs one.
- **Import**, **Export**, **Running**, **Mounting**: reading an Aggregate directory into a repository; writing a repository's Aggregate to a directory; serving a directory through a memory store and Exporting back to it; reading an Aggregate from GitHub into a page.

**Status:** **built** means code and a named test match the rule. **built (untested)** means code matches and no test covers it. **not built** means the rule is decided and no code implements it. **bug: code differs** means the code does what the note says instead. **undecided (Sn)** means the rule waits on conflict Sn; the note says what the code does meanwhile. A test is named as `file` › "test name". Paths that start with `test/` are at the repo root; all others are under `packages/`. Tests in `test/support/repository-contract.ts` run once per repository, and their names begin with the repository's name, which is left out here. This document restates the accepted ADRs and decides nothing itself: each rule names its sources, and a rule that disagrees with an accepted ADR is a defect in this document, corrected here, never a reason to set the ADR aside. A rule sourced only from code and tests, an archived guide or a ruling in [DECISIONS.md](DECISIONS.md) says so.

## Data model: the Aggregate directory

| Path or key | Optional | Written by | Refused at intake when |
|---|---|---|---|
| `aggregate.json` `version` | no (`1`) | Export | any other version |
| `aggregate.json` `metaSpaceId` | no | Export | absent, or not a UUID |
| `<space-id>/` | — | Export | it holds `space.json` and its name is not a lower-case UUID |
| `space.json` `version` | no (`1`) | Export | any other version, as one refusal |
| `space.json` `id` | yes, in a hand-written file | Export | it contradicts the directory name |
| `space.json` `title`, `maps`, `defaultMap` | `maps`, `defaultMap`: yes | Export | see maps-and-graphs.md |
| Map `kind` | yes (`positioned`) | Export | any other kind |
| Map `positions`: the Map entries, keyed by Resource id, each `{ x, y, size?, content? }` | no, may be empty | Export | an entry naming no Resource, or an entry key it does not declare (maps-and-graphs.md MG-86) |
| Map `id`, Graph `id` | yes, in a hand-written file | Export | not a UUID |
| `resources/<id>.json` `id` | no | Export | absent, or not a UUID |
| `resources/<id>.json` `title`, `kind`, `content` | no | Export | ST-29–ST-31 |
| `assets/<hash>.<ext>` | yes | Export | not named for its bytes, over 10 MiB, or a second file of one hash |

Every object in `aggregate.json`, `space.json` and a Resource file's envelope rejects a key it does not declare (ST-24). Nothing else in a Space directory is read: a `*.md` file beside `space.json` or in `resources/` is the author's (ST-31).

## Repository

- **ST-1** The browser reaches stored Spaces only through `SpaceBackend` over HTTP. It names no file, path, database or storage, and no request can carry one. Mounting is the one exception (ST-86). *Why:* the browser must not depend on where Spaces are kept. Sources: ADR 0030, ADR 0132. **built (untested)**: `app/src/space.ts` (an `HttpSpaceBackend` is the default backend), lint zone on `@project/aggregate` in `eslint.config.js`.
- **ST-2** The stored seam offers a lazy single-Space read, a complete Aggregate read, a Space listing and one commit. The server's repository is a strict superset that adds the two lifecycle doors, `loadMetaSpaceId` and `markExported`; the browser-facing seam declares neither door. *Why:* establishment and replacement are administrative and must be unreachable from a page. Sources: ADR 0030, ADR 0078. **built**: `test/unit/space-resource-repository.test.ts` › "declares the server repository as a strict superset of the HTTP seam".
- **ST-3** PostgreSQL and SQLite share one Space repository implementation; each database supplies only its own small store of statements. *Why:* two repositories would drift in what they answer. Sources: ADR 0030, ADR 0095. **built**: `test/unit/space-resource-repository.test.ts` › "accepts the one SQL repository and the E2E repository without adapters".
- **ST-125** Both runtimes share one schema history per database, in two encodings: Prisma Next applies its migration packages in `migrations/app/` or `migrations-sqlite/app/`, and `sqlx` applies the plain-SQL files under `migrations-sql/postgres/` and `migrations-sql/sqlite/`, one per package and named for it, each holding the statements that package's operations execute, in its order (its prechecks and postchecks left out), as `sqlx`'s migrator reads them. Applied by `sqlx`, the files produce the schema Prisma Next produces, in the `public` schema on PostgreSQL and outside each tool's own bookkeeping tables on SQLite. A migration package's history is never rewritten, so a schema change adds a package and its file together. Rust takes ownership of the history when PostgreSQL moves to it (ADR 0155), and from then (rust-host 16) `sqlx` is the only migrator for both databases (ADR 0173): `infinity-cube migrate --store <postgres|sqlite>` applies the plain-SQL files, which are then the whole history, the Prisma Next packages and the two tests holding them equal are deleted, a database holding tables but no `_sqlx_migrations` is refused with a message saying to reset it, and CI holds the TypeScript runtime's Prisma Next contract to each migrated database with `prisma-next db verify --schema-only`, without `--strict`, which would fail on `_sqlx_migrations`. **not built** (rust-host 16). *Why:* both runtimes then produce the same schema; one migrator then keeps one record of what is applied, so neither tool's record is ever seeded from the other's (ADR 0173). Sources: ADR 0155, ADR 0165, ADR 0173. **built** (the two encodings, until rust-host 16): `test/unit/shared-migrations.test.ts` › "hold one plain-SQL file for each Prisma migration, in the same order", "hold %s as the statements Prisma executes" (each file holding its package's statements, none carrying a parameter); `crates/host/tests/shared_migrations.rs` › `given_a_sqlite_file`, `given_a_postgresql_server` (the schema each produces, compared; ignored by default, run by CI's `rust` job against PostgreSQL through Compose, on `compose.yaml`'s image). No Rust store applies them yet (rust-host 15, 16).
- **ST-4** Every repository (SQL and memory) passes one shared behavioural contract, the whole lifecycle included, and decides every commit with the one commit decision. A repository that answers differently is defective. *Why:* a Space must behave the same whichever store holds it. Sources: ADR 0078, ADR 0095, ADR 0096, ADR 0098. **built**: `test/unit/sql-fast-path-decision.test.ts` › "decides exactly what decideCommit decides, and hands every structural Edit to it"; `test/support/repository-contract.ts` (composed for each repository).
- **ST-5** In the SQL repository, a commit that is a single update keeping `defaultMap`, every Map and Graph id and which Map owns each Graph, the set of Resources and their kinds, and every Space Resource selection commits without waiting on other such commits (positions, Open, size, Shape, Edges, titles, content and Graph order all qualify). A commit that adds or removes a Space, Resource, Map or Graph, or changes `defaultMap` or a selection, waits until no other such commit or whole-Aggregate operation is running, and so do complete reads and the lifecycle doors. *Why:* ordinary editing must not queue behind the whole Aggregate. Sources: ADR 0078, ADR 0095. **built**: `test/unit/sql-fast-path-decision.test.ts` › "writes a Map-internal Edit to the Space other Spaces select into", "hands deleting a Graph another Space selects to decideCommit, which refuses it".
- **ST-6** A revision is a non-negative integer stored as canonical decimal text, at most 2^63−1, on every database and on the wire. A created Space lands at revision 0 and each update adds one. *Why:* a revision must never lose precision on its way through. Sources: ADR 0095. **built**: `test/support/repository-contract.ts` › "stores and commits a revision above Number.MAX_SAFE_INTEGER as canonical decimal text", "refuses to store a revision above the 2^63-1 ceiling"; `persistence/test/commit-decision.test.ts` › "lands a created Space at revision 0 with a null exportedRevision".
- **ST-7** A read that meets contradictory stored state (Spaces with no Meta identity, an Aggregate failing intake, a document that does not parse, a non-canonical revision) fails as an invariant failure, which HTTP answers as 500 `internal-error` (ST-80). It is never repaired on read. *Why:* broken stored state is a defect, and guessing would hide it. Sources: ADR 0078, ADR 0094. **built**: `test/support/repository-contract.ts` › "raises an identifiable invariant failure for a stored Space whose revision is not canonical"; `test/unit/database-startup.test.ts` › "fails explicitly on stored Spaces that no Meta identity names".
- **ST-100**: removed, see editing.md ED-1 (an Edit is a validated transition from one Space to the next; Editing owns that no Space value is edited in place).

## The SQLite host

- **ST-126** (2026-11-19) Every SQLite caller (the host, `cube import --store sqlite`, `cube export --store sqlite` and `pnpm dev:sqlite`) reads one file, named by `SQLITE_PATH`, and refuses to start when it is relative (`SQLITE_PATH must be an absolute path: <value>`) or when its parent directory is missing or unwritable. The host and the CLI also refuse an unset or blank `SQLITE_PATH` (`SQLITE_PATH must name the SQLite database file`); `pnpm dev:sqlite` instead uses the default file `.scratch/sqlite/infinity-cube.db` under the repository root, creating its parent directory, and hands that one absolute path to both its migration and its host. Migration alone, given a blank one, configures no database (`prisma-next.config.sqlite.ts` leaves `db` unset), so it migrates no file. From rust-host 16, `infinity-cube migrate --store sqlite` keeps the relative-path and parent rules, creates a missing file, and refuses a blank `SQLITE_PATH`, so it never answers success having migrated nothing (ADR 0173; **not built**). The CLI also refuses a file that does not exist, naming `pnpm db:migrate:sqlite`, and creates nothing there. `pnpm dev:sqlite` refuses before it migrates, and the host checks again at composition. *Why:* migration runs from the repository root and the host from `packages/app`, so a relative value would migrate one file and open another, and SQLite would otherwise create an empty unmigrated file and fail on a missing table. Sources: ADR 0095, ADR 0173; code and tests. **built**: `test/unit/prisma-sqlite-foundation.test.ts` › "applies the same absolute-path rule to every SQLite caller", "omits a database path when SQLITE_PATH is blank", "keeps the CLI existing-file rule separate from migration", "fails clearly when the SQLite parent directory is missing", "fails clearly when the SQLite parent directory is not writable"; `test/unit/sqlite-path-policy.test.ts` › "accepts a POSIX absolute path and refuses a relative one"; `test/unit/sqlite-dev-script.test.ts` › "reports as one line, and starts nothing, when SQLITE_PATH %s"; `test/integration/sqlite-http-runtime.test.ts` › "refuses to compose when SQLITE_PATH is %s", "refuses to compose when SQLITE_PATH is relative"; `test/integration/sqlite-infinity-cube-cli.test.ts` › "refuses to run without SQLITE_PATH naming a file", "refuses a SQLITE_PATH naming no file and creates nothing there"; the development default is untested: `scripts/dev-sqlite.ts`, `sqliteDevelopmentPath` in `src/sqlite/db.ts`.
- **ST-127** (2026-11-19) One InfinityCube process uses a SQLite file at a time. Inside it every repository operation is serialised, so overlapping Edits answer as on PostgreSQL: a stale revision is a conflict and nothing waits on SQLite. A second process on the live file, even one only reading, is unsupported: an operation meeting its lock fails at once, or waits out the driver's busy timeout synchronously, answering nothing else meanwhile, and then fails or succeeds as the other lock clears. A failure answers HTTP `503 persistence-unavailable`, which the browser retries, never `409`, and leaves no partial write or stuck lock. A network filesystem, a file shared between hosts and a hosted SQLite service are not supported. *Why:* SQLite locks the whole file, and the repository's one concurrency difference between databases is that queue (ADR 0095). Sources: ADR 0095; code and tests. **built**: `test/integration/sqlite-contention.test.ts` › "answers the loser of a same-Space race as a conflict and writes nothing of it", "fails ${operation} against a ${lock} lock as ${wait} BUSY, leaving the file unchanged and unlocked", "waits out a second process that lets go inside the busy timeout, then commits", "answers HTTP as retryable 503 persistence-unavailable inside the client timeout, never 409".
- **ST-128** (2026-11-19) The file is written with SQLite's rollback journal in `delete` mode and `synchronous=FULL`, the settings the driver's connections have, since nothing in `src/sqlite/` sets either; WAL is not enabled. A consistent copy is taken with the host and every other writer stopped, or with SQLite's backup API. *Why:* a copy of a file mid-transaction need not be a consistent database, and the copy advice holds only while these settings do, so a change to either changes this rule. Sources: code and tests (no ADR). **built**: `test/integration/sqlite-space-repository.test.ts` › "writes the file in rollback-journal delete mode with synchronous FULL".

## Meta lifecycle

- **ST-8** A repository is uninitialized when it holds no Spaces and no Meta identity. Nothing is inferred about Meta from order, count or topology: every complete Aggregate names its Meta Space. *Why:* the root is a stated fact, never a guess. Sources: ADR 0074, ADR 0078. **built**: `test/support/repository-contract.ts` › "initializes and replaces only through explicit Meta-rooted aggregates".
- **ST-9** `initializeAggregate` takes a complete Aggregate. It answers `initialized`, `existing` when the same Aggregate is already stored, or `already-initialized` when a different one is. Sameness compares authored meaning, not serialization or object-key order. Only one of two different concurrent initializations succeeds. *Why:* re-running an initialization must be harmless and never merge. Sources: ADR 0074, ADR 0078. **built**: `test/support/repository-contract.ts` › "classifies canonical and different initialization proposals", "ignores object-key insertion order when classifying initialization", "lets only one different concurrent initialization establish state".
- **ST-10** A database host initializes an uninitialized repository at start-up, from Default Content, and never reseeds an initialized one. While the database is unreachable it keeps retrying with a bounded back-off; it stops on a failure that a second attempt confirms no wait cures. *Why:* a fresh database opens on a Space, and an author's deletions are never undone. Sources: ADR 0018, ADR 0077, ADR 0124. **built**: `test/unit/database-startup.test.ts` › "initializes an uninitialized repository from Default Content", "answers the stored Meta identity without reseeding an initialized repository", "backs off, up to a bound it then holds", "stops at contradictory stored state that a second read confirms".
- **ST-11** Default Content is one deterministic generator, used by database start-up and `cube init`. What it generates is ordinary authored state: nothing protects, repairs or re-adds it, and deleting all of it never triggers a reseed. Which Aggregates are valid is in space-and-resources.md. Today it generates the ordinary new Space (see space-and-resources.md), titled `New space`. The Rust CLI's `init` has a generator of its own (`crates/host/src/init.rs`), `init_directory`, which takes the Meta Space's title: the CLI passes `New space` (`NEW_SPACE_TITLE`), and the desktop shell's New Space passes the name the person gave (ST-131); and `conformance/init/` holds the two to the same files for the same ids: `test/unit/init-conformance.test.ts` and `crates/host/tests/init.rs` › `given_a_missing_directory::writes_the_files_of_the_conformance_case_byte_for_byte`. *Why:* initialization and reset must not drift. Sources: ADR 0018, ADR 0077; ADR 0171 (the title `init_directory` takes). **built**: `test/unit/database-startup.test.ts` › "mints one complete Meta Space through the injected identity source", "answers the stored Meta identity without reseeding an initialized repository"; `test/unit/run.test.ts` › "writes a new aggregate to a %s directory, which a run then serves".
- **ST-99** Default Content will generate the release's starting Aggregate (its content is tracked in `.scratch/default-content/issues/01-generate-the-starter-content.md`, repo root), and a CLI hard reset rebuilds the repository from the same generator. The hard reset also clears the asset store; nothing else does. There is no merge-style seed command and no reset control in the browser. *Why:* a fresh install and a reset show the same thing. Sources: ADR 0077, ADR 0106. **not built**: as above; today `cube import <dir> --dangerous-replace` stands in for the reset, and it keeps the asset store.
- **ST-12** `replaceAggregate` deletes everything stored and writes the new Aggregate, in one step, whether or not the stored state is valid or even parses. *Why:* replacement is the way out of broken stored state. Sources: ADR 0030, ADR 0078, ADR 0094. **built**: `test/support/repository-contract.ts` › "replaces everything stored, freeing the Resource ids it clears"; `test/unit/import-aggregate.test.ts` › "truncates a stored aggregate that fails intake and imports in its place".
- **ST-13** Replacement is never unconditional. It must name the Meta Space id the operator saw, read without validating the rest (`loadMetaSpaceId`). If a different Meta id is stored when it writes, it conflicts and writes nothing. If none was stored when read, replacement may clear Spaces that have no Meta. *Why:* an operator must not replace an Aggregate they did not look at. Sources: ADR 0078, ADR 0094, ADR 0096. **built**: `test/support/repository-contract.ts` › "refuses a replacement authorized against a superseded Meta identity", "truncates stored Spaces without a Meta identity only when none was expected".
- **ST-14** Replacement answers `uninitialized` on an empty repository and never establishes first state; the caller then takes the initializing door. *Why:* each door does one thing. Sources: ADR 0078, ADR 0094, ADR 0096. **built**: `test/support/repository-contract.ts` › "refuses replacement before initialization"; `test/unit/import-aggregate.test.ts` › "initializes rather than replaces an empty repository under replace".
- **ST-15** Both lifecycle doors refuse an Aggregate that fails intake with structured refusals, before anything is deleted or stored. *Why:* a bad proposal must cost nothing. Sources: ADR 0078, ADR 0094. **built**: `test/support/repository-contract.ts` › "refuses an initialization that fails domain intake, storing none of it", "rolls back a refused replacement".

## Commits

- **ST-16** A commit is one non-empty change set. Each change creates a Space snapshot, updates one at its expected revision, or deletes one at its expected revision, and names a Space at most once, by its id in lower case. *Why:* a single Edit and a topology Edit use the same operation, and a Space's id is its directory's name, which Import reads only in lower case, so a Space created under an upper-case id would be exported where no later run could read it. Sources: archived guide `editing-and-persistence.md` (no ADR); code and tests for the lower-case id. **built**: `persistence/test/commit-decision.test.ts` › "refuses an empty change set", "refuses one Space named twice", "refuses a Space named in upper case, which Import could not read back"; `conformance/http/wire-cases.ts` › "answers 400 invalid-request for a Space named in upper case", which every host runs (the Rust host's port in `crates/http-conformance/src/cases.rs`, and its decision in `crates/host/src/commit/tests.rs` › `rejects_a_space_named_in_upper_case`).
- **ST-17** A commit has one outcome, named once for both sides of the seam: `committed` (every assigned revision and deleted id), `conflict` (every mismatched current value), or `aggregate-refused` (stable intake identities and locations). A malformed request is `rejected`. *Why:* both sides decode the same three answers. Sources: ADR 0098. **built**: `test/support/repository-contract.ts` › "reports every conflict and rolls back every refused aggregate", "answers a stale expected revision with the current aggregate".
- **ST-18** A candidate is accepted only if the whole resulting Aggregate passes intake; a refused commit stores nothing. Which Aggregates are valid is in space-and-resources.md. *Why:* no commit may leave the store inconsistent. Sources: archived guide `editing-and-persistence.md` (no ADR). **built**: `test/support/repository-contract.ts` › "refuses a commit that fails domain intake and stores nothing".
- **ST-19** Deleting a Space that a Space outside the commit still references is a conflict, not an aggregate refusal. A reference the commit itself submits is judged by intake and refused. *Why:* the caller's view of the other Space is stale, so it reloads rather than invents a revision. Sources: archived guide `editing-and-persistence.md` (no ADR). **built**: `test/support/repository-contract.ts` › "atomically creates, links, reads, converges on, and deletes a Space".
- **ST-20** A commit may not claim a Resource another Space owns. The store adds no check of Map or Graph ids across Spaces. Uniqueness itself is SR-6 (Spaces and Resources) and MG-2, MG-35 (Maps and Graphs). *Why:* only Spaces and Resources are looked up store-wide. Sources: ADR 0030. **built**: `test/support/repository-contract.ts` › "refuses a commit claiming a Resource another Space owns", "scopes Graph identities to their containing Space".
- **ST-21** A repository answers a Space's Resources in ascending id order, whatever the order they arrive in. The domain's own order is SR-10. *Why:* reads are deterministic. Sources: code and tests (no ADR). **built**: `test/support/repository-contract.ts` › "returns a Space's Resources in ascending id order however they were supplied".
- **ST-104** The commit decision forgives `ordinary-space-unreferenced` for a Space the stored Aggregate already left unreferenced, so the Edit that initializes a stored mapless target can commit on every repository. *Why:* an unrelated Edit must not be refused for a state it did not cause. ## Intake and strictness

- **ST-22** Every Space value is built by one intake that parses the space document and every Resource, validates references and indexes the result, whether it comes from files or from a stored snapshot. Nothing downstream takes a value that has only passed the schema. This holds within each runtime: TypeScript has `loadSpace`, and a Rust host has one `intake` crate of its own (ST-118), held to the same corpus by kind of refusal and where it is, not by wording (ADR 0156). Every JSON text intake reads, `aggregate.json`, a `space.json`, a Resource file and a commit body, is parsed by `parseJsonText` (`core`), which refuses a string, a key or a value at any depth, that escapes a lone UTF-16 surrogate as text that is not JSON: such a file is refused `invalid-json`, located at the file, and such a commit body as ST-77 says. *Why:* a Space is consistent and indexed by construction, and no string reaches a file or a store that UTF-8 cannot hold, or that the Rust intake would read differently. Sources: ADR 0010, ADR 0156, ADR 0160. **built**: `graph/test/space.test.ts` › "reports a bad shape as errors rather than throwing"; `graph/test/space-snapshot.test.ts` › "builds the validated indexed Space consumed by graph logic", "reports an invalid persistence shape without constructing a Space"; `core/test/json-text.test.ts` (a lone high or low surrogate, a pair written low then high, in a key, nested and at the root, and an escaped pair accepted); `conformance/intake/directory/invalid-json-lone-surrogate` (a Resource file's value) and `invalid-json-lone-surrogate-key` (an `aggregate.json` key).
- **ST-23** Intake does no I/O and is synchronous: Resource files are handed to it as an argument. *Why:* reading bytes is the shell's business, so intake runs anywhere. Sources: ADR 0020. **built (untested)**: `graph/src/space.ts` `loadSpace`.
- **ST-24** `aggregate.json`, the space document, a Map, a Map entry, a size, a Graph and an Edge each reject a key they do not declare, at every door: file, stored document, HTTP and intake. A Map entry declares `x`, `y`, `size` and `content`, so a retired `open`, `shape` or `openSize` key is refused like a misspelt one. *Why:* a stripped key is a question answered silently. Sources: ADR 0079, ADR 0104, ADR 0122, ADR 0127. **built**: `core/test/schema.test.ts` › "rejects an undeclared key rather than opening on a Map its author did not name", "rejects a key the map does not declare, rather than stripping it", "refuses a value JSON cannot carry, and the retired shape and open keys", "refuses the retired openSize", "refuses a Graph carrying a key the format does not declare, rather than stripping it", "refuses a key the Edge does not declare, rather than stripping it".
- **ST-25** A Resource file's envelope rejects an undeclared key. A stored Resource document, which is also what HTTP carries, strips one. Each listed plugin's `content` is strict at every door, parsed by that plugin's schema and nothing else; a kind no plugin in the build draws has its `content` carried unread (SR-62). *Why:* a file is hand-written and must say what it got wrong; the plugin's schema is the one parser of its content. Sources: ADR 0127, ADR 0128. **built**: `core/test/schema.test.ts` › "strips a key beside the stored envelope, and refuses one its kind's content does not declare"; `core/test/resource-document-equality.test.ts` › "refuses an unknown $kind content key at every door", "carries a kind no plugin draws whole at every door, its content unread (ADR 0142)".

## File format

- **ST-27** An Aggregate directory holds `aggregate.json` (`version` 1 and `metaSpaceId`, and no Space inventory), one directory per Space named by its lower-case UUID, and `assets/`. A Space is in the Aggregate because its directory is there. *Why:* one fact, one place. Sources: ADR 0136. **built**: `test/unit/aggregate-round-trip.test.ts` › "writes a versioned aggregate file naming the Meta Space, and one directory per Space"; `test/unit/read-aggregate.test.ts` › "refuses a Space directory whose name is its UUID in upper case".
- **ST-109** The root file is `aggregate.json` and nothing else: Import, Running, `check`, Export's read-back and a mount read no other name, so a directory holding only the earlier root file, `hyper.json`, is refused as one with no `aggregate.json`. Export into such a directory writes `aggregate.json` and leaves `hyper.json` alone, as it leaves every file it does not own (ST-56); the author renames or removes it with git. *Why:* the file is named for what it roots, so a later rename of the product does not touch the format, and reading two names would put a rule for one rename in every source. Sources: ADR 0136. **built**: `test/unit/read-aggregate.test.ts` › "refuses a directory with no aggregate file, naming it"; `test/unit/export-aggregate-in-place.test.ts` › "never touches what Import does not read". No test uses the earlier file's name.
- **ST-28** A Space directory holds `space.json` (`version`, `id`, `title`, `maps`, `defaultMap`) and `resources/`. The space file lists no Resources and has no Space-level `graphs`: a Map holds its Graphs, and a Graph's `edges` is required and may be empty. *Why:* the directory is the inventory. Sources: ADR 0020, ADR 0041. **built**: `core/test/schema.test.ts` › "holds no resources — a resource exists because its file does (ADR 0020)", "nests a Graph under the Map that owns it, with no Space-level collection", "accepts a graph with no edges — a Map mints its initial Graph empty".
- **ST-29** Each Resource is `resources/<id>.json` holding the envelope `{ id, title, kind, content }`, specified as JSON Schema in `docs/schema/resource/`. Its identity is the `id` inside, never the file name, and a duplicate id across files is refused naming both. *Why:* renaming a file is not an identity change. Sources: ADR 0020, ADR 0128, ADR 0142. **built**: `test/unit/aggregate-json-schema.test.ts` › "admits a valid Resource file through the whole of intake"; `graph/test/space.test.ts` › "rejects the same resource id in two files, naming both".
- **ST-30** `kind` is required, with no default: a file with no kind, or a malformed kind id, is refused. A well-formed kind that no plugin in this build draws is not refused: its Resource is read with its `content` whole (SR-62). The kind-id grammar is SR-17. *Why:* a missing kind must never quietly mean one, and one Resource whose plugin is absent must not make the whole Aggregate unreadable. Sources: ADR 0128, ADR 0142. **built**: `graph/test/resource-file.test.ts` › "refuses a file that declares no kind, with no Ur default (ADR 0128)", "refuses a malformed kind id, saying what a kind id is", "reads a well-formed kind id no plugin in this build draws, its content whole (ADR 0142)".
- **ST-31** A Resource keeps no file beside its Resource file: every file a Resource uses is an asset (ST-34), which its content names by URL. A Markdown Resource's content is `{ url }`, and its URL is `/assets/<hash>`; its text is a plain Markdown file with no frontmatter, held at `assets/<hash>.md` in an Aggregate directory, where `<hash>` is the last segment of the URL. A path locator, a media type, inline source and any other URL are refused. A new Markdown Resource names the asset of zero bytes, which needs no file. A Markdown asset the directory does not hold is not refused. A `*.md` file in a Space directory or its `resources/` is not read, and Export leaves it alone. *Why:* a Markdown file and a picture are the same thing to the host, and one way of holding bytes is enough. Sources: ADR 0128, ADR 0142. **built**: `core/test/schema.test.ts` › "reads a Markdown Resource file as the URL of the asset holding its text (ADR 0142)", "refuses a Markdown Resource file that carries its source, a sidecar or an outside URL"; `graph/test/resource-file.test.ts` › "refuses a sidecar locator, an inline source, or a URL outside the asset store"; `test/unit/run.test.ts` › "writes a Markdown Resource as its Resource file and its text as an asset, and removes both on delete"; `test/unit/export-aggregate-in-place.test.ts` › "never touches what Import does not read".
- **ST-32** Resources are found only directly in `resources/`, and Space directories only directly in the Aggregate directory. *Why:* nested Spaces may later want subdirectories, which a recursive scan would make ambiguous. Sources: archived guide `editing-and-persistence.md` (no ADR). **built**: `test/unit/read-single-space.test.ts` › "reads a space-file or directory input with globally sorted, non-recursive resources"; `test/unit/read-aggregate.test.ts` › "does not descend past the immediate children".
- **ST-33** A Map stores `kind: 'positioned'`, the only kind. A hand-written Map may leave it out; any other kind is refused. *Why:* a second kind can be added without a migration, and a hand-written Map stays short. Sources: code and tests (no ADR). **built**: `core/test/schema.test.ts` › "defaults a map with no kind to positioned, so one can be hand-written", "rejects a map kind it does not know".
- **ST-34** A stored asset is `assets/<hash>.<ext>`, where `<hash>` is the SHA-256 of its bytes as 43 characters of unpadded base64url, also the last segment of its URL. The extension gives its media type through one table, and any other extension, or none, is `application/octet-stream`; Mermaid source is `mmd`, `text/vnd.mermaid`. Export keeps the name of a file already there, and names a new one by the table, `.bin` for a type the table does not list. One asset is written once however many Resources reference it. *Why:* the name proves the bytes. Sources: ADR 0118, ADR 0142, ADR 0158. **built**: `test/unit/aggregate-round-trip.test.ts` › "stores one file for two Resources showing the same picture", "keeps each asset file name and media type through Import then Export", "carries a listed media type through Export then Import, and an unlisted one as octet-stream"; `test/unit/export-aggregate.test.ts` › "keeps the name an asset has in the directory, so its extension survives"; `persistence/test/assets.test.ts` › "maps .%s to %s", "writes %s with .%s".
- **ST-35** One directory format serves every store: the same Aggregate Exports to the same bytes whichever store held it and however its objects were ordered. Sizes are written width before height and Resource file keys in envelope order. Every Map content, and the `content` of a Resource whose kind no plugin draws, is written with its keys sorted at every depth. An asset is written as the bytes the store holds. *Why:* a directory is reviewed in git. Sources: ADR 0118, ADR 0142. **built**: `test/unit/export-aggregate.test.ts` › "exports one Space identically however its stored objects were ordered", "writes every size width before height, however it was stored"; `test/unit/infinity-cube-cli.test.ts` › "canonicalizes a Resource file independently of document key insertion order"; `test/unit/missing-plugin-round-trip.test.ts` › "writes its content and Map content in one key order, whatever order the store answers".

## Rolling forward

- **ST-36** A format change rolls schema, fixtures, examples and tests forward in one change. There is no versioned reader, transitional key, alias, document migration or compatibility parser. *Why:* InfinityCube is unreleased and makes no compatibility promise for any copy outside the repository. A preview build is such a copy and does not end the unreleased state. - **ST-37** A file whose `version` this build does not read gets one refusal naming the version, not one per key. A Space-level `graphs` key gets its own refusal, because authors still write it by mistake. No other refusal names a key this build does not declare. *Why:* one clear sentence beats a refusal per key, and a refusal is for something someone can write now. Sources: ADR 0056. **built**: `test/unit/read-single-space.test.ts` › "answers a version it cannot read once, ahead of every key that moved", "refuses a retired space-level graphs key rather than stripping it".
- **ST-38**: removed, see ST-24 (view or canvas keys and ids are undeclared keys).

## Reading a directory

- **ST-39** One reader reads a complete Aggregate, assets included, from a source that names itself, lists one directory (a missing one lists empty), reads one file (answering its bytes or why not) and states how many reads it allows at once. Neither source operation throws. The reader imports nothing from Node. *Why:* the CLI, Running, Export's read-back and Mounting read through one reader and refuse in the same words. A Rust host's reader agrees with it on the kind of refusal and where it is, not on the words (ADR 0156). Sources: ADR 0130, ADR 0133, ADR 0156. **built**: `test/unit/read-aggregate.test.ts` › "reads aggregate.json first, then what the scan finds, in its order"; `test/unit/aggregate-package-browser-safe.test.ts` › "imports no Node builtin from any source module".
- **ST-40** The reader refuses a root with no `aggregate.json`, reads and parses `aggregate.json` before anything else and stops on a malformed one, and never has more reads in flight than its source allows. *Why:* a directory that is not an Aggregate fails fast. Sources: ADR 0133, ADR 0136. **built**: `test/unit/read-aggregate.test.ts` › "refuses a directory with no aggregate file, naming it", "reads nothing past a malformed aggregate.json", "never has more reads in flight than the source allows".
- **ST-41** The reader reports every directory it could not list, every file it could not read and every Space's diagnostics together, each under its path. *Why:* an author fixes everything in one pass. Sources: ADR 0133. **built**: `test/unit/read-aggregate.test.ts` › "reports every unreadable Space together rather than stopping at the first", "reports every directory that could not be listed together, in ordinal order".
- **ST-42** A path InfinityCube owns is never a symbolic link: `aggregate.json`, `assets/` and its files named by a hash, each root directory named for a Space id, and in each Space directory `space.json`, `resources/` and its `*.json`. A link there is a discovery failure naming the path, all reported together. A link InfinityCube does not own is neither read nor refused. Every source lists a link as a link. *Why:* a directory that imports must be one Export can write back. Sources: ADR 0119, ADR 0134, ADR 0136, ADR 0142. **built**: `test/unit/read-aggregate.test.ts` › "refuses every owned link together, in the order Importing reads them", "leaves a link InfinityCube does not own to the author", "refuses the same link from a source over files in memory".
- **ST-43** A source keeps its own reach policy (concurrency, retries, size limits); a fetch it gives up on is a file that could not be read. *Why:* the reader stays one thing. Sources: ADR 0133. **built**: `app/test/github-source.test.ts` › "reports a blob that still fails after its one retry as unreadable, with its status".
- **ST-44** Reading mints the Space, Map and Graph ids a hand-written directory leaves out, in directory order however reads complete; it takes a Space's id from its directory name and refuses a `space.json` id that contradicts it. A Resource file's id is never minted. *Why:* ids are optional only in hand-written input, and minting is deterministic. Sources: ADR 0030, ADR 0041, ADR 0109. **built**: `test/unit/read-aggregate.test.ts` › "mints the Map and Graph ids a hand-authored Space leaves out, and keeps its Resources' own", "mints in ordinal directory order however the reads complete", "refuses a space file that declares an identity its directory contradicts", "refuses a Resource file that leaves out its id rather than minting one".

## Import

- **ST-45** Import reads one complete Aggregate directory and finishes all file validation before it reaches the repository. *Why:* a refused directory touches nothing. Sources: ADR 0030, ADR 0117. **built**: `test/unit/import-aggregate.test.ts` › "finishes file validation before calling the repository".
- **ST-46** Without `--dangerous-replace`, Import initializes an empty repository, answers unchanged when the repository already holds exactly this Aggregate, and otherwise refuses, leaving storage alone and naming the flag. *Why:* replacing an author's work is never a default. Sources: ADR 0030, ADR 0094, ADR 0124. **built**: `test/unit/import-aggregate.test.ts` › "initializes an empty repository through the initializing door", "answers unchanged when the repository already holds exactly this aggregate"; `test/unit/infinity-cube-cli.test.ts` › "refuses to import over an initialized repository, naming the flag that would proceed".
- **ST-47** Import never runs a working read (MG-75), so it never initializes a mapless Space. *Why:* importing is not opening. Sources: ADR 0079. **built**: `test/unit/infinity-cube-cli.test.ts` › "does not load a successfully imported Space"; `test/unit/aggregate-round-trip.test.ts` › "round-trips unchanged, initialized by neither export nor import".
- **ST-48** Import never rewrites the files it reads. *Why:* Export is the only way back to files. Sources: ADR 0079. **built**: `test/unit/run.test.ts` › "leaves the directory byte-for-byte unchanged when nothing is edited".
- **ST-49** Import admits every file directly in `assets/` named by a hash, alone or followed by a dot and any extension, whatever its media type, typed by its extension (ST-34), and stores them before either lifecycle door runs, whether or not a Resource references them. A file over 10 MiB, one not named for its own bytes, or two files of one hash refuse the directory. A file whose name is not a hash, a dotfile and a subdirectory in `assets/` are the author's. An asset reference whose bytes the directory lacks is not refused. Assets stored by an Import that is then refused stay stored. *Why:* the store is outside the Aggregate's revision. Sources: ADR 0118. **built**: `test/unit/import-aggregate.test.ts` › "admits every asset in assets/ before the aggregate is stored, referenced or not", "admits a file named by its hash alone as application/octet-stream", "does not refuse an asset URL whose bytes the directory does not carry", "leaves alone what in assets/ is not named by a hash", "refuses an asset file not named for its content, before storing anything", "refuses two files of one hash, naming both, before storing anything". The size cap and the refused-Import clause are untested.
- **ST-50** Seeds, fixtures and tests reach the store through the same Import and lifecycle doors. The fixture importer also refuses an asset reference its own `assets/` does not carry. *Why:* one path in. Sources: ADR 0030, ADR 0078, ADR 0106, ADR 0118. **built**: `test/unit/tracked-fixture-aggregate.test.ts` › "imports as a complete Meta-rooted aggregate through the production importer", "refuses to seed a fixture naming a stored image no tracked file produces".

## Export

- **ST-51** Export writes one repository's complete Aggregate, never one Space, and only from the CLI or Running; no page saves files. An uninitialized repository writes nothing. *Why:* the Aggregate is the unit that reads back. Sources: ADR 0030. **built**: `test/unit/export-aggregate.test.ts` › "writes nothing and answers uninitialized when the repository holds no aggregate".
- **ST-52** Export writes fully identified, canonical files: every id written, deterministic bytes that re-enter through intake. Re-Exporting over its own output changes no byte. *Why:* a re-export is reviewable as a diff. Sources: ADR 0030, ADR 0041. **built**: `test/unit/infinity-cube-cli.test.ts` › "writes deterministic fully identified files that re-enter through version 1 intake"; `test/unit/aggregate-round-trip.test.ts` › "re-exports over its own output without changing a byte".
- **ST-105** A Space Resource's selection and framing survive Export and Import unchanged. *Why:* a selection is authored and must round-trip. Sources: archived guide `editing-and-persistence.md` (no ADR). **built**: `test/unit/aggregate-round-trip.test.ts` › "preserves every selected Map and Graph, and the framing, on a Space Resource".
- **ST-53** Before writing anything, Export computes the complete set of files and checks in memory that Import would read them back as a valid Aggregate. If not, it answers `would-not-read-back` and writes nothing. *Why:* Export must never write what Import refuses. Sources: ADR 0119. **built**: `test/unit/export-aggregate-in-place.test.ts` › "writes nothing when the files would not read back as a valid aggregate".
- **ST-54** Export refuses a destination holding a `space.json` in a directory whose name is not a lower-case UUID, as Import would. A directory with no `space.json` is the author's and is left alone, whatever its name. *Why:* Export owns only what Import reads. Sources: archived guide `editing-and-persistence.md` (no ADR). **built**: `test/unit/export-aggregate.test.ts` › "refuses a destination holding a Space directory import could not read back", "leaves a UUID-shaped directory no export could have written", "leaves a UUID-named directory that holds no space.json"; `test/unit/read-aggregate.test.ts` › "refuses a Space directory whose name is its UUID in upper case".
- **ST-55** Every Export writes in place. It creates a missing destination, never moves or recreates the destination or a Space directory, skips each file whose bytes already match, and replaces each other one through a fresh dot-prefixed temporary file renamed over it. *Why:* the directory is the author's checkout, and git holds what a backup would. Sources: ADR 0119. **built**: `test/unit/export-aggregate-in-place.test.ts` › "keeps the destination and each Space directory, and stages nothing beside them", "leaves a file whose bytes are unchanged exactly as it was"; `test/unit/infinity-cube-cli.test.ts` › "exports the stored aggregate to the canonical version 1 directory".
- **ST-56** Export owns exactly the files Import's scan finds. It removes those the Aggregate no longer serializes to, then any directory that leaves empty, and never reads or touches anything else. A removed Space's directory loses only owned files. *Why:* an author's notes beside an Aggregate are theirs. Sources: ADR 0119, ADR 0133, ADR 0136, ADR 0142. **built**: `test/unit/export-aggregate-in-place.test.ts` › "removes a deleted Resource's own files and nothing else", "never touches what Import does not read"; `test/unit/aggregate-round-trip.test.ts` › "removes the directory of a Space the aggregate no longer holds".
- **ST-57** Export never writes or removes through a symbolic link, and checks again for one at write time. Another process that swaps a directory for a link between that check and a write or removal is out of scope: it needs write access to the directory already, and the run's directory lock (ST-124) keeps a second InfinityCube run off it. *Why:* a link could point outside the directory. Sources: ADR 0119, ADR 0134. **built**: `test/unit/export-aggregate-in-place.test.ts` › "refuses to remove files through a linked resources directory", "refuses to remove assets through a linked assets directory", "never writes through a link left where a temporary file would go".
- **ST-58** A write that fails part-way leaves a mix of new and old files, reports it, and records nothing; git restores the directory. *Why:* whole-write atomicity costs more than git already gives. Sources: ADR 0119. **built**: `test/unit/infinity-cube-cli.test.ts` › "reports a write that fails part-way, records nothing, and leaves the files it did not reach".
- **ST-59** Export records, per Space, the revision it projected, and only after every file is written. A commit that lands during the Export does not move what is recorded. *Why:* a revision recorded against bytes that did not land cannot be recovered. Sources: ADR 0030, ADR 0119. **built**: `test/unit/aggregate-round-trip.test.ts` › "records the revision of every Space, after every file is written"; `test/unit/infinity-cube-cli.test.ts` › "marks the projected revision when a newer edit commits during export".
- **ST-103** Whether a Space has changed since its last Export is derived only from revisions the repository has acknowledged, compared with the exported revision it recorded. *Why:* an unacknowledged local Edit is not yet stored, so it cannot be unexported. Sources: code and tests (no ADR). **built**: `persistence/test/session.test.ts` › "derives export status only from acknowledged durable revisions", "derives export status from the returned durable state while conflicted".
- **ST-60** Export writes the bytes of every stored asset the Aggregate references and owns the files in `assets/` named by a hash: one no Resource references is removed, and an emptied `assets/` with it. A reference is a whole string value of exactly `/assets/<hash>` anywhere in a Resource's `content` or a Map entry's Map content, found without naming a kind, so the assets of a Resource whose kind no plugin draws travel too. A reference written inside another asset's bytes is not found. A file of a referenced asset whose bytes the store does not hold is kept, and the asset of zero bytes needs no file. *Why:* a directory carries what it needs and nothing stale. Sources: ADR 0106, ADR 0118, ADR 0142. **built**: `test/unit/export-aggregate.test.ts` › "rewrites assets whole, so an asset no Resource references leaves the directory", "carries the text and binary assets a Resource of another kind references, and not after", "keeps what Import does not own inside assets/", "completes and removes no file of the name of a referenced asset whose bytes are absent", "writes no file for the asset of zero bytes, which needs none"; `test/unit/referenced-asset-hashes.test.ts` › "are found in Map content as in Resource content, once each, in ordinal order". That a reference inside an asset's bytes is not carried is untested.
- **ST-61** An external URL, and an asset URL whose bytes the store does not hold, Export as the URL only, and the Export still completes. *Why:* bytes InfinityCube does not hold are not the repository's. Sources: ADR 0106, ADR 0118. **built**: `test/unit/export-aggregate.test.ts` › "exports an external URL and an asset URL whose bytes are absent as URLs only".

## Running

The Rust CLI's `infinity-cube run` runs a directory by these rules too (ST-120).

- **ST-62** `cube run <dir>` Imports the directory into a fresh memory store, serves the application from it, and discards the store when it stops. Running always uses the memory store, and a database host never Imports or Exports a directory. While it runs, the directory is the durable copy. *Why:* an Aggregate on disk can be edited without a database. Sources: ADR 0030, ADR 0117. **built**: `test/unit/run.test.ts` › "serves the directory it was started on".
- **ST-63** Running Exports once edits have been quiet for about a second, and on SIGINT, SIGTERM or SIGHUP, waiting for the write, then exits zero, or non-zero if that write failed. A second signal exits at once, non-zero. A failed write is tried again after another quiet period. The desktop sidecar also stops this way when its standard input closes (ST-116). The desktop shell, which serves the Rust host in its own process (ST-121), waits for the write when a window or the application closes, asking after ten seconds whether to keep waiting or close without saving (ST-122). *Why:* a crash loses at most the last second, and stopping never loses an edit. Sources: ADR 0117. **built**: `test/unit/run.test.ts` › "waits for quiet: an edit inside the period restarts it", "flushes a pending edit when stopped, and waits for the write", "tries a failed write again once another quiet period passes"; `test/integration/run-command.test.ts` › "exits at once, non-zero, on a second SIGINT while it is stopping".
- **ST-64** Writes are serialized: any number of edits during one write cause exactly one further write. A run with no edit leaves the directory byte-for-byte unchanged, beside the empty lock file it creates there (ST-124). *Why:* the directory changes only because the author changed something. Sources: ADR 0117, ADR 0162. **built**: `test/unit/run.test.ts` › "serialises writes: edits during a write cause exactly one further write", "leaves the directory byte-for-byte unchanged when nothing is edited, beside its empty lock file".
- **ST-65** Opening a Space never writes the directory: under Running, the first working read's initialization (MG-74) does not trigger an Export. The initialization is still committed to the memory store as ST-84 requires, and the next Edit's Export writes it; a run that ends with no Edit leaves the directory as it was, so the next run initializes again. *Why:* only an author's Edit should change their files. Sources: ADR 0080, ADR 0117; `DECISIONS.md` ruling 3. **built**: a commit made while answering a read (`GET`, `HEAD` or a product address) is not an Edit and schedules no Export (`src/run/run.ts` `readsMarked`); `test/unit/run.test.ts` › "writes nothing when opening a Space initializes it and nothing is edited (ST-65)", "writes the initialization with the next Edit (ST-65)", "initializes a Space with no Map when it is read, and writes those same ids with the next Edit (ST-65)"; at the wire, `conformance/http/process-cases.ts` › "leaves the directory byte for byte unchanged when opening a Space initializes it (ST-65)", "writes the initialization with the next Edit (ST-65)", run against the production Node host by `test/integration/http-conformance.test.ts`.
- **ST-66** Git answers for history, undo and a writer that is not a run (an author's editor, `cube mcp`, a `git pull`): Running keeps no fingerprint, on-disk change detection or merge, and its last write wins. Two runs of one directory are refused instead (ST-124). *Why:* the author's directory is already under version control. Sources: ADR 0117, ADR 0162. **built (untested)**: `src/run/run.ts`.
- **ST-124** Every host that runs a directory, `cube run`, the desktop sidecar, the Rust CLI's `run` and the desktop shell, holds a lock on it from before Import reads it until its last write has landed or failed, or until Import refuses the directory, and a run of a directory another run holds, in that process or another, in either runtime, is refused with the kind `locked`: `cube run` and `infinity-cube run` exit 1 naming the directory and saying to stop the other run, the sidecar announces the refusal, and the desktop shell shows it in its refusal dialog, naming no command. The lock is SQLite's exclusive lock on the empty file `.infinity-cube.lock` in the directory, taken with no busy timeout by an exclusive transaction never committed (`node:sqlite` in `src/run/directory-lock.ts`, `rusqlite` in `crates/host/src/lock.rs`), and the operating system releases it when the process ends, however it ends. A missing or empty directory is refused before any lock, so no lock file is created there; a directory Import refuses keeps the file. The file is never deleted; it is a dot-entry, and Import, `check` and Export read and write only the names Import owns, so none of them opens it. A content repository should ignore it (`.infinity-cube.lock` in its `.gitignore`); nothing InfinityCube writes adds that entry, and the README and the `infinity-cube-getting-started` skill tell the person to add it. A lock that cannot be taken for another reason stops the run as any failure to start does. `check`, `mcp`, `init`, `import` and `export` take no lock. On a network filesystem the lock is as good as its advisory locking. *Why:* two runs of one directory each Export over the other, losing Edits with nothing said; a lock the kernel releases leaves nothing stale behind a crash. Sources: ADR 0162. **built**: `test/unit/run.test.ts` › "refuses a second run of a directory a run holds, and runs it once the first has stopped", "runs another directory while one is held", "holds the lock until the last write has landed", "keeps its lock file out of what Import, Export and check read and write", "refuses a %s directory before locking it, creating no lock file"; `test/integration/run-command.test.ts` › "refuses a second run of the directory a run holds, naming it, and runs it once the holder is killed"; `test/integration/desktop-sidecar.test.ts` › "announces a refusal naming a directory another sidecar holds, and runs it once that one is killed"; `crates/host/tests/run.rs` › `given_a_directory_a_run_holds`, `given_an_empty_directory::refuses_to_start`; `crates/cli/tests/run.rs` › `given_a_directory_another_run_holds`, and across runtimes `given_a_directory_a_node_run_holds` and `given_a_directory_this_binary_runs`, which take the TypeScript lock with Node through `src/run/directory-lock.ts` itself (Linux in CI; the file is Unix-only); `packages/desktop/src-tauri/src/server/tests.rs` › `given_a_folder_another_run_holds`. Release when Import refuses the directory is **built (untested)**: `src/run/run.ts` releases the lock before it answers Import's refusal, and in Rust the lock `RunBuilder::start` takes (`crates/host/src/run.rs`) is dropped when it returns Import's refusal; no test runs a directory again after Import refused it. On Windows the lock is compiled by the `rust-windows` job and its Rust tests run there, but no test runs Node beside it; macOS is not run. On Linux under Xvfb, by hand (issue 13's Evidence), the desktop application holding a folder refused a second process of the application in its dialog, opening no Space window, and `infinity-cube run` with exit 1, was refused by a CLI run holding it, and opened it once the holder had exited.
- **ST-67** Running refuses, non-zero and serving nothing, a missing or empty directory (dot-entries do not count), naming `cube init`; a single Space directory with no `aggregate.json`; and a directory intake refuses, listing its errors. *Why:* Running never invents an Aggregate. Sources: ADR 0117, ADR 0124, ADR 0136. **built**: `test/unit/run.test.ts` › "refuses a %s directory as holding no aggregate, and writes nothing", "refuses a single Space directory, naming the missing aggregate file", "refuses a directory the aggregate intake refuses, with its errors"; `test/unit/run-process.test.ts` › "names init, with the directory as one shell word, for a missing or empty directory".

## The desktop sidecar

The desktop sidecar (`src/desktop/`) is the production Node host: a run served without Vite, built by `pnpm desktop-sidecar:build`. The desktop shell does not run it (it serves the Rust host, ST-121); the sidecar is the host the HTTP conformance suite holds every other host to, and the one the standalone HTTP host tickets adopt.

- **ST-113** `desktop-sidecar <dir> <built-app-dir>` starts a run of `<dir>` as Running does (ST-62), refusing what Running refuses on starting (ST-67) and a directory another run holds (ST-124), and serves it with the built application in `<built-app-dir>`. It listens on `127.0.0.1` only, at a port the system picks, and writes exactly one JSON line to standard output: `{"kind":"listening","port":…,"secret":…}` once it can be reached, or `{"kind":"refused","message":…}`, exiting non-zero once the whole line is written, when the directory cannot be run. For a missing or empty directory the message names no command, since a presenter has no `pnpm cube init`. A built application with no `index.html` inside it, an `index.html` that is a link out of it included, is refused the same way, before the directory is read; every built file is read only from inside it, as ST-119 reads it. Everything else goes to standard error. *Why:* the shell learns the address and the secret, or why not, from one line it can parse. Sources: ADR 0155; code and tests. **built**: `test/integration/desktop-sidecar.test.ts` › "announces a refusal and exits non-zero for a directory it cannot run", "announces a refusal and exits non-zero when the built page is a link out of the build", "announces the whole of a refusal larger than a pipe holds before exiting", "writes an edit to the directory and exits zero when its standard input closes"; `The desktop sidecar bundle` › "writes an edit to the directory and exits zero when its standard input closes" runs the bundle `desktop-sidecar:build` writes.
- **ST-114** Every request must name the sidecar's own `Host`, `127.0.0.1:<port>`, or it is refused 421 before anything else. `/?launch=<secret>` with the secret minted at launch answers 302 to `/`, setting a session cookie `HttpOnly; SameSite=Strict; Path=/` whose name carries the port; with any other secret it is refused 403 and sets no cookie. Every other request without that cookie holding the secret is refused 403. These refusals are plain text, `no-store`, and belong to the sidecar alone: they guard a loopback port, which the desktop shell's custom URI scheme does not have, so the shell makes none of them (ST-121, ADR 0155). *Why:* any program on the machine, and any web page through DNS rebinding, can reach a loopback port, and the HTTP application has no authentication; a webview keeps one cookie store for every window and scopes a cookie by host, not port, so a cookie named for its port keeps two Aggregates' sessions apart. Sources: ADR 0155; code and tests. **built**: `test/unit/desktop-handler.test.ts` › "refuses a request naming any other Host, before anything else", "refuses a request without the session cookie, or with the wrong one", "trades the launch secret for an HttpOnly, SameSite=Strict session cookie", "refuses a launch link carrying another secret, and sets no cookie", "keeps each window’s session when two Aggregates share one cookie store"; at the wire, `conformance/http/process-cases.ts` › "answers 421 to a request naming any Host but its own", "answers 403 to a request without the session cookie, and to a wrong launch secret", "trades the launch secret for an HttpOnly, SameSite=Strict session cookie by a redirect", run against the production Node host by `test/integration/http-conformance.test.ts`.
- **ST-115** Past the lock-down (ST-114), the API and the asset paths (ST-74) go to the Fetch application, and a product address to product resolution (ST-81, ST-82). Any other request that is not GET or HEAD is 405 with `Allow: GET, HEAD`. A read of a file the build holds serves it with `nosniff`, cached `public, max-age=31536000, immutable` under `/assets/`, where the build names every file by its content, and `no-cache` elsewhere. Any other request under `/assets/` goes to the Fetch application, which answers a malformed hash 400 `invalid-asset-hash` (ST-76). Any other read, a path the build does not hold included, and `index.html` itself however its path is spelled, is the single-page fallback: the built `index.html` with `nosniff`, `no-store` and a Content Security Policy that is Mounting's (ST-94) without the GitHub hosts, admitting each inline script by its hash. This routing, fallback, caching and policy are the rule a host serving the built application meets; the Vite development host leaves the paths it does not serve to Vite. *Why:* the window's page fetches from its own origin only, and a content-named file never changes. Sources: ADR 0155; code and tests. **built**: `test/unit/desktop-handler.test.ts` › "answers the API from the run", "answers the root address with the run’s product answer, a redirect to a Space", "serves the page, with its Content Security Policy, for a product address that resolves", "serves a built file as itself, cached for good", "answers %s of an asset path the build does not hold as the Fetch application does: 400 invalid-asset-hash (ST-76)", "answers a path the build does not hold with the page", `conformance/http/wire-cases.ts` › "serves the shell, with its policy, at %s" (`/index.html`, escaped and in upper case, which every host runs, the Rust host by `crates/host/tests/wire.rs`), "refuses a write to a path that is neither the API nor a product address"; the HTTP conformance suite's shell cases (`conformance/http/wire-cases.ts`), run against the sidecar process and its handler.
- **ST-116** When its standard input closes, which is how whatever starts it stops it (the HTTP conformance suite's process cases among them), the sidecar stops serving, waiting for any request already being answered, writes any edit not yet on disk, and exits zero, or non-zero if that write failed. SIGINT, SIGTERM and SIGHUP stop it the same way, as they stop a run (ST-63), and a second stop request exits at once, non-zero. *Why:* whatever starts it stops it with no signal of its own, by closing its input. Sources: ADR 0155, ADR 0117, ADR 0119; code and tests. **built**: `test/integration/desktop-sidecar.test.ts` › "writes an edit to the directory and exits zero when its standard input closes", "writes an edit to the directory and exits zero on SIGHUP, as a run does".

## The desktop shell

- **ST-121** (ST-131, from ADR 0171, states the Start window and New Space, which this rule points to; where ST-131 is not built, reopening and Recent, this rule states the shell as built.) The desktop shell (`packages/desktop/src-tauri`) runs each Aggregate directory it opens as Running does (ST-62), with the Rust host (ST-119) in its own process, one run per window, refusing what Running refuses on starting (ST-67) in a dialog that names no command and gives each refusal's kind and location (ST-117). It opens no window but the Start window (ST-131), an Aggregate's, the windows an Aggregate's page opens, and a close's question (ST-122): a folder named on the command line opens at once; with none named, or none that opens, the Start window shows, after each named one that did not open is reported; File › Open… (`CmdOrCtrl+O`) asks for another folder with the platform's chooser while it runs, and a folder that does not open from it is reported and changes nothing else. A folder Running would refuse as missing or empty is not refused in words naming a command: the shell asks whether to create a new Space there, and on Create Space writes one as `init` does (ST-70, ST-11), through the host's `init_directory`, and opens it; declining leaves the folder unwritten and unopened, so at launch with nothing open the Start window shows. File › New Space… (`CmdOrCtrl+N`) shows the Start window's New Space form (ST-131). The shell writes one new Space at a time, so two asked for at once on one folder cannot both find it empty (no test drives the two at once). `tauri.conf.json` declares no window, so nothing opens unless this rule opens it. The menus follow the platform's conventions (ADRs 0167 and 0168, UI-8): on macOS the application menu (About, Check for Updates…, Hide, Quit), File (New Space…, Open…, Close Window), Edit, View (full screen), Window (Minimize, Zoom, Bring All to Front, and the open windows) and Help; on Linux and Windows File (New Space…, Open…, Close Window `CmdOrCtrl+W`, Quit), View (Toggle Full Screen, `F11`) and Help, with no Edit menu, since the webview answers the clipboard keys itself there. Help holds InfinityCube Help and Report an Issue…, which the shell opens in the system browser at fixed addresses of InfinityCube's repository (a window never navigates there, and no page may ask the shell to open an address), and on Linux and Windows Check for Updates… and About. - **ST-111** `mcp <dir>` serves a local MCP server over standard input and output, whose tools list, read, write and delete the directory's files and `check` it as ST-110 does. A missing `<dir>`, or one that is a file, is refused, naming `cube init`, and serves nothing; an empty one is served, and `check` there says what to write rather than naming a command. ## HTTP

- **ST-73** The HTTP application is a Hono app on the Web Fetch model. It exports its route type for a typed client, validates every value crossing the network at runtime, and imports no Node builtin or Vite module. Hosts, asset serving and process lifecycle live in adapters. *Why:* one application runs in every host, a page included. Sources: ADR 0034. **built**: `test/unit/http-node-builtin-restrictions.test.ts` › "restricts the node: prefix for every builtin, including the prefix-only ones"; `test/unit/vite-hono-host.test.ts` › "loads one Fetch application and serves its API through a real Node socket".
- **ST-74** The API is `GET /api/spaces` (listing), `GET /api/spaces/:id` (a working read), `GET /api/aggregate` (a complete read, which never initializes), `POST /api/spaces` (one commit), `POST /assets` and `GET /assets/:hash`. Nothing else is served: a method the contract does not serve is 405, and an undeclared path 404. A working read of a Space that does not exist is 404 `not-found`. Every answer but a stored asset carries `Cache-Control: no-store`. *Why:* one write door and lazy reads. Sources: ADR 0034. **built**: `http/test/space-http-app.test.ts` › "retains collection listing and lazy resource loading", "loads the complete aggregate from its own resource", "refuses the retired PUT resource commit", "keeps invalid ids distinct from undeclared paths", "returns not found for an absent lazy resource"; `http/test/asset-http-app.test.ts` › "answers 405 for %s under %s, naming what is allowed".
- **ST-75** `POST /assets` takes the raw bytes as its body and admits any media type up to 10 MiB, counted as it arrives. The declared `Content-Type` is the media type, stored as its lower-case essence, and `application/octet-stream` when it is missing or invalid; bytes already stored keep the type they were first stored under. An encoded body is refused. It answers `{ url }` and `Location`, 201 when stored and 200 when the store already holds those bytes. Refusals: `unsupported-media-type` (415, for a content-encoded body) and `asset-too-large` (413). Which pictures an Image Resource stores is the Image plugin's rule, applied before storing (SR-63). *Why:* every plugin saves bytes the same way, and the store draws no line between text and binary. Sources: ADR 0106, ADR 0142. **built**: `http/test/asset-http-app.test.ts` › "admits %s under the declared media type, whatever it is", "answers the same URL for the same bytes, stores them once, and keeps the first type", "refuses a body over 10 MiB by counting what arrives, storing nothing", "stores an asset of exactly 10 MiB", "refuses an encoded body rather than storing the encoding"; `persistence/test/assets.test.ts` › "reads %j as %s".
- **ST-76** A stored asset's hash is the SHA-256 of its bytes as unpadded base64url, and its URL is `/assets/<hash>`. It is served there immutably cached, with `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`. Only PNG, JPEG, WebP and GIF are served under their own type; every other asset is served as `application/octet-stream`, so stored HTML or SVG never runs as a page of this origin. The stored type travels beside the served one, and the browser's asset client reads the bytes typed as they were stored. A malformed hash is 400 `invalid-asset-hash` and an absent asset 404; HEAD is served. The asset of zero bytes is always held, as `application/octet-stream`, and storing it writes nothing. Every repository is also the asset store, nothing deletes an asset from it, and neither lifecycle door touches it. *Why:* content addressing makes a URL permanent, and a store that admits anything must never serve active content. Sources: ADR 0106, ADR 0142. **built**: `persistence/test/assets.test.ts` › "is named by the SHA-256 of nothing", "serves %s as %s"; `http/test/asset-http-app.test.ts` › "serves %s as application/octet-stream, never as active content", "answers HEAD with the headers GET would carry", "answers 400 for a malformed hash whatever the method", "answers 404 for a well-formed hash nothing is stored at", "serves the asset of zero bytes though nothing stored it"; `http/test/asset-http-client.test.ts` › "reads an asset back under the media type it was stored as, whatever it is served as"; `test/support/repository-contract.ts` › "keeps stored assets outside the aggregate its lifecycle doors replace", "holds the asset of zero bytes already, under the type it always has".
- **ST-77** A commit request must be `application/json` in UTF-8 with no content encoding (else 415 `unsupported-media-type`) and at most 1 MiB, counted as it arrives; `Content-Length` is never trusted. An oversized body is 413 `payload-too-large`, read and discarded up to an allowance so the connection survives, and the connection is dropped past it. A body that is not JSON, or that escapes a lone UTF-16 surrogate (ST-22), is 400 `invalid-request` with the detail "Malformed JSON in request body" and no `errors`. The Node host decodes a body nested as deeply as `JSON.parse` reads; the Rust host's limit is ST-119's, a difference ADR 0160 keeps. *Why:* a lying header must not smuggle a body, and an honest client keeps its connection; every host answers a body that is not JSON in the same words. Sources: archived guide `editing-and-persistence.md` (no ADR); ADR 0160. **built**: `http/test/space-http-app.test.ts` › "rejects a %s-encoded request body", "measures the body rather than trusting an over-declared length", "drains an oversized body that ends within the drain allowance", "stops draining a body that keeps arriving past the drain allowance", "rejects a lone surrogate escape in %s as a malformed body", "decodes a body nested deeper than the Rust host reads"; `conformance/http/wire-cases.ts` › "answers 400 invalid-request for a lone surrogate escape, as for malformed JSON".
- **ST-123** Every request to the Space API or the asset store whose method is neither `GET` nor `HEAD` is refused 403 `forbidden`, as Problem Details with the detail "Send a change from the application's own page.", before its body is read, when it names `Sec-Fetch-Site` with any value but `same-origin` or `none`, or, whatever its `Sec-Fetch-Site`, names an `Origin` and a `Host` and the `Origin`'s host and port are not that `Host` (an `Origin` of `null` included). A request naming neither header is served, and a request naming no `Host` (the desktop scheme handler's, which admits a change by its own rule, ST-121) is not judged by its `Origin`. Both the Fetch application and the Rust host's `Application` apply it; product addresses and the shell are not judged by it. The memory store keeps any number of assets. *Why:* any page in the browser can send a run's loopback listener a simple `POST` with no preflight, and only the browser's own headers tell that from the application's page, which is always same-origin. Sources: ADR 0161; code and tests. **built**: `conformance/http/wire-cases.ts` › "answers 403 forbidden to a change sent with Sec-Fetch-Site: %s, changing nothing", "answers 403 forbidden to a change whose Origin is %s, changing nothing" (with no `Sec-Fetch-Site` and with `same-origin`), "stores an asset sent with Sec-Fetch-Site: %s from its own origin", "stores an asset sent from its own origin naming no Sec-Fetch-Site", "answers a read whatever site a browser says sent it", run against the Node host's handler (`test/unit/http-conformance-handler.test.ts`) and process (`test/integration/http-conformance.test.ts`); `crates/http-conformance/src/cases.rs` › `given_a_change_from_another_site` (the `Sec-Fetch-Site`, both own-origin and read cases, run against the Rust host's `Application` by `crates/host/tests/wire.rs` and through the scheme handler by `packages/desktop/src-tauri/src/scheme/tests.rs`); `crates/host/tests/wire.rs` › `given_a_change_from_another_site` (the `Origin` case, which the scheme handler is exempt from, refusing it first; a request naming no `Host` served whatever its `Origin`; and a cross-site change refused with no frame of its body read). Under Xvfb, WebKitGTK 2.52.6 sent a page's change under the desktop scheme, an Edit's `POST /api/spaces` and a `POST /assets`, with no `Sec-Fetch-Site` and no `Origin`, its `Referer` the page, and they were answered 200 and 201 (`.scratch/rust-host/issues/13-swap-the-sidecar-for-the-rust-host.md`); what WKWebView sends is not observed.
- **ST-78** A commit outcome maps to one status, from one table both the application and the browser transport read: `committed` 200, `conflict` 409 (carrying the current values), `aggregate-refused` 422. A rejected commit is 400 `invalid-request`. *Why:* the two sides cannot disagree. Sources: ADR 0057, ADR 0098. **built**: `persistence/test/http-protocol.test.ts` › "gives every commit outcome a status of its own, and decodes each by it"; `http/test/space-http-app.test.ts` › "maps a rejected commit to request correction".
- **ST-79** Every HTTP error is RFC 9457 Problem Details (`application/problem+json`). Its `type` is a closed, stable identity; `title` and `detail` are prose no consumer branches on; optional `errors` carry codes and RFC 6901 pointers. The codec is strict and decoded once into the commit result; there is no other error shape. *Why:* errors cross seams as identities, never sentences. Sources: ADR 0057. **built**: `persistence/test/http-protocol.test.ts` › "round trips every problem identity and an RFC 6901 whole-document pointer", "strictly rejects unknown problem types, fields, and malformed pointers", "rejects a Problem Details title or status that disagrees with its type".
- **ST-80** A stored-seam failure answers by what it is: an unreachable database 503 `persistence-unavailable`; broken stored state, or a failure nothing classifies, 500 `internal-error`. The reason goes to the log, never the response. *Why:* 503 promises the wait will help, which only an outage justifies. Sources: archived guide `editing-and-persistence.md` (no ADR). **built**: `http/test/space-http-app.test.ts` › "answers a commit failure that is neither named arm as 500 internal-error", "hides and logs aggregate repository failures"; `test/unit/vite-hono-host.test.ts` › "answers one invariant failure on the root with a 500 after one read".
- **ST-101** The browser's commit result is the repository's outcome plus the transport's own failures, retryable or permanent, and the transport classifies those failures itself. A Fetch rejection is a retryable `network` failure and a timeout a retryable `timeout`. `request-timeout` is `timeout`; `rate-limited` is retryable `rate-limited`; `persistence-unavailable` and `internal-error` are retryable `unavailable`, each carrying the delay when the response sends a valid `Retry-After`. `unauthorized` and `forbidden` are permanent `forbidden`, `invalid-request` permanent `invalid-commit`, `payload-too-large` permanent `payload-too-large`. Any other problem, a malformed body, a status that disagrees with its Problem Details, or an unexpected client error is a permanent `protocol` failure. *Why:* the repository and HTTP never decide what the session retries. Sources: ADR 0098. **built**: `http/test/http-backend.test.ts` › "maps %s to retryable %s"; `test/unit/http-space-backend-failures.test.ts` › "maps Fetch rejection to a retryable network failure", "honours Retry-After on an unavailable response", "rejects malformed success and conflict bodies as permanent protocol failures", "maps unexpected client errors to permanent protocol failures".
- **ST-102** A commit result's failure arms carry a code (and a `Retry-After` where one applies) and no message. A `protocol` failure carries only a typed `ProtocolFault` naming the broken expectation, for diagnostics. A Problem Details `detail` is never passed on. How the application words each code is in editing.md. *Why:* errors cross the seam as identities, never sentences. Sources: ADR 0057, ADR 0098. **built**: `test/unit/http-space-backend-failures.test.ts` › "rejects malformed success and conflict bodies as permanent protocol failures"; `http/test/http-backend.test.ts` › "mints a distinct failure for each rejected commit".
- **ST-81** A server host answers a product URL with these statuses: a malformed URL is 400; a well-formed one that resolves to nothing (a canvas id, which product URLs do not carry, included) is 404, with Problem Details or the application's error surface; an existing one reaches the application. The destination table it resolves by is NV-80. *Why:* a web address has real HTTP semantics. ## Mounting

- **ST-85** Mounting reads a complete Aggregate from a public GitHub location, `github:owner/repo@ref/path`, into a memory repository inside a static page, established through `initializeAggregate`. The page answers its own HTTP API through the same Space host, intake, commit decision and working-space loader as a server. *Why:* an Aggregate can be shown with no server or database, and behaves as a Running one. - **ST-86** Only a mount composition reads an Aggregate or uses a lifecycle door in the browser; no other app module imports the reader. *Why:* ST-1 holds everywhere else. Sources: ADR 0130, ADR 0132. **built (untested)**: lint zone on `@project/aggregate` in `eslint.config.js`; `app/src/mount/`.
- **ST-87** GitHub is the only source, public repositories only, and no token is ever used. `ref` defaults to the default branch and `path` to the root; a ref runs to the next `/`. The location resolves to a commit once, in at most one call, and only the selected directory's tree is listed, in one call. A truncated tree is refused before anything is fetched. *Why:* the unauthenticated API allows few calls. Sources: ADR 0130, ADR 0132. **built**: `app/test/github-location.test.ts` › "ends a ref at the next slash, so a slashed branch is addressed by SHA or tag"; `app/test/github-source.test.ts` › "spends no call resolving a ref that is already a commit SHA", "lists only the selected directory's tree, by its path at the commit, in one call", "refuses a directory whose own tree is truncated".

## Effects across operations

- **Nothing writes an Aggregate directory except Export.** `init` and Running both write through Export, and Import, Mounting and opening a Space write nothing (ST-48, ST-51, ST-65).
- **Every door applies the same intake.** File, stored document, HTTP, Import, Export's read-back, the lifecycle doors and Mounting all refuse the same shapes with the same identities. Within one runtime, the doors agree on the words; between a Rust door and a TypeScript one, on the kind of error and where it is (ADR 0156). Exception: a stored Resource document strips an undeclared envelope key that a file refuses (ST-25).
- **Nothing initializes a Space but a working read.** Listing, the complete Aggregate read, Import, Export and the mount reader never do (MG-75). No exceptions.
