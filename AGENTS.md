# AGENTS.md

Instructions for AI coding agents working in this repo.

InfinityCube is a local prototype for graph-native technical presentations: Resources on authored Maps, connected into directed Graphs and presented by traversal.

## Read before changing an area

The seven docs in [`docs/requirements/`](docs/requirements/) are the binding record of behaviour. Read the relevant doc before the code. Its status distinguishes the requirement from what is built; code does not override a requirement. A behaviour change updates its owning doc in the same commit. [`CONTEXT.md`](CONTEXT.md) defines names. [`docs/adr/archive/`](docs/adr/archive/) is history, not binding.

## Rules that bite

- **Start production UI work with the `shadcn-first-ui` skill, before any code.** Search `@project/ui`, then the shadcn registry; record a deviation before hand-rolling. See [the skill](.agents/skills/shadcn-first-ui/SKILL.md) and [UI](docs/requirements/ui.md).
- **Never start, stop, restart or kill a dev server you did not start, and never free a port.** Verify with tests and CI; see [Commands](#commands).
- **Mint ids through the injected `newId`, never by mocking `crypto.randomUUID`.** See [Anti-slop](docs/agents/anti-slop.md).
- **Relative imports inside a package are extensionless, and type-only imports use `import type`.**
- **`eslint-suppressions.json` only shrinks:** it is generated, never hand-edited or regenerated to admit a new assertion. See [Anti-slop](docs/agents/anti-slop.md#the-suppressions-baseline).
- **A module bundled into a Vite config imports `@project/*` by relative path**, or the dev server will not start. See [Build and tooling](docs/agents/build-tooling.md).
- **When the chrome changes, search `test/e2e/` too:** the PostgreSQL and SQLite restart proofs drive it and run only in CI's database jobs.

## State

InfinityCube is unreleased and makes no compatibility promise for any copy outside the repository. An Aggregate directory is recovered from git or read with the build that wrote it, and a browser's stored copy of a mounted talk (not built) may be unreadable after a deploy. Format changes follow [Storage and hosts](docs/requirements/storage.md#rolling-forward).

## Commands

- Install: `pnpm install` (Node >= 26.8.1, pnpm 9).
- Dev: `pnpm dev` (app at http://localhost:5173) is the normal PostgreSQL-backed HTTP runtime and requires the configured database to be up. `pnpm dev:new` (port 5174) serves an initially empty memory repository; server-side startup creates the normal one-resource **new space** once. `pnpm dev:fixture` (port 5175) serves the tracked fixture through the same HTTP boundary over an isolated memory repository. `pnpm dev:roadmap` regenerates and serves the V1 dependency-map Space on port 5176 through that memory runtime. `pnpm dev:sqlite` (port 5177) is the opt-in file-backed SQLite host (`SQLITE_PATH`, default `.scratch/sqlite/infinity-cube.db`); PostgreSQL remains the default. `pnpm cube import --store sqlite` and `pnpm cube export --store sqlite` reach SQLite, require `SQLITE_PATH` and a migrated file, and must not share a file a running host has open. Edits in any memory runtime survive browser reloads for that server's lifetime. None writes source files except `dev:roadmap`, whose generated files stay under its ignored `.scratch/v1-release/roadmap-space/` directory. **Never start, stop, restart or kill a server you did not start**, and do not free a port (`kill`/`pkill vite`/`lsof -ti:5173 | xargs kill` etc.). `pnpm dev` is not port-strict: a second one (say, in another worktree) takes the next free port and prints it — which is also why an agent must not start one. The scripted `dev:*` hosts stay `--strictPort`, and a second `pnpm dev` usually lands on 5174, `dev:new`'s port. **Whether a server is running is a fact about the machine, and this file cannot tell you.** Look, don't assume: `lsof -nP -iTCP:5173-5299 -sTCP:LISTEN` — wider than the five scripted ports, because a `pnpm dev` that found them taken is listening above them. A running dev server is hot-reloading (Vite HMR + React Fast Refresh), so your edits are already live in it; if none is running, nothing is serving your change and no amount of editing makes it visible. To verify changes, use the tests (Playwright starts its own servers) and CI, as "Before claiming done" sets out — never a dev server.
- Verify: `pnpm verify` runs `typecheck:toolchain` -> `typecheck` -> `typecheck:packages` -> `ui:catalog:check` -> `lint` -> `lint:anti-slop` -> `format:check` -> `test:coverage` (i.e. the compiler assertion, then `tsc --noEmit` over the root program, then `pnpm -r typecheck` over each package's own config, `eslint . --max-warnings=0 --prune-suppressions`, `oxlint -c .oxlintrc.json` over the 15 vendored anti-slop rules, `prettier --check .`, `vitest run --coverage`). **`typecheck:toolchain` runs first** because a typecheck against the wrong compiler still passes, so proving which `tsc` ran has to happen before trusting what it said. CI runs that chain as **two jobs**, so a red lint and a red test suite are different check names: `verify:static` is the first seven commands and `test:coverage` is the eighth, and `verify` is defined as those two — the list of eight lives in `package.json` and nowhere else, so a developer's one command and CI's two cannot drift. **Both typechecks are needed**: the root program's `include` has `"*.config.ts"`, and `*` does not cross directory boundaries, so `packages/app/vite.config.ts`, `vite-space-http-plugin.ts` and `http-server-build.config.ts` are covered only by the per-package pass. Warnings fail the lint run; coverage thresholds are per-package and pinned at what already holds — the `thresholds` block in `vitest.config.ts` names the gated packages — with no global threshold on purpose.
- Run: `pnpm cube run <dir>` runs an Aggregate directory: it Imports `<dir>` into a fresh memory store, serves the application on port 4173 or the next free one (`--port <port>` fixes it), Exports back to `<dir>` once edits have been quiet for about a second — in place, like every Export: only the files Import reads, unchanged ones skipped, each changed one renamed over its target, `<dir>` and its Space directories never moved, and git rather than InfinityCube answering for a write that fails part-way — and flushes on SIGINT, SIGTERM or SIGHUP before exiting zero; a second signal exits at once. A missing or empty `<dir>` (dot-entries such as `.git` do not count) is refused non-zero, naming `pnpm cube init <dir>`, which writes a new aggregate there and exits without serving; an invalid one, or a single Space directory with no `aggregate.json`, is refused non-zero with the intake's errors. `pnpm cube check <dir>` reads `<dir>` through the same Import into a memory store that is then discarded, so it refuses what `run` refuses on starting (not a write that fails later), exits zero for an accepted directory, and neither serves nor writes; it is how an agent checks files it has written. `pnpm cube mcp <dir>` serves a stdio MCP server whose tools list, read, write and delete `<dir>`'s files and check it as `check` does (`src/mcp/aggregate-mcp-server.ts`); start it with `pnpm --silent`, since standard output carries only the protocol. A run opens the browser unless `--no-open`, and a relative `<dir>` is relative to where `pnpm` was invoked, for every `cube` verb. **Unlike the dev hosts, an agent may start and stop `pnpm cube run --no-open` itself**, on a directory of its own (a temp directory, never the human's working directory) when developing or testing InfinityCube — it is how `test/integration/run-command.test.ts` runs it, a database-free file that CI runs in the `postgres` job because `vitest.integration.config.ts` takes every integration file not named `sqlite-*`. A run the person asks for through the `infinity-cube-getting-started` skill may be on their content directory. Stop it with SIGINT so its last write lands, and stop it before editing the directory's files, or its next write overwrites them. The `cube` script `exec`s node, so pnpm signals the launcher (`src/cli/run-launcher.ts`) itself rather than a shell that forks it, and the launcher starts the run (`src/cli/run-process.ts`) in a process group of its own and forwards it the signals it receives, once each: under pnpm one Ctrl-C reaches the launcher twice (the terminal's and pnpm's), so it drops a repeat of the same signal within 250ms, and pnpm forwards a second Ctrl-C as SIGTERM, which is never dropped. A failed write is tried again after the quiet period.
- Test: `pnpm test` (Vitest, `vitest` for watch). Unit + property tests (fast-check) live in `packages/*/test`.
- Mutation testing: `pnpm mutate:session` and `pnpm mutate:graph` run StrykerJS (`stryker.conf.mjs`) over one source file against a named oracle. **A deliberate local diagnostic, never a gate** — not in `verify`, not in CI, `thresholds.break` is `null`, and the tickets that introduced it forbid a threshold. `--mutate` and `--testFiles` are chosen as a *pair* per campaign, because the whole suite cannot run inside Stryker's sandbox (the `test/unit` scans that shell out to `git ls-files` — `current-domain-vocabulary`, `conflict-markers`, `docs-agents-citation-accuracy`, `docs-agents-ticket-status`, and those reading through `test/support/structural-scan.ts` — get `[]`), so a campaign names the tests that are the oracle for the code it mutates — and nothing keeps that pairing honest but the reader. A score is evidence for a conversation about the oracle, not a number to move; the standing limits on what one means, including this runner's `static: true` false survivors, are in `.scratch/mutation-testing/engine.md`. Output goes to the gitignored `/reports/` and `/.stryker-tmp/`.
- E2E: `pnpm e2e` (Playwright, Chromium only) stays database-free and exercises HTTP; `pnpm e2e:fixture` selects only the tracked-fixture project. Every test owns a fresh Vite host, `E2eMemorySpaceRepository` and catalog; reloads and extra pages inside that test share them, while no revision leaks to another test. The `chromium` project imports the tracked fixture and `new-space` starts empty so database startup creates one resource. Hosts use worker-scoped ports beginning at 5300, away from the human's 5173–5175. `pnpm e2e:postgres` is the separate one-test project proving a real PostgreSQL edit survives a fresh Vite host. **CI runs it, as the last step of the `postgres` job** — it sits there rather than in `e2e` because it applies no migration of its own and needs the database `test:integration:postgres` has already migrated. Locally it stays opt-in: run it only with PostgreSQL up and migrated, and always stop PostgreSQL afterward. `pnpm e2e:sqlite` is its SQLite counterpart, proving a real SQLite edit survives a fresh Vite host on the file `SQLITE_PATH` names. **CI runs it too, as the last step of the `sqlite` job**, after that job's `test:integration:sqlite` has migrated the job's temp file — the same placement for the same reason. Locally it stays opt-in: run it only with `SQLITE_PATH` set to a file `pnpm db:migrate:sqlite` has migrated. **Both proofs live in `test/e2e/`, not `packages/app/e2e/`, and both drive the application surface** — each opens a Space and addresses the Space's name, its Resources and `persistence-status` through the same helpers the normal suite uses (`test/support/restart-proof.ts`, shared between the two rather than copied). So a change to the Space's chrome breaks both exactly as it breaks the others, and **nothing in `verify`, `e2e` or `e2e:ladle` will tell you**: the two commands that can observe it each need a database, so a surface change that swept `packages/app/e2e/**` and stopped there reaches CI red. One-time first: `pnpm exec playwright install chromium`.
- Ladle E2E: `pnpm e2e:ladle` runs `playwright.ladle.config.ts` over `packages/app/ladle-e2e/`, against a `ladle serve --noWatch` catalogue it starts itself on port 61100. This is the behaviour check for story evidence and it is **its own CI job**, run by neither `verify` nor `e2e` — so a component change that breaks a story is only caught here. The two Playwright configs share one flake policy (`retries: 2` and `failOnFlakyTests` under CI, `retries: 0` on a laptop); under `failOnFlakyTests` a retry that passes still fails the run, so the retries buy the trace and the reproduce-or-not signal rather than tolerance for a blip.
- Mount E2E: `pnpm e2e:mount` runs `playwright.mount.config.ts` over `packages/app/e2e/mount.spec.ts`: it runs `pnpm build:mount` into `packages/app/node_modules/.mount-e2e` with a branch of a fake repository as its default, serves the build from `packages/app/e2e/static-server.ts` on port 5282 with single-page fallback and the build's own `_headers`, and answers every GitHub request from `packages/app/fixture` by route interception, failing a test on any Content Security Policy violation. It is **its own CI job, `mount`**, run by neither `verify` nor `e2e`, which ignores the spec; it shares the two Playwright configs' flake policy.
- Build: `pnpm build` (Vite build of the app). `pnpm build:mount` writes the static application for Mounting to `packages/app/dist-mount`: the same `index.html` composed by `src/mount-main.tsx` instead of the HTTP entry, assets under content-hashed names, and a Cloudflare `_headers` file carrying its Content Security Policy (`packages/app/mount-headers.ts`). `VITE_DEFAULT_SPACE_SOURCE`, read at build time, names the GitHub location a page with no `source` parameter mounts; with neither, the page asks for one.
- PostgreSQL integration: copy `.env.example` to the ignored `.env`, fill its password and matching `DATABASE_URL`, then run `pnpm postgres:up` followed by `pnpm test:integration:postgres`. Always finish with `pnpm postgres:down`; it keeps the named volume. `docker compose down --volumes` is the destructive reset. `pnpm test:integration:sqlite` is the matching file-backed suite (temp file, no Docker). Normal `pnpm verify` and `pnpm e2e` do not require PostgreSQL.

## Package layout & boundaries

Sixteen `@project/*` workspace packages under `packages/`:

- `resource-api` — the Resource API, the one door a Resource plugin reaches. `/domain` is the plugin contract with no React: `definePlugin`, `Resource<C>` (the one Resource structure, which `core`'s `Resource` instantiates per kind), outlines, asset references and `Answer`. `/view` is the view half a plugin draws with (`Surface`, Claims and exclusive work, `Title`, `Own` and `Rail`); `/view/host` is what a host provides those components with (`ResourceHostProvider` and the rail store), which a plugin's source may not import; `/view/testing` is `renderPlugin`, the test host, for a plugin's tests only. It depends on no package of ours, which its `rootDir` and lint zone enforce.
- `plugin-ur` — the Ur plugin: `/domain` (its content and Map content schemas) and `/view` (what it draws in its rect). It imports no package of ours but `resource-api`'s `/domain` and `/view`, and its domain half no React and no view.
- `plugin-image` — the Image plugin, shaped as `plugin-ur` is: `/domain` (its `{ url, naturalSize? }` content and picture admission) and `/view` (its picture, and Replace run as exclusive work under a Claim). The same import rule as `plugin-ur`.
- `plugin-markdown` — the Markdown plugin, shaped as `plugin-ur` is: `/domain` (its `{ url }` content, its `{ open }` Map content and the `\n` line-ending rule) and `/view` (its text read through `assets.read`, Open with a size hint, and its edit: a Claim, the source editor and the text the host renders, both reached through `resource-api`'s `ResourceHost`, never CodeMirror or a parser of its own). The same import rule as `plugin-ur`.
- `plugin-reference` — the Reference plugin, shaped as `plugin-ur` is: `/domain` (its `{ target }` content, its one Resource reference, and its `{ open }` Map content, Open where there is no Map) and `/view` (Closed, its Title and glyph; Open, its Target through the surface's `Embed`, passed its own Title; Open and Close on its rail). The same import rule as `plugin-ur`.
- `plugin-space` — the Space plugin, shaped as `plugin-ur` is: `/domain` (its `{ spaceId, map, graph, framing? }` content, its one Space reference, which it owns, its `{ open }` Map content and its selection declaration, `viewOf`/`selectView`) and `/view` (Closed, its Title and glyph and no request; Open, the Map through the surface's `Embed space`, passed `select` (its view and content commit) and the Claim Edit takes; Edit or Done, Open and Close on its rail). The same import rule as `plugin-ur`.
- `plugin-default` — the Default plugin, shaped as `plugin-ur` is but in no plugin list: `/domain` (content and Map content read as unknown, and no Target) and `/view` (the Title and a note that the kind is not available). Core and ui reach it only through `plugins`, as the default for a kind that names no plugin. The same import rule as `plugin-ur`.
- `plugins` — the build's plugin list, the one package that imports a `plugin-*` package: `/domain` lists each plugin's domain half once, in the order every choice among kinds is offered in (`PLUGINS`), with the default plugin beside it (`DEFAULT_PLUGIN`), and `/view` pairs each with its view half (`PLUGIN_VIEWS`, `DEFAULT_PLUGIN_VIEW`). Adding or removing a plugin is one line in each half. Its domain half names no view.
- `core` — domain model. Zod schemas (`schema.ts`, incl. `spaceFileSchema` — the space-file shape) + schema-derived `Resource`/`Graph`/`GraphEdge`/`Map` types (`types.ts`). No React, no framework deps. Depends on the domain halves of `resource-api` and `plugins`, reading each listed plugin as a module of declarations (`plugin-modules.ts`).
- `graph` — pure graph logic over a `Space`: `loadSpace` (the one intake — parse, validate references including duplicate Edges within a Graph, index), the `Space` type and the one `SpaceLookup` it carries, Graph→Edge derivation, traversal, the Graph palette with `nextGraphColor`, the colour rule every Graph creation gesture stores by (`graph-color.ts`, so `newSpace` and persistence's first-load Graph can reach it), and the `LayoutStrategy` contract (`LayoutStrategyGraph`, `buildLayoutStrategyGraph`, `gridStrategy`, `positionedStrategy`). Depends only on `core`. **Its index is curated and there is no `export *`**, and the unit of curation is the **module**: it names every function something outside the package calls, and every type exported by a module those calls reach — whether or not a consumer writes that type down today. `validate` is absent as a whole module: it runs inside `loadSpace`, the one intake. `SpaceReferenceError` is off the surface although `loadSpace`'s `SpaceError` union names it, while `ResourceFileError` in that same union is offered — reachability is not the test, and neither is depth. Adding a name is a deliberate act — `test/unit/graph-package-surface.test.ts` holds the index's declarations and the module they produce to one list, so a new export fails until it is listed there. A test of an internal helper imports it from its own module rather than through the index.
- `http` — browser-safe Fetch transport: the Hono `/api/spaces` route tree, request and response policy and the inferred `SpaceHttpApp` client contract. It *consumes* the narrow `StoredSpaceRepository` seam rather than declaring it — that lives in `persistence`, beside the `LoadedSpace` and `SpaceSummary` it is written in terms of. Depends only on `core`, `persistence`, Hono and runtime-neutral media parsing; imports no host, database, app or render implementation.
- `persistence` — browser-safe `SpaceBackend` and `SpaceSession` contracts, optimistic revision handling, commit coalescing, retry/conflict states, and the memory adapter. It also declares the **stored** side of the seam once, for both consumers: `StoredSpaceRepository` and `RepositoryCommitResult` (`src/repository.ts`), which `@project/http` takes and which `@project/aggregate` (`src/space-repository.ts`) extends into `SpaceRepository` by adding `initializeAggregate`, `replaceAggregate` and `markExported`. The server seam is a superset, never a second declaration — a `Resource`/`Graph` change cannot leave the two sides disagreeing, and the browser still cannot name the aggregate lifecycle or export because the seam the Fetch application consumes does not declare them. **Two lifecycle doors and no mode parameter on either**: a mode argument would hide a destructive choice, and Meta is named, never inferred from array position. Seeds, fixtures and tests seed through those same two. Depends on `core` and `graph` so every committed snapshot passes the normal domain intake. It also owns **`createObservableState`**, the one observable-state seam behind `SpaceSession`, Navigation and SpaceAuthoring's own `getState`/`subscribe` interfaces: publication installs the next state synchronously, snapshots the subscriber set so a listener added mid-publication begins at the next one rather than part-way through the current, contains synchronous throws and thenable rejections, continues to the observers behind the failure, and reports through a sink `createNonThrowingReporter` has made incapable of interrupting the work it describes. Each collaborator keeps its own state and its own interface; only notification is shared. **`app` therefore imports observable state from `persistence` although Navigation has nothing to do with persistence**; `.scratch/authoring-seams/issues/01-one-observable-state-module.md` records why that home was taken and what the alternatives cost.
- `aggregate` — the browser-safe half of an Aggregate directory and the stores behind the HTTP application: the directory reader (`readAggregateFrom`, which reads a complete aggregate from an `AggregateSource` — a name, a listing of one directory, a read of one file answering its bytes or why not, and how many reads it allows at once — deciding itself what to list and read; `scanAggregateFrom`, the files Importing reads and the Space directories among them, found by listing alone; and `mapSource`, a source over bytes already in memory), the `SpaceRepository` seam, the aggregate lifecycle, `MemorySpaceRepository` and `createSpaceHost`, the product resolution the host performs. Root `src/` keeps the filesystem source (`directorySource` in `src/aggregate-directory/`), the SQL repository and the CLI, and imports these from here. Depends on `core`, `graph`, `persistence` and `http`, and imports no Node builtin: the lint zone bans one and `test/unit/aggregate-package-browser-safe.test.ts` reads its sources for one.
- `react-flow-adapter` — the React Flow (`@xyflow/react`) projection: projects a Space and its Map-owned Graphs into RF nodes/edges and renders `ResourceNode`. It implements no `LayoutStrategy`: `gridStrategy` and `positionedStrategy` are `graph`'s.
- `ui` — reusable, presentation-agnostic React components and shadcn-style primitives (Tailwind v4, CVA, Lucide, and Base UI controls), the `StatusPanel` operational-feedback module, the one command surface (`CommandSurface`, `CommandToolbar`, `ChoiceMenu`) the Dock and the Resource rail both draw, `MarkdownSourceEditor` (the one component allowed to know CodeMirror exists), the `AppShell` that frames the canvas, and the plugin host that draws a plugin's view half inside its rect (`PluginResource`, `PresentedPluginResource`). Depends on `core` and on the view halves of `resource-api` and `plugins`, draws each kind from the catalogue a surface is handed (`plugin-catalog.tsx`), and it hands every plugin the Markdown renderer and source editor (`ResourceTextHost.tsx`) and the embeddings (`ResourceEmbedding.tsx`: a Resource, or a Map the host draws). Its rules are [UI](docs/requirements/ui.md).
- `app` — wiring and composition: it composes each opened Space, and owns Space loading, product-URL navigation, the canvas and its camera, the presenting Stage and its chrome, and hand-rolled CSS.
  - **`compose-app.ts` states once what an opened Space is composed of**: `composeCore` answers the one working-space reader, `currentSpace`, the opening Map and Navigation; `composeApp` adds Space Authoring, the render adapter, the continuation and Edge Authoring, in the order they are built — the continuation before Edge Authoring, which publishes into it. Every collaborator closes over that one reader, which gives them one `Space` identity. Open Spaces (`open-spaces.ts`) is `composeApp`'s one caller and hands each composition to `createApp`. A test that wants collaborators calls `composeCore` or `composeApp` rather than writing the chain out.
  - **Zustand is the render adapter's and nothing else's**: it holds the published projection ([Rendering](docs/requirements/rendering.md), `canvasProjection`), drag bookkeeping and the `none | resource | edge` canvas selection. Navigation (the Active Graph, Traversal history) and Space Authoring keep their own state behind `createObservableState`, read through one `useSyncExternalStore`. Open/Closed is authored on the Map, so Navigation carries no opened-Resource field.
  - Navigation and browser history are [Navigation](docs/requirements/navigation.md); where an Edit continues and why there is no creation pane are [UI](docs/requirements/ui.md); Edge Authoring is [Rendering](docs/requirements/rendering.md); Map resolution is [Editing](docs/requirements/editing.md).

Hard rules — **all four are enforced, not just documented**. Two layers, because neither catches what the other does: ESLint `no-restricted-imports` zones catch package specifiers and relative escapes (`../../*`), and each package's narrowed tsconfig `paths` makes an illegal alias unresolvable. `rootDir` is set on `resource-api` alone, the one package that resolves no `@project/*` import — anywhere else it rejects the legitimate `@project/*` import too, since the referenced file resolves outside the package, which is why the relative-escape half is a lint rule rather than a compiler setting.

- Domain logic stays out of React (keep it in `core`/`graph`).
- React Flow stays out of the domain and the reusable UI: **`core`, `graph`, `http`, `persistence`, `aggregate`, `ui`, `resource-api` and every `plugin-*` must not import `@xyflow/react`**, which `no-restricted-imports` in `eslint.config.js` enforces. `react-flow-adapter` holds the projection into React Flow, and `app`, the composition layer, imports `@xyflow/react` as well. The same zone names elkjs, which no package depends on. Read that entry as banning a *render-time* engine from the domain, not as siting a returning one: the Map and Graph requirements put Auto-arrange in `graph`, attached to an Edit, so building it means re-siting the ban rather than obeying the lint message.
- Reusable UI goes in `ui`; app-specific glue goes in `app`.
- Vite-config imports by relative path: see [Rules that bite](#rules-that-bite).

## Conventions & gotchas

- **Strict TypeScript everywhere**, incl. `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`.
- **`package.json`'s TypeScript entries look wrong and are not**: `tsc` is TypeScript 7 and the only type-checking truth, and `typescript` resolves to TypeScript 6 on purpose. See [`build-tooling.md`](docs/agents/build-tooling.md) before touching either.
- **`verbatimModuleSyntax` + ESLint `consistent-type-imports` are on** — use `import type` for type-only imports or lint/typecheck fails.
- **Cross-package imports** use the `@project/*` path aliases: declared in `tsconfig.base.json`, mirrored in `vitest.config.ts` `resolve.alias`, and **narrowed per package** in each `packages/*/tsconfig.json` so a package can only resolve what it may legally depend on. Vite needs no alias: it resolves through the workspace `exports`. Vitest's *is* load-bearing: the root package declares no `@project/*` deps, so there is no symlink to resolve through. Two lists to keep in sync, plus the package's own narrowed one.
- **Relative imports inside a package are EXTENSIONLESS** (`./foo`, not `./foo.ts`).
- **Use a functional core and imperative shell for cross-module coordination.** Compute and validate the complete next state in a private pure core before producing side effects; a thin imperative shell then updates collaborators in an order that preserves valid intermediate states. Expose the coordination as one operation rather than returning a plan for callers to execute. Keep framework and store events outside the seam, depend on existing module interfaces, and do not manufacture single-adapter ports for deterministic private helpers. An edit event is a notification, not state transfer: each editor first installs its authoritative completed state and only then emits the notification; the coordinator derives the next Space from the current state owned by its collaborators rather than from state carried by the event.
- **Comments and these docs assert only what their writer checked, and carry no lineage.** A negative result or a measurement goes in a ticket, a claim about another module names the test that holds it, and history goes in the commit or the ticket. The rules are [`workflow.md`](docs/agents/workflow.md#what-a-comment-may-assert).
- **Vocabulary is guarded.** `path` means a file path, "arrangement" is prose, and retired words ("workspace", and the retired name for a Space) are held out of the source by `test/unit/current-domain-vocabulary.test.ts`, which no arm runs over Markdown. Read [Workflow](docs/agents/workflow.md#domain-vocabulary) before adding an arm or an exemption.

## Before claiming done

**The full bar runs in CI, on a draft PR.** `pnpm verify`, `pnpm e2e` and `pnpm e2e:ladle` overload the local machine, so the laptop runs targeted checks and CI runs the suite.

1. **Check locally, aimed at the change**: `pnpm typecheck` and `pnpm typecheck:packages`, `pnpm exec eslint <files>`, `pnpm exec vitest run <files>`, and `pnpm exec playwright test <spec>` when iterating on one UI behaviour (`-c playwright.ladle.config.ts` for a story spec under `packages/app/ladle-e2e/`). `pnpm verify:local` is the whole-repo static bar plus coverage at two workers.
2. **Open a draft PR at the first commit.** Branch off `main`, push, `gh pr create --draft`. CI runs on pull requests and pushes to `main` only, so a pushed branch with no PR is never checked. Asking for the work authorises pushing its branch and opening its draft PR; marking it ready, merging and pushing to `main` wait for the user.
3. **Done is `CI passed` green** — the gate job over every required job. Watch with `gh pr checks --watch`; when the gate is red, find the red job in that list and read it with `gh run view <run-id> --log-failed`. `main` is gated, so the baseline is green and a red job is yours until `git stash` or `git log` on the file shows otherwise.
4. **Report the evidence**: the local commands you ran and those you skipped, the `CI passed` result with each job behind it, and which CI job read what changed, or that none did. Claim success only for a result you watched arrive.
