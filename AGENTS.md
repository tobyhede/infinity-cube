# AGENTS.md

Instructions for AI coding agents working in this repo.

InfinityCube is a local prototype for graph-native technical presentations: Resources on authored Maps, connected into directed Graphs and presented by traversal.

## Read before changing an area

Accepted ADRs in [`docs/adr/`](docs/adr/README.md) are binding and append-only. The seven docs in [`docs/requirements/`](docs/requirements/) restate them in current words as a snapshot: [`snapshot.lock.json`](docs/requirements/snapshot.lock.json) records which ADRs they restate, and an accepted ADR that `python3 scripts/adr_snapshot.py check` lists as pending binds where the two differ (ADR 0175); a proposed one binds nothing. Read [`CONTEXT.md`](CONTEXT.md) for names, then the owning doc below, then any ADR that `python3 scripts/adr_snapshot.py check` lists as pending, before the code. A requirement that disagrees with an accepted ADR is a defect in the requirement. Status in a doc distinguishes the requirement from what is built; code does not override either. A behaviour change updates its owning doc in the same commit, and a new or changed decision is a new ADR, which edits no requirements doc: the next refresh folds it in ([Workflow](docs/agents/workflow.md#adrs-and-the-requirements-snapshot)). [`docs/adr/archive/`](docs/adr/archive/) holds only the retired product guides, kept as history.

## Rules that bite

- **Start production UI work with the `shadcn-first-ui` skill, before any code.** Search `@project/ui`, then the shadcn registry; record a deviation before hand-rolling. See [the skill](.agents/skills/shadcn-first-ui/SKILL.md) and [UI](docs/requirements/ui.md).
- **Never start, stop, restart or kill a dev server you did not start, and never free a port.** Verify with tests and CI; see [Commands](#commands).
- **Mint ids through the injected `newId`, never by mocking `crypto.randomUUID`.** See [Anti-slop](docs/agents/anti-slop.md).
- **Relative imports inside a package are extensionless, and type-only imports use `import type`.**
- **`eslint-suppressions.json` only shrinks:** it is generated, never hand-edited or regenerated to admit a new assertion. See [Anti-slop](docs/agents/anti-slop.md#the-suppressions-baseline).
- **A module bundled into a Vite config imports `@project/*` by relative path**, or the dev server will not start. See [Build and tooling](docs/agents/build-tooling.md).
- **When the chrome changes, search `test/e2e/` too:** the PostgreSQL and SQLite restart proofs drive it and run only in CI's database jobs.

## State

InfinityCube is unreleased and makes no compatibility promise for any copy outside the repository. An Aggregate directory is recovered from git or read with the build that wrote it, and a browser's stored copy of a mounted Aggregate (not built) may be unreadable after a deploy. Format changes follow [Storage and hosts](docs/requirements/storage.md#rolling-forward).

## Commands

- Install: `pnpm install` (Node >= 26.8.1, pnpm 9).
- Dev: `pnpm dev` (app at http://localhost:5173) is the normal PostgreSQL-backed HTTP runtime and requires the configured database to be up. `pnpm dev:new` (port 5174) serves an initially empty memory repository; server-side startup creates the normal one-resource **new space** once. `pnpm dev:fixture` (port 5175) serves the tracked fixture through the same HTTP boundary over an isolated memory repository. `pnpm dev:roadmap` regenerates and serves the V1 dependency-map Space on port 5176 through that memory runtime. `pnpm dev:sqlite` (port 5177) is the opt-in file-backed SQLite host (`SQLITE_PATH`, default `.scratch/sqlite/infinity-cube.db`); PostgreSQL remains the default. Beside it, `infinity-cube serve --store sqlite [--port <port>] [--built <dir>]` is the Rust CLI's SQLite host (Storage ST-120, ST-126): it serves the file `SQLITE_PATH` names, which it never creates or migrates and which must already exist (it refuses a missing one, naming `pnpm db:migrate:sqlite`, and has no default file), on `127.0.0.1` from port 4173 up, as the Rust CLI's `run` does but with no Import, Export or directory lock. An agent may start and stop it on a migrated file of its own, never the human's. `infinity-cube serve --store postgres [--port <port>] [--built <dir>]` is its PostgreSQL counterpart, beside `pnpm dev`: it serves the database `DATABASE_URL` names (the environment, then the nearest `.env`), which it never migrates, refusing an unset or blank one before it takes a port; an agent may start and stop it on a database of its own, never the human's. `pnpm cube import --store sqlite` and `pnpm cube export --store sqlite` reach SQLite, require `SQLITE_PATH` and a migrated file, and must not share a file a running host has open. Edits in any memory runtime survive browser reloads for that server's lifetime. None writes source files except `dev:roadmap`, whose generated files stay under its ignored `.scratch/v1-release/roadmap-space/` directory. **Never start, stop, restart or kill a server you did not start**, and do not free a port (`kill`/`pkill vite`/`lsof -ti:5173 | xargs kill` etc.). `pnpm dev` is not port-strict: a second one (say, in another worktree) takes the next free port and prints it — which is also why an agent must not start one. The scripted `dev:*` hosts stay `--strictPort`, and a second `pnpm dev` usually lands on 5174, `dev:new`'s port. **Whether a server is running is a fact about the machine, and this file cannot tell you.** Look, don't assume: `lsof -nP -iTCP:5173-5299 -sTCP:LISTEN` — wider than the five scripted ports, because a `pnpm dev` that found them taken is listening above them. A running dev server is hot-reloading (Vite HMR + React Fast Refresh), so your edits are already live in it; if none is running, nothing is serving your change and no amount of editing makes it visible. To verify changes, use the tests (Playwright starts its own servers) and CI, as "Before claiming done" sets out — never a dev server.
- Verify: `pnpm verify` runs `typecheck:toolchain` -> `typecheck` -> `typecheck:packages` -> `ui:catalog:check` -> `lint` -> `lint:anti-slop` -> `format:check` -> `test:coverage` -> `crap:ts` (i.e. the compiler assertion, then `tsc --noEmit` over the root program, then `pnpm -r typecheck` over each package's own config, `eslint . --max-warnings=0 --prune-suppressions`, `oxlint -c .oxlintrc.json` over the 15 vendored anti-slop rules, `prettier --check .`, `vitest run --coverage`, then the TypeScript CRAP gate over the coverage that run wrote). **`typecheck:toolchain` runs first** because a typecheck against the wrong compiler still passes, so proving which `tsc` ran has to happen before trusting what it said. CI runs that chain as **two jobs**, so a red lint and a red test suite are different check names: `verify:static` is the first seven commands and the `coverage` job runs `test:coverage` and `crap:ts`, and `verify` is defined as those — the list of nine lives in `package.json` and nowhere else, so a developer's one command and CI's two cannot drift. **Both typechecks are needed**: the root program's `include` has `"*.config.ts"`, and `*` does not cross directory boundaries, so `packages/app/vite.config.ts`, `vite-space-http-plugin.ts` and `http-server-build.config.ts` are covered only by the per-package pass. Warnings fail the lint run; coverage thresholds are per-package and pinned at what already holds — the `thresholds` block in `vitest.config.ts` names the gated packages — with no global threshold on purpose.
- Run: `pnpm cube run <dir>` runs an Aggregate directory: it Imports `<dir>` into a fresh memory store, serves the application on port 4173 or the next free one (`--port <port>` fixes it), Exports back to `<dir>` once edits have been quiet for about a second — in place, like every Export: only the files Import reads, unchanged ones skipped, each changed one renamed over its target, `<dir>` and its Space directories never moved, and git rather than InfinityCube answering for a write that fails part-way — and flushes on SIGINT, SIGTERM or SIGHUP before exiting zero; a second signal exits at once. A missing or empty `<dir>` (dot-entries such as `.git` do not count) is refused non-zero, naming `pnpm cube init <dir>`, which writes a new aggregate there and exits without serving; an invalid one, or a single Space directory with no `aggregate.json`, is refused non-zero with the intake's errors. A run locks `<dir>` from before it Imports until its last write has landed (ADR 0162, Storage ST-124), so a second run of the same directory, by `cube run`, `infinity-cube run`, the desktop application or the sidecar, is refused non-zero, naming it; the lock is SQLite's on the empty `<dir>/.infinity-cube.lock`, which is never deleted and which a content repository ignores, and the operating system releases it when the run's process ends, however it ends, so a test that kills a run may start another on the same directory. `pnpm cube check <dir>` reads `<dir>` through the same Import into a memory store that is then discarded, so it refuses what `run` refuses on starting (not a write that fails later), exits zero for an accepted directory, and neither serves nor writes; it is how an agent checks files it has written. `pnpm cube mcp <dir>` serves a stdio MCP server whose tools list, read, write and delete `<dir>`'s files and check it as `check` does (`src/mcp/aggregate-mcp-server.ts`); start it with `pnpm --silent`, since standard output carries only the protocol. A run opens the browser unless `--no-open`, and a relative `<dir>` is relative to where `pnpm` was invoked, for every `cube` verb. **Unlike the dev hosts, an agent may start and stop `pnpm cube run --no-open` itself**, on a directory of its own (a temp directory, never the human's working directory) when developing or testing InfinityCube — it is how `test/integration/run-command.test.ts` runs it, a database-free file that CI runs in the `postgres` job because `vitest.integration.config.ts` takes every integration file not named `sqlite-*`. A run the person asks for through the `infinity-cube-getting-started` skill may be on their content directory. Stop it with SIGINT so its last write lands, and stop it before editing the directory's files, or its next write overwrites them. The `cube` script `exec`s node, so pnpm signals the launcher (`src/cli/run-launcher.ts`) itself rather than a shell that forks it, and the launcher starts the run (`src/cli/run-process.ts`) in a process group of its own and forwards it the signals it receives, once each: under pnpm one Ctrl-C reaches the launcher twice (the terminal's and pnpm's), so it drops a repeat of the same signal within 250ms, and pnpm forwards a second Ctrl-C as SIGTERM, which is never dropped. A failed write is tried again after the quiet period.
- CRAP: functions scoring above **30** on the CRAP metric (cyclomatic complexity weighted by test coverage; formula in `scripts/crap/score.ts`) fail CI. `pnpm crap:ts` scores the TypeScript from the coverage `pnpm test:coverage` writes and gates the packages `crap.config.ts` names, the same ones `vitest.config.ts` gates on coverage; `--report` lists every package's worst and never fails. `pnpm crap:rust` runs the Rust crates under `cargo llvm-cov` and scores them with `cargo crap` against `.cargo-crap.toml`; it needs `cargo-nextest`, `cargo-llvm-cov`, `cargo-crap` and `llvm-tools-preview` at the versions the `crap-rust` CI job pins, and leaves out the desktop shell. CI runs the TypeScript gate as the last step of `coverage` and the Rust one as its own job, `crap-rust`. Each config's allow-list only shrinks: an entry is never the way past a failure, and `pnpm crap:ts` also fails on a stale one (`cargo crap` does not, so delete a Rust entry by hand when its function comes under).
- Test: `pnpm test` (Vitest, `vitest` for watch). Unit + property tests (fast-check) live in `packages/*/test`.
- Mutation testing: `pnpm mutate:session` and `pnpm mutate:graph` run StrykerJS (`stryker.conf.mjs`) over one source file against a named oracle. **A deliberate local diagnostic, never a gate** — not in `verify`, not in CI, `thresholds.break` is `null`, and the tickets that introduced it forbid a threshold. `--mutate` and `--testFiles` are chosen as a *pair* per campaign, because the whole suite cannot run inside Stryker's sandbox (the `test/unit` scans that shell out to `git ls-files` — `current-domain-vocabulary`, `conflict-markers`, `docs-agents-citation-accuracy`, `docs-agents-ticket-status`, and those reading through `test/support/structural-scan.ts` — get `[]`), so a campaign names the tests that are the oracle for the code it mutates — and nothing keeps that pairing honest but the reader. A score is evidence for a conversation about the oracle, not a number to move; the standing limits on what one means, including this runner's `static: true` false survivors, are in `.scratch/mutation-testing/engine.md`. Output goes to the gitignored `/reports/` and `/.stryker-tmp/`.
- E2E: `pnpm e2e` (Playwright, Chromium only) stays database-free and exercises HTTP; `pnpm e2e:fixture` selects only the tracked-fixture project. Every test owns a fresh Vite host, `E2eMemorySpaceRepository` and catalog; reloads and extra pages inside that test share them, while no revision leaks to another test. The `chromium` project imports the tracked fixture and `new-space` starts empty so database startup creates one resource. Hosts use worker-scoped ports beginning at 5300, away from the human's 5173–5175. `pnpm e2e:postgres` is the separate one-test project proving a real PostgreSQL edit survives a fresh host on the database `DATABASE_URL` names: a Vite host by default, or the host process `INFINITY_CUBE_RESTART_PROOF_HOST` names, as the SQLite proof below takes it. **CI runs it, as the last steps of the `postgres` job** — once on the Vite host and once on `infinity-cube serve --store postgres`, built in that job and serving the `vite build` output through `--built` — and it sits there rather than in `e2e` because it applies no migration of its own and needs the database `test:integration:postgres` has already migrated. Locally it stays opt-in: run it only with PostgreSQL up and migrated, and always stop PostgreSQL afterward. `pnpm e2e:sqlite` is its SQLite counterpart, proving a real SQLite edit survives a fresh host on the file `SQLITE_PATH` names: a Vite host by default, or the host process `INFINITY_CUBE_RESTART_PROOF_HOST` names as JSON, `{ "name", "argv", "cwd"?, "env"? }`, with `{port}` filled in `argv` (an `argv` naming `{directory}` or `{built}` is refused), announcing itself as an HTTP conformance host does but with no launch secret, and exiting zero on SIGINT (`test/support/restart-proof-host.ts`); its seeding and Export go through the TypeScript repository either way, with no request in flight and, for a host process, its process gone first. **CI runs it too, as the last steps of the `sqlite` job**, after that job's `test:integration:sqlite` has migrated the job's temp file — the same placement for the same reason — once on the Vite host and once on `infinity-cube serve --store sqlite`, built in that job and serving the `vite build` output through `--built`, over the same file Prisma Next migrated. Locally it stays opt-in: run it only with `SQLITE_PATH` set to a file `pnpm db:migrate:sqlite` has migrated. **Both proofs live in `test/e2e/`, not `packages/app/e2e/`, and both drive the application surface** — each opens a Space and addresses the Space's name, its Resources and `persistence-status` through the same helpers the normal suite uses (`test/support/restart-proof.ts`, shared between the two rather than copied). So a change to the Space's chrome breaks both exactly as it breaks the others, and **nothing in `verify`, `e2e` or `e2e:ladle` will tell you**: the two commands that can observe it each need a database, so a surface change that swept `packages/app/e2e/**` and stopped there reaches CI red. One-time first: `pnpm exec playwright install chromium`.
- Ladle E2E: `pnpm e2e:ladle` runs `playwright.ladle.config.ts` over `packages/app/ladle-e2e/`, against a `ladle serve --noWatch` catalogue it starts itself on port 61100. This is the behaviour check for story evidence and it is **its own CI job**, run by neither `verify` nor `e2e` — so a component change that breaks a story is only caught here. The two Playwright configs share one flake policy (`retries: 2` and `failOnFlakyTests` under CI, `retries: 0` on a laptop); under `failOnFlakyTests` a retry that passes still fails the run, so the retries buy the trace and the reproduce-or-not signal rather than tolerance for a blip.
- Mount E2E: `pnpm e2e:mount` runs `playwright.mount.config.ts` over `packages/app/e2e/mount.spec.ts`: it runs `pnpm build:mount` into `packages/app/node_modules/.mount-e2e` with a branch of a fake repository as its default, serves the build from `packages/app/e2e/static-server.ts` on port 5282 with single-page fallback and the build's own `_headers`, and answers every GitHub request from `packages/app/fixture` by route interception, failing a test on any Content Security Policy violation. It is **its own CI job, `mount`**, run by neither `verify` nor `e2e`, which ignores the spec; it shares the two Playwright configs' flake policy.
- Build: `pnpm build` (Vite build of the app). `pnpm build:mount` writes the static application for Mounting to `packages/app/dist-mount`: the same `index.html` composed by `src/mount-main.tsx` instead of the HTTP entry, assets under content-hashed names, and a Cloudflare `_headers` file carrying its Content Security Policy (`packages/app/mount-headers.ts`). `VITE_DEFAULT_SPACE_SOURCE`, read at build time, names the GitHub location a page with no `source` parameter mounts; with neither, the page asks for one. `pnpm desktop-sidecar:build` writes the desktop sidecar (ADR 0155; `src/desktop/`) to `packages/app/dist-desktop-sidecar/desktop-sidecar.mjs`, one ES module with every dependency inlined: `node desktop-sidecar.mjs <dir> <built-app-dir>` runs `<dir>` on `127.0.0.1` at a port the system picks, announces `{kind, port, secret}` as one JSON line on standard output (`src/desktop/announcement.ts`), refuses any request not naming its own `Host` or not holding the session cookie it trades for `/?launch=<secret>` (a cookie named for its port, since a webview's cookie store scopes by host, not port), and writes the last edit and exits when its standard input closes, or on SIGINT, SIGTERM or SIGHUP as a run does; a second one exits at once. `test/integration/desktop-sidecar.test.ts` drives it as a process. The desktop shell does not run it (it serves the Rust host); it is the production Node host the HTTP conformance suite holds every other host to. Its rules are Storage ST-113–ST-116.

## Package layout & boundaries

Eighteen `@project/*` workspace packages under `packages/`, and a Cargo workspace at the root:

- `resource-api` — the Resource API, the one door a Resource plugin reaches. `/domain` is the plugin contract with no React: `definePlugin`, `Resource<C>` (the one Resource structure, which `core`'s `Resource` instantiates per kind), outlines, asset references and `Answer`. `/view` is the view half a plugin draws with (`Surface`, Claims and exclusive work, `Title`, `Own` and `Rail`); `/view/host` is what a host provides those components with (`ResourceHostProvider` and the rail store), which a plugin's source may not import; `/view/testing` is `renderPlugin`, the test host, for a plugin's tests only. It depends on no package of ours, which its `rootDir` and lint zone enforce.
- `plugin-ur` — the Ur plugin: `/domain` (its content and Map content schemas) and `/view` (what it draws in its rect). It imports no package of ours but `resource-api`'s `/domain` and `/view`, and its domain half no React and no view.

Seeds, fixtures and tests seed through those same two. Depends on `core` and `graph` so every committed snapshot passes the normal domain intake. It also owns **`createObservableState`**, the one observable-state seam behind `SpaceSession`, Navigation and SpaceAuthoring's own `getState`/`subscribe` interfaces: publication installs the next state synchronously, snapshots the subscriber set so a listener added mid-publication begins at the next one rather than part-way through the current, contains synchronous throws and thenable rejections, continues to the observers behind the failure, and reports through a sink `createNonThrowingReporter` has made incapable of interrupting the work it describes. Root `src/` keeps the filesystem source (`directorySource` in `src/aggregate-directory/`), the SQL repository and the CLI, and imports these from here. Depends on `core`, `graph`, `persistence` and `http`, and imports no Node builtin: the lint zone bans one and `test/unit/aggregate-package-browser-safe.test.ts` reads its sources for one.

A test that wants collaborators calls `composeCore` or `composeApp` rather than writing the chain out.

- `desktop` — the desktop application (ADR 0155): a Tauri shell in `src-tauri/` (Rust) whose Start window (ADR 0171, ST-131; `src/start.rs`, its page `packages/app/start.html`) shows when a launch names no folder or none opens (`src/launch.rs`) and for File › New Space…, whose form writes a new Space through the host's `init_directory`; a folder named on the command line, or chosen from File › Open… or the Start window's Open Folder…, opens as an Aggregate directory, and a missing or empty one is offered a new Space (`src/new_space.rs`), each in a window of its own served by a run of the Rust host (`crates/host`) in the shell's own process, through the `infinitycube` URI scheme with no port, `Host` check or launch secret (Storage ST-121). Beside the pnpm packages, one **Cargo workspace** at the repository root (`Cargo.toml`, one `Cargo.lock`, one `target/`) has five members: `crates/intake`, `crates/host` (the Rust host library, Storage ST-119), `crates/http-conformance` (test code only), `crates/cli` (the `infinity-cube` binary, Storage ST-120) and the desktop shell `packages/desktop/src-tauri` (Storage ST-121), which composes `host` as the CLI does. `intake` is the Rust intake (ADR 0156; Storage ST-118): pure, with no IO and no async, it takes an Aggregate directory's files as bytes by path (`AggregateFiles`) and answers the checked aggregate or every refusal of the first stage that refuses, located as the TypeScript intake locates it. It parses JSON with its own reader rather than `serde`, so a number is the double `JSON.parse` reads and an object keeps its keys in order; its plugin list (`src/plugins/`) mirrors `packages/plugins`, one module per plugin declaring its content rules and its content's key order (which the host's Export reads), and a plugin's content rules change in both in one change. `crates/intake/tests/conformance.rs` runs every directory case of `conformance/intake/` against it. `host` is the Rust host as a library with no listener: the `SpaceRepository` seam, its memory store and the one SQL repository over a database's store of statements, SQLite's and PostgreSQL's (`PostgresStore`) (`src/sql/`, which never migrates and which the CLI's `serve --store sqlite` and `serve --store postgres` serve), whose commits the pure `decide_commit` decides; and `Run`, which Imports, serves and Exports once Edits are quiet, on a clock its builder requires beside the directory and the id source. `crates/host/tests/wire.rs` runs every case of `conformance/http/wire-cases.ts` and `store-condition-cases.ts` against `Application`, `tests/corpus.rs` the corpus's commit cases and the Export bytes of every accepted directory case, and `tests/run.rs` the writer under tokio's paused time, `tests/sqlite_wire.rs` the table and the store-condition cases over the SQLite repository, each on a fresh file `tests/sqlite_support` migrates from `migrations-sql/sqlite/`, and `tests/postgres_wire.rs` the same cases over the PostgreSQL repository: the table on a fresh migrated database seeded with the tracked fixture, the case of a store with no Meta Space on a fresh migrated database holding nothing, the unreachable-store cases on a stand-in that refuses every connection, and the broken-stored-state cases on a database no migration has run on; every case but the unreachable-store ones needs a server and is ignored by default. `http-conformance`, a dev-dependency of `host` and of the desktop shell and nothing else, writes once the HTTP conformance cases both run, against an `Adapter` each implements (`Application::handle`, and the scheme handler), and its `cases!` generates one test per case in each; it also holds the fixture's ids, the stand-in built application and the counted id source their tests share. Each test porting an HTTP conformance case, in that table, `wire.rs`, `run.rs` or the desktop shell's `src/scheme/tests.rs`, carries `// Case: <name>`, and `test/unit/http-conformance-rust-ports.test.ts` fails for a case with no port that it does not exempt with why. `cli` is the `infinity-cube` binary over `host`: `run` puts the host's application behind an HTTP/1.1 listener on `127.0.0.1` with the `Host` check in front, `check` Imports into a store it discards, and `serve --store sqlite` and `serve --store postgres` put the application over the SQLite or the PostgreSQL repository behind the same listener; `tests/check.rs` runs every directory case of the corpus through `check --json`, and `tests/run.rs`, `tests/serve.rs` and `tests/serve_postgres.rs` drive the binary as a process. `anyhow` is allowed in its `main` alone. `rust-toolchain.toml` pins the toolchain, which rustup installs on first use and CI reads from the same file. `[workspace.package]` and `[workspace.lints]` are inherited by every member (`[lints] workspace = true`): `unsafe_code` is forbidden and clippy's `unwrap_used`, `expect_used`, `panic`, `dbg_macro`, `todo`, `unimplemented`, `mem_forget`, `print_stdout` and `print_stderr` are denied, with `clippy.toml` allowing the first three in tests and a narrow `#[expect]` with its reason at each place whose job is to print. A new member joins `members` and inherits both; a dependency used by more than one member goes in `[workspace.dependencies]`.

Hard rules — **all four are enforced, not just documented**. Two layers, because neither catches what the other does: ESLint `no-restricted-imports` zones catch package specifiers and relative escapes (`../../*`), and each package's narrowed tsconfig `paths` makes an illegal alias unresolvable. `rootDir` is set on `resource-api` alone, the one package that resolves no `@project/*` import — anywhere else it rejects the legitimate `@project/*` import too, since the referenced file resolves outside the package, which is why the relative-escape half is a lint rule rather than a compiler setting.

- Domain logic stays out of React (keep it in `core`/`graph`).
- React Flow stays out of the domain and the reusable UI: **`core`, `graph`, `http`, `persistence`, `aggregate`, `ui`, `resource-api` and every `plugin-*` must not import `@xyflow/react`**, which `no-restricted-imports` in `eslint.config.js` enforces. `react-flow-adapter` holds the projection into React Flow, and `app`, the composition layer, imports `@xyflow/react` as well. The same zone names elkjs, which no package depends on. Read that entry as banning a *render-time* engine from the domain, not as siting a returning one: the Map and Graph requirements put Auto-arrange in `graph`, attached to an Edit, so building it means re-siting the ban rather than obeying the lint message.
- Reusable UI goes in `ui`; app-specific glue goes in `app`.
- Vite-config imports by relative path: see [Rules that bite](#rules-that-bite).

## Conventions & gotchas

- **Strict TypeScript everywhere**, incl. `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`.
- **`package.json`'s TypeScript entries look wrong and are not**: `tsc` is TypeScript 7 and the only type-checking truth, and `typescript` resolves to TypeScript 6 on purpose. See [`build-tooling.md`](docs/agents/build-tooling.md) before touching either.
- **`verbatimModuleSyntax` + ESLint `consistent-type-imports` are on** — use `import type` for type-only imports or lint/typecheck fails.
- **Cross-package imports** use the `@project/*` path aliases: declared in `tsconfig.base.json`, mirrored in `vitest.config.ts` `resolve.alias`, and **narrowed per package** in each `packages/*/tsconfig.json` so a package can only resolve what it may legally depend on. Vite's browser build resolves through the workspace `exports`; the server module runner and the server builds start in root `src/`, where pnpm exposes no `@project` symlinks, and take `packages/app/workspace-aliases.ts`. Vitest's *is* load-bearing: the root package declares no `@project/*` deps, so there is no symlink to resolve through. Three lists to keep in sync, plus the package's own narrowed one. **A Resource plugin is aliased by pattern, never by name**: one `"@project/plugin-*/domain"` entry in each tsconfig and one `"@project/plugin-*/view"` entry where the package may reach views; in Vitest, the two patterns `packages/app/plugin-specifiers.ts` exports; in the server list, the domain pattern alone. So adding a `packages/plugin-*` package edits no alias list. `test/unit/plugin-aliases.test.ts` lists the `packages/plugin-*` packages git tracks, fails one lacking `src/domain.ts` or `src/view.tsx`, resolves each through the Vitest and server lists, pins which tsconfigs carry each pattern, and fails any alias list that names a single plugin.
- **Relative imports inside a package are EXTENSIONLESS** (`./foo`, not `./foo.ts`).
- **Use a functional core and imperative shell for cross-module coordination.** Compute and validate the complete next state in a private pure core before producing side effects; a thin imperative shell then updates collaborators in an order that preserves valid intermediate states. Expose the coordination as one operation rather than returning a plan for callers to execute. Keep framework and store events outside the seam, depend on existing module interfaces, and do not manufacture single-adapter ports for deterministic private helpers. An edit event is a notification, not state transfer: each editor first installs its authoritative completed state and only then emits the notification; the coordinator derives the next Space from the current state owned by its collaborators rather than from state carried by the event.
- **Comments and these docs assert only what their writer checked, and carry no lineage.** A negative result or a measurement goes in a ticket, a claim about another module names the test that holds it, and history goes in the commit or the ticket. The rules are [`workflow.md`](docs/agents/workflow.md#what-a-comment-may-assert).
- **Vocabulary is guarded.** `path` means a file path, "arrangement" is prose, and retired words ("workspace", and the retired name for a Space) are held out of the source by `test/unit/current-domain-vocabulary.test.ts`, which no arm runs over Markdown. Read [Workflow](docs/agents/workflow.md#domain-vocabulary) before adding an arm or an exemption.

## Before claiming done

**The full bar runs in CI, on a draft PR.** `pnpm verify`, `pnpm e2e` and `pnpm e2e:ladle` overload the local machine, so the laptop runs targeted checks and CI runs the suite.

1. **Check locally, aimed at the change**: `pnpm typecheck` and `pnpm typecheck:packages`, `pnpm exec eslint <files>`, `pnpm exec vitest run <files>`, and `pnpm exec playwright test <spec>` when iterating on one UI behaviour (`-c playwright.ladle.config.ts` for a story spec under `packages/app/ladle-e2e/`). `pnpm verify:local` is the whole-repo static bar plus coverage at two workers and the TypeScript CRAP gate.
2. **Open a draft PR at the first commit.** Branch off `main`, push, `gh pr create --draft`. CI runs on pull requests and pushes to `main` only, so a pushed branch with no PR is never checked. Asking for the work authorises pushing its branch and opening its draft PR; marking it ready, merging and pushing to `main` wait for the user.
3. **Done is `CI passed` green** — the gate job over every required job. Watch with `gh pr checks --watch`; when the gate is red, find the red job in that list and read it with `gh run view <run-id> --log-failed`. `main` is gated, so the baseline is green and a red job is yours until `git stash` or `git log` on the file shows otherwise.
4. **Report the evidence**: the local commands you ran and those you skipped, the `CI passed` result with each job behind it, and which CI job read what changed, or that none did. Claim success only for a result you watched arrive.
